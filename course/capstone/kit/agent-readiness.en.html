    Agent-readiness scorecard

    An agent can change a repository safely only if it can find the change point, read the rules, run fast and repeatable tests, and hit the same checks your project requires. This scorecard turns that readiness into observations. The repository and numbers in the worked example below are course-made for teaching.

    You score ci-dashboard twice during M1:

    • Start: in week 5, before your first reviewed change merges. Record the commit you scored.
    • End: when you submit M1, on the M1 head commit.

    The change between the two scorecards, plus one blocker you removed and measured again, is your M1 modernisation evidence. Put both scorecards in your M1 work record. This is not a new submission or mark.

    Run every command through the course launcher described in Week 0 setup.

    Score one dimension

    1. Generate. You may ask an approved agent to propose a level and evidence for a dimension. Treat the answer as a list of claims, not a score.
    2. Choose a disproving observation. For each claim, decide which output or file would show it is false. For example, "tests are fast" is disproved by the runner's time.
    3. Verify. Run the command or open the file at the scored commit. Record the commit, the exact command or path, and what you observed.
    4. Score. Give the highest level where you can show every anchor. A dimension with no evidence link is recorded as 1, whatever you believe about it.
    5. Name the top blocker. Write the single observation that keeps this dimension from the next level.

    Score the repository as it is at the commit, not as you plan to make it.

    The student ci-dashboard package starts without a test suite or merge gates, so a level-1 start on Tests or Checks is expected. python3 -I launch.py smoke is a runnable smoke-test command and may be recorded as such, but it does not by itself provide a test suite or a merge gate.

    The four dimensions

    Each level includes everything in the levels below it.

    Structure: can an agent find the change point?

    Probe: pick one behaviour your M0 feature touches. Starting from the README and file names, predict the function an agent must change. Then open files until you reach it and record each file you opened.

    Level Observable anchor
    1 No written map from behaviour to code.
    2 A map exists (a README table or context file), but at least one level-3 anchor is not met, such as an entry you checked being wrong at the scored commit or the change point sitting in a function that mixes unrelated work such as routing, SQL and formatting.
    3 Every map entry you checked is accurate, and the change point is in a function with one responsibility (no routing, SQL and formatting mixed). The probe reached the change point in three file opens or fewer. Each module's responsibility, and what it must not import or own, is written down.
    4 A module boundary is enforced by a test or check, and you show it failing on a deliberate violation.

    Evidence: the probe log (behaviour, files opened in order, path:line of the change point); for level 4, the failing output.

    Documentation: are the rules written where an agent reads them?

    Probe: give a fresh agent session only the context file. Ask how to install, run and test the project, and what must never change. Then copy and run every command it gives you.

    Level Observable anchor
    1 No context file (such as AGENTS.md or CLAUDE.md), or the file lists no run or test command.
    2 A context file lists commands, but at least one fails when copied at the scored commit, or at least one level-3 anchor is not met, such as no project invariant (behaviour or security rule that must not change) being written down.
    3 Every listed command runs as written through the launcher. At least three invariants are written down, and each names the test or check that protects it.
    4 A check runs the documented commands, so a stale command fails the check. You show it failing once.

    Evidence: the file path at the commit, the output of each documented command, and the invariant-to-test list.

    Tests: fast, repeatable, covering what you will change

    Before measuring, agree a time budget for the test command you will run after every agent change. If you have no reason to choose otherwise, use 30 seconds as reported by the test runner. The launcher's own safety checks are not part of this time.

    Probe: run the full test command twice at the scored commit and keep the runner's summary line both times. Search the tests for hidden inputs: the real clock, unseeded randomness, network access, test order and files outside the workspace. Then list the code paths your M1 change will touch. Break one on purpose, run the tests, record the result and revert.

    Level Observable anchor
    1 Both full-suite runs fail, or no runnable test command or test exercises the paths you will change.
    2 At least one full-suite run passes, but at least one of these holds: it exceeds the time budget; a test reads a hidden input; the runs differ; or a deliberate break of a path you will change goes undetected.
    3 Two passing runs with the same pass/fail result for every test, both within the budget, no hidden inputs, and the deliberate break makes a test fail.
    4 Failure messages name the broken behaviour. Your testing workshop evidence shows each surviving mutant on the changed paths was killed or explained.

    Evidence: both summary lines, the hidden-input search, and the deliberate-break output.

    Checks: what must an agent's change pass?

    Probe: list every gate that runs before merge: formatting, lint, type check, secret scan, dependency audit, hooks and CI. Make two deliberately bad changes: add an unused import and add a project-defined canary such as PROJECT_CANARY_0123456789ABCDEF to a source file, with a custom scanner rule such as PROJECT_CANARY_[A-Z0-9]{16}. Record which gate stopped each change, then revert.

    Level Observable anchor
    1 No automatic gate. Correctness depends on someone remembering to run something.
    2 An unused-import change can merge because gates can be run by hand, nothing requires them, or a gate already fails at the scored commit and is ignored.
    3 One offline command or CI job runs every gate and exits non-zero when any gate fails; it stops an unused-import change.
    4 The gates also run where the agent works, through a hook before a commit is offered, so the agent sees the failure itself. A secret scan is among them and its custom rule stops the project canary.

    Evidence: the gate command, its failing output for each bad change it stopped, which gate (if any) let the canary pass, and its passing output after the revert.

    Worked example: "the tests are fast"

    shelf-loans is a small library-loan service. Loans last 14 days, and the library is closed on Sundays. You score the Tests dimension at the start of the milestone.

    # loans/policy.py
from datetime import date, timedelta


LOAN_DAYS = 14


def due_date(borrowed: date) -> date:
    due = borrowed + timedelta(days=LOAN_DAYS)
    if due.weekday() == 5:  # the library is closed on Sundays
        due += timedelta(days=1)
    return due

    # tests/test_policy.py (one of 18 tests)
from datetime import date, datetime
import time

import pytest

from loans.policy import due_date


@pytest.fixture(autouse=True)
def warm_cache():
    time.sleep(2)  # let the catalogue cache warm up


def test_due_date_is_not_sunday():
    today = datetime.now().date()
    assert due_date(today).weekday() != 6

    The warm_cache fixture is in test_policy.py, so it covers all 18 tests in this example only if those tests are in that module. Moving it to conftest.py would broaden its scope.

    Generation. You ask an agent to score the Tests dimension. It answers:

    Tests: 4. The suite is fast and deterministic, and tests/test_policy.py covers the due-date rules.

    Verification. The answer contains three claims: fast, deterministic and covering the due-date rules. You check each one at the scored commit.

    Claim What you ran or opened Observation Holds?
    Fast The test command, twice 18 passed in 36.42s and 18 passed in 36.38s; budget 30 s. Each test spends 2 s in warm_cache, and no test reads that cache. No
    Deterministic Hidden-input search datetime.now() in test_due_date_is_not_sunday. Two passing runs on the same day cannot show what happens on another weekday. No
    Covers due-date rules Set LOAN_DAYS = 13, ran the tests, reverted 18 passed on a Wednesday. Nothing checks the loan length. No

    Start score: Tests 2. The suite runs and passes, but it is over budget, it reads the clock, and a deliberate break goes undetected. Top blocker: the due-date test depends on the day it runs.

    Removing the blocker. You remove the unused sleep and replace the clock with seven fixed dates, Monday 2 March to Sunday 8 March 2026:

    from datetime import date, timedelta

import pytest

from loans.policy import due_date


WEEK = [date(2026, 3, 2) + timedelta(days=i) for i in range(7)]


@pytest.mark.parametrize("borrowed", WEEK, ids=str)
def test_due_date_is_two_weeks_later_or_next_open_day(borrowed):
    due = due_date(borrowed)
    assert due.weekday() != 6, f"due on a Sunday: {due}"
    assert (due - borrowed).days in (14, 15)

    The first run reports 2 failed, 22 passed in 0.41s. Loans borrowed on 7 and 8 March are due on Sunday 22 March. The old test only ever checked the day it ran, so it passed on every run from Monday to Friday. The code compares with Saturday (5) instead of Sunday (6). You record this defect and fix it in a separate reviewed change with this test as its regression.

    End score: Tests 3. Two runs report 24 passed in 0.39s and 24 passed in 0.40s, no test reads a hidden input, and LOAN_DAYS = 13 now gives 6 failed, 18 passed. It is not 4 yet because you have no mutation evidence for this path.

    The scorecard entry for this dimension:

    Dimension Start (commit) End (commit) Evidence Blocker removed
    Tests 2 (a1b2c3d) 3 (e4f5a6b) Summary lines, hidden-input search and the LOAN_DAYS = 13 output at both commits Clock-dependent due-date test: replaced by seven fixed dates; before and after output linked

    Use the same pattern of claim, disproving observation and recorded output for the other three dimensions.

    Worked example on ci-dashboard: Documentation and Checks

    The Week 5 worked example removes one blocker in each of the two dimensions a context file and a hook can raise today on ci-dashboard; Tests waits for a test command. It adds a context file with run and test commands and three invariants, each mapped to a check, and verifies the file with the fresh-session probe. It then adds a pre-commit hook that runs lint and stops an unused-import change. It shows the failing case, the passing case and the resulting scorecard rows.

    What to submit in M1

    Add these to the M1 work record:

    1. Both scorecards: a level, commit and evidence link for each of the four dimensions, plus the top blocker named at the start.
    2. One removed blocker: the start observation, the reviewed change that removed it, and the same observation repeated at the end commit.
    3. One sentence per dimension explaining why the level changed or stayed the same.

    How it is marked

    The scorecard is evidence for the agent workflow design dimension of the course rubric within M1's 6 points. Its four workflow levels are: context and configuration absent; context and configuration present without a gate or cost record; context, skills, hooks, permissions and evaluation gates with a cost record; and A/B or cost comparison plus reusable project norms.

    • Markers reopen a sample of your evidence links at the commits you name. A level that the evidence does not support is corrected to the level the evidence shows.
    • The size of the change does not earn marks. A dimension that honestly stays at 2 is acceptable. Scoring the start low to make the change look larger does not help, because start evidence is checked against the start commit.
    • One removed blocker with before-and-after observations is enough for full marks on this scorecard's M1 evidence. Removing more blockers does not raise this scorecard's ceiling.
    • Deleting or skipping tests, or turning off a gate, does not count as removing a blocker. It lowers the Tests or Checks level. Replacing a test with one that still fails on every deliberate break the old test caught is not deletion, as in the worked example. Markers check this by:
    • Re-running the intentional break recorded at the start on the end commit.
    • Comparing the passed, skipped, xfailed, and deselected counts in both summaries.
    • Reading the complete git diff <start> <end> -- <test paths> for the test paths.

    Common mistakes

    • Accepting an agent's level because it sounds right. Every level needs a command output or a file path at a named commit.
    • Treating two passing runs as proof of repeatability. Search the test code for hidden inputs as well.
    • Counting a gate that exists but does not block a bad change.
    • Timing the whole launcher command. Use the time the test runner reports.
    • Scoring planned work. Score what the commit shows, and put the plan in the blocker line.

    AI use

    You may use an approved agent to propose levels and evidence. The verification commands, recorded observations and per-dimension explanations are your own. Note AI use once in the M1 work record and reuse its ID.

    Estimated time

    About 45 minutes for each scoring pass. The first 15 minutes of the start pass are the Week 5 workshop's readiness activity. Removing the blocker is part of your M1 change, not extra work.
