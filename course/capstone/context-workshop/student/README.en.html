    repository-context workshop: Find the relevant context

    This page describes the earlier fourteen-week layout and is being rewritten; where it differs, the syllabus applies.

    At a glance

    • Task: finish the class map of one ci-dashboard request by hand, choose context for a fixed question and rehearse the paired collection, check one permission boundary, package your tracing method as a SKILL.md, test when it triggers and use it once read-only on your candidate contribution project, then revise a small ci-dashboard tool server until an agent could use it safely, and prove that with a test that speaks the protocol.
    • Hand in: one work record holding the call-path map, the A/B report, both boundary results, your skill directory, trigger-test.yaml, skill-transfer.yaml, the revised tool_behavior.py, test_protocol.py and your own explanation.
    • Done when: skill_check.py, transfer_check.py and public_check.py report no problems, test_protocol.py passes through the launcher, and every prompt in explanation.en.md has an answer that points at something you actually observed.
    • Time: about ten hours in Week 3, including the Week 3 class time spent on Part A, which begins with the class map. This is practice inside M0, not a separate mark.

    Objectives

    Trace one request across files in ci-dashboard (LO4). Choose the context an agent needs, verify one permission boundary, package a repeatable procedure as a skill whose description fires when it should, and design tools for a reader that sees only their names, schemas and descriptions (LO2). Each part has the same rhythm: generate or write something, check it against an expectation you set first, then change one thing.

    Prerequisites

    Complete Week 0 setup; its launcher and profile resolver are the only supported way to run the commands below. Commands run from the supplied course root. Copy only this public student/ directory into a new workspace outside the private repository; exclude .git, caches, wheels, teacher assets and credentials. On macOS use an absolute path under /private/tmp, since /tmp is a symlink the launcher rejects. Replace LAB_WORK with your workspace path. Resolve VERSION and DIGEST using:

    uv run --project infra/hosted --locked python infra/hosted/resolve_profile.py --profile offline --json

    Tasks

    Part A: context and boundaries

    1. Map the project-list path (50 minutes, the first 15 in class). Work in your own ci-dashboard repository (get it first if you have not). Follow GET /domains/ci_dashboard/ from the route to what the visitor sees, reading the source; the application does not need to run. In your work record, keep:
    2. the commit you read (git rev-parse HEAD);
    3. the path as a text list of arrows, each labelled confirmed (file:line at that commit), refuted (what the code does instead) or cannot tell;
    4. every branch the arrows hide: what a visitor without a session receives, and what the page shows to a user with no projects;
    5. one open behavior question with the test you would look for before editing, and a bounded edit with what a caller would observe after it.

    Then ask a classmate or a TA to pick one arrow you labelled confirmed and try to show from the code at your commit that it is wrong. Record whether it held. You reuse this map in step 5 and when you choose your M0 scope. 2. Select context (40 minutes). Read the starter application and starter-app/app.py; the fixed task asks which path checks this app's health. Edit context.py as text. Keep its Project, Commands and Boundaries sections; replace placeholders with relevant facts from the starter application and check each fact against a line of app.py or its README. Packet A will contain only the fixed task; packet B adds this context. Predict which packet would let a model answer the health-path question, and why. The collector enforces the approved model's combined prompt-byte limit before generation. Shorten context when told to; do not change model parameters. 3. Verify a boundary (30 minutes). Read the supplied hook.py. Predict both results, then run each command separately. Keep the hook unchanged.

    sh sh scripts/course-sandbox --profile offline --version VERSION --digest DIGEST --workspace LAB_WORK -- python -B hook.py '{"event":"before_write","path":"src/app.py"}' sh scripts/course-sandbox --profile offline --version VERSION --digest DIGEST --workspace LAB_WORK -- python -B hook.py '{"event":"before_write","path":"../outside.py"}'

    The first should exit 0 and the second 2. Explain why an allowed ordinary edit and a rejected escape are both necessary. The hook illustrates policy; the launcher's isolation is the actual execution boundary. 4. Collect one fixed pair (45 minutes). Run the course controller from the course root. It runs the health task once without context and once with it, with fresh execution and identical approved configuration. Use a new output directory outside the workspace.

    sh uv run --project infra/hosted --locked python capstone/context-workshop/student/ab_collect.py LAB_WORK --core --output LAB_EVIDENCE

    The pair runs on the FAKE practice route: both rows receive the same fixed practice reply, so both fail the health task whatever your context says. It rehearses the workflow only (two fresh runs, identical configuration, one call each, metrics and a receipt) and is not real-model evidence. It cannot confirm or refute your step 2 prediction, so record that prediction as cannot tell. Check instead that ab-report.en.md says Mode: fake and has one without and one with row. The course replay in step 1 of the Week 3 fixture guide is where you see two packets change an answer. A runtime failure keeps its attempt record: preserve it and ask for help before a new, labelled attempt.

    Part B: a skill that fires when it should

    A skill is a directory with a SKILL.md file: YAML front matter with a name and a description, then a Markdown body with the procedure. An agent that supports skills sees only the name and description until it decides to load one, so the description decides whether the skill is ever used. The body is loaded only after that, and everything in it then costs context, so hold the procedure itself there and leave longer background in a separate file in the same directory. A skill grants no permission and does not replace the launcher.

    1. Write the skill (45 minutes). In step 1 you traced the project-list path by hand across three files and checked each arrow at one commit. Write that procedure as skills/trace-request/SKILL.md, so an agent or another developer can repeat it on another request. The supplied skills/verify-change/SKILL.md shows the format for a different job; do not copy its content.
    2. name: trace-request, matching the directory name.
    3. description: both the job the skill does and the situation that should trigger it, phrased the way a person would ask for it ("Use when ..."). At least eight words.
    4. ## Steps: at least two concrete steps; give the exact command for any step a command can do.
    5. ## Judgement: the decisions a step list hides: which way to go when more than one reading fits ("If two routes match, ..."), and the moves to avoid.
    6. ## Verification: the exact command or check, in backticks, that shows the trace was right.

    Check the structure from the course root; it reads your files as data:

    sh uv run --locked python capstone/context-workshop/student/skill_check.py LAB_WORK/skills/trace-request/SKILL.md LAB_WORK/trigger-test.yaml

    The trigger-test problems it reports are for step 7. 6. Use it on ci-dashboard (30 minutes). Choose a different request in your ci-dashboard repository from the one in step 1. Follow your own skill, with or without an approved agent, and write three lines in your work record: what you did by hand in step 1, what the skill made you do differently, and one step, judgement or verification you changed after using it. Step 3 of the Week 3 studio uses the same loop for a skill's description: record the mismatch, name the change, recheck. A skill nobody has used is a draft.

    Then carry it to your candidate contribution project (about 60 minutes). A skill written beside one repository quietly assumes its layout. Use yours once more, read-only, on the project you have picked as a candidate for your contributions, and record that run in skill-transfer.yaml. If you have no candidate yet, use one of the repositories listed below or another that meets the same criteria.

    • Choose the repository and one request you can trace: an HTTP route, a command-line command or a message handler. The repository must be public, on any forge, under a licence the Open Source Initiative has approved (MIT, Apache-2.0, the BSD licences, GPL, LGPL, AGPL, MPL-2.0 and many more; transfer_check.py holds the full list), which every approved contribution project meets. If you chose the course-hosted contribution route, use the course practice repository and add route: course-hosted under repository in your record. Export only the part that holds the request: at most 200 files and 1 MB. Any of the repositories below also fits; their licence and size were read from each repository at the commit shown.

      Repository Commit Licence (file) Export these paths Files A request to trace
      https://github.com/miguelgrinberg/microblog a975ef64864354867c88e0ed3a17ba7d17dca752 MIT (LICENSE) app microblog.py config.py tests.py LICENSE 47 GET /api/users/<id>
      https://github.com/pallets/flask d73fa1cdcbd8b1465c151db8924ba58b1dd14e35 BSD-3-Clause (LICENSE.txt) examples/tutorial LICENSE.txt 23 POST /auth/register in the tutorial app
      https://github.com/bottlepy/bottle cbd569c447b3fd53f194cef9a306146ce6a07a59 MIT (LICENSE) bottle.py test LICENSE 45 how a route's return value becomes the response body

      Whichever repository you use, your record names it and the commit you exported. - Export one pinned commit on your own machine with plain git. Type these commands yourself and never run a model-suggested command outside the launcher. OSS_CLONE is a new folder outside your workspace and LAB_OSS a new, empty one; the example uses the first row:

      sh git clone --no-checkout https://github.com/miguelgrinberg/microblog.git OSS_CLONE mkdir LAB_OSS git -C OSS_CLONE archive a975ef64864354867c88e0ed3a17ba7d17dca752 app microblog.py config.py tests.py LICENSE | tar -x -C LAB_OSS find LAB_OSS -type f | wc -l cp -R LAB_WORK/skills LAB_OSS/skills

      git archive writes exactly that commit's files without .git, which the launcher refuses anyway. Do not install the repository's dependencies or run its code on your machine. If the launcher reports the folder as too large, export fewer paths. - Run the skill on LAB_OSS through the launcher only, with an approved agent that loads SKILL.md skills or by following it yourself. The launcher copies LAB_OSS into a container with no network and discards every change, so your export stays exactly as exported. Run each command the skill names as sh scripts/course-sandbox --profile approved-hosted --version VERSION --digest DIGEST --workspace LAB_OSS -- COMMAND. With an agent, ask the way a user would, without naming the skill, and record whether the session loaded your skill. Never fill that in from what a model says it would do. The container has no network, so the repository's own dependencies are usually missing: a verification step that cannot run there is a misfit worth recording. - Record in skill-transfer.yaml the repository, the commit and what you exported, how you ran the skill, the path it traced (files and functions), one step, judgement or verification that did not fit this repository, and the change you then made to LAB_WORK/skills/trace-request/SKILL.md, with what you saw when you used the changed skill on the same request. If the skill did not trigger, change its description first. Point skill.transfer in agent-capabilities.yaml at the record and check it from the course root:

      sh uv run --locked python capstone/context-workshop/student/transfer_check.py LAB_WORK/skills/trace-request/SKILL.md LAB_WORK/skill-transfer.yaml

      It reads both files as data. It checks that the record is complete and agrees with your skill, never whether the skill fired or traced well. 7. Test when it triggers (45 minutes). Fill trigger-test.yaml. Write at least three requests that should load your skill, worded the way people ask (do not name the skill), and at least one near miss that sounds similar but needs something else, such as a request verify-change should answer. Set should_trigger and write your predicted value for every prompt before you observe anything. Then observe with one of two routes and record which in observer and observer_detail: - peer (the template's default): a classmate who sees only the two skills' names and descriptions, then one prompt at a time, and says which skill they would load, or none. - agent, when your course provides an approved agent that loads SKILL.md skills: install both verify-change and your skill where that agent looks for skills. Use a fresh session per prompt and record whether it loaded your skill.

    Both routes earn the same feedback. If any observed value differs from should_trigger, change the description once, observe only those prompts again and record the result under revision. The feedback checks that your record is complete and consistent; it does not reward or penalize what the observer chose. Run the skill_check.py command again until it reports no problems. Its advisory table lists the words each prompt shares with your description; a should-trigger prompt that shares none is a common reason a skill never fires.

    Part C: a tool server an agent can use

    The supplied server exposes ci-dashboard records through four tools. protocol.py is the course scaffold: it speaks the stdio protocol, checks every call's arguments against the tool's published inputSchema (including enum, minimum, maximum, required and additionalProperties), fills schema defaults, limits each session to 12 accepted calls a minute and turns an unexpected exception into a structured error. Leave it unchanged. tool_behavior.py is a working first draft for you to revise. ci_snapshot.json is a small synthetic export with ci-dashboard's projects, pipelines, builds and build statuses. The exact contract is in SPEC.en.md.

    An agent chooses and calls tools from their names, schemas and descriptions alone, so review the draft against five rules:

    1. Put every limit in the schema. Write the allowed statuses as "enum": [...]: the scaffold rejects any other value before your code runs, and the agent can read the full list of valid values. A limit stated only in the description is invisible to that check. When the two disagree, the agent meets rejections that nothing it read accounts for.
    2. Return only what the next step needs. Hand back the fields an agent will use, not the stored record. Every extra field is paid for again at each later step, and mirroring the storage layout breaks your tool when that layout changes. If you cut a list short, say so.
    3. Report a failure as a result the agent can read. Return a structured error naming what failed and whether trying again could succeed: an unknown ID fails every time, a rate limit clears. A raw exception gives the agent nothing to act on; a structured error tells it whether a retry is worth making.
    4. Say what comes back and where each input comes from. State what each tool returns and which tool produces each ID it accepts ("the pipeline_id returned by list_pipelines"), so the agent can call them in sequence. Guidance that spans several tools goes in the server INSTRUCTIONS.

    5. Guard every irreversible action. Mark the read-only tools with readOnlyHint: true. Give the irreversible tool destructiveHint: true and a dry_run argument that defaults to true, so a call that leaves it out only previews the effect.

    6. Review the draft (30 minutes). Before running anything, list in your work record which rule each part of the draft breaks and what an agent would do wrong because of it. Then run the public check and compare its report with your list:

    sh sh scripts/course-sandbox --profile offline --version VERSION --digest DIGEST --workspace LAB_WORK -- python -B public_check.py

    It checks the hook and the static half of rules 1, 4 and 5 through tools/list. It cannot see rules 2 and 3 or the brake's behavior; those need calls.

    Optional: watch an agent use your server (about 15 minutes, not in the estimate). server_replay.py gives your server one request: "Cancel the running build on the unit-tests pipeline. An old ticket gives its build_id as 103." The agent is a short course-written policy, not a model; its six rules are listed in the script. For the draft, predict whether the agent carries an ID from a result into its next call, recovers when the ticket's ID is wrong, and previews before it cancels. Then run:

    sh sh scripts/course-sandbox --profile offline --version VERSION --digest DIGEST --workspace LAB_WORK -- python -B server_replay.py --summary

    On the draft, the first call cancels build 103, which had already passed, and the running build keeps running; the last line gives the three observations. Run it again after step 9, and once with --ticket-id 999, and mark each prediction confirmed or refuted. The policy reads only the field names in the contract and never sends a bad argument, so it shows what your result shapes, errors and brake allow, not how a model reads your schemas and descriptions. It calls the scaffold inside its own process, which is why it cannot serve as your protocol test. Nothing in feedback reads its output. 9. Revise the tools (120 minutes). Edit tool_behavior.py until the server meets the contract. Keep the tool names and read data only from the store the scaffold passes in: feedback runs your server against a different snapshot with the same shape. Change one rule at a time and rerun the public check. Ask for feedback once your schemas pass, before you start on shaping and errors. 10. Test through the protocol (45 minutes). Write test_protocol.py: start protocol.py as a subprocess (from the test file's own directory), send JSON-RPC lines, read the responses and assert on them. Cover at least one chain (list_pipelines to search_builds to get_build), one error with its retryable value, and the brake (omitting dry_run previews and leaves the build running). Importing tool_behavior and calling functions does not count: a protocol test must fail when the protocol layer is broken. The feedback runs your test against the supplied protocol.py, against a server that answers identically but is written differently, and against a broken copy of each, so assert on the responses, not on the server's source text or file digest. Run it through the launcher:

    ```sh
sh scripts/course-sandbox --profile offline --version VERSION --digest DIGEST --workspace LAB_WORK -- python -B test_protocol.py
```

    Part D: explain

    1. Explain and revise (45 minutes). Compare your predictions in steps 2, 7 and 8 with what you observed, including the replay if you ran it. Explain one useful context fact, one limitation of the two-observation experiment, the trigger prompt you predicted wrongly and why, and the rule whose fix changed the most agent-visible behavior. Discuss feedback and revise once.

    Deliverables

    Keep the project-list map with its commit, the two context packets (reference the fixed task and context.py), the generated ab-report.json and ab-report.en.md with their two traces, both boundary results, skills/trace-request/ with its three before/after lines, trigger-test.yaml, skill-transfer.yaml, your revised tool_behavior.py, test_protocol.py with its launcher output, the replay output if you ran it, and your short independent explanation. Keep agent-capabilities.yaml pointing at these files. Use the existing work record. The teaching team keeps the controller receipt separately; do not place private receipts or unrelated conversations in your work. Incomplete runs stay incomplete.

    Grading

    Check Points
    Context output has the three sections and fits 2,000 characters 10
    SKILL.md structure: name, description with "when", steps, judgement, verification 10
    Trigger test and candidate-project run recorded completely and consistently 10
    Tools discovered and chained correctly on unseen data 10
    Rule 1: schema constraints, and the handlers accept exactly what the schema says 10
    Rule 2: documented fields only, bounded size, truncation reported 10
    Rule 3: structured errors with the right retryable value, and the call allowance 10
    Rule 4: descriptions name ID sources, agree with the schema; server instructions 5
    Rule 5: annotations, dry_run default, preview leaves state, commit changes it 10
    Your protocol test passes, and fails when the protocol layer is broken 5
    Hook allows the ordinary edit and rejects every unsafe event 5
    A/B report complete with controller evidence 5

    These points show which checks pass; the workshop has no separate course mark and its evidence counts towards M0. A higher model pass rate is not required, and the trigger check never rewards what the observer happened to choose. Feedback calls the files your manifest declares, so relocated files earn the same points; it runs your server on a different snapshot, so answers recorded from ci_snapshot.json earn nothing. See the syllabus for the portfolio and project allocation. The optional extension has the HTTP adapter and the three-pair comparison; it adds no requirement.

    AI use rules

    • Green: context text, the skill body, tool revisions and the protocol test may use approved assistance. Generated code and commands run only through the launcher.
    • Yellow: if an agent is your trigger observer, record what the session actually did; never fill observed from what a model says it would do.
    • Red: write the predictions (steps 2, 7, 8) and the final explanation yourself.

    Attach one AI-use note to the work and reuse its ID:

    E-01: tool/model and purpose, or "none"; what I verified myself; evidence references.

    Estimated time

    About ten hours: Part A 2 h 45 min, Part B about three hours, Part C 3 h 15 min, Part D 45 min. These are planning estimates for Week 3, not limits. Record your predicted and actual time in the existing calibration log. Ask for help at the first boundary check, after your schemas pass, or whenever the plan stops fitting.
