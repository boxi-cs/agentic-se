    Tests that detect a meaningful fault

    Objectives

    Use mutation testing, explain one property and replay a supplied fuzz case; reuse the method (and the tests you wrote) in M1. (LO5).

    This workshop starts with a small public utility extracted from the ci-dashboard validation boundary. It is deliberately outside the M1 seed set; no M1 seed or seed input is copied into this exercise. The workshop target is a UTC timestamp parser; the project tests later apply the same three checks to your own M1 target.

    Prerequisites

    Use Week 0 setup and the week 7 activity. Run the commands from the course root. They copy only fixture/ and student/ into a new workspace, so the original fixture stays unchanged and a peer can reproduce the baseline.

    Tasks

    1. Predict and challenge the public target

    Read fixture/target.py and student/checks.py without running them. Predict which mutants the weak check can kill. Run the weak suite and the bounded mutation command, then record one surviving mutant and the input that should distinguish it. Add one assertion to weak_checks in student/checks.py, rerun the mutation command, and keep the before/after output.

    2. Add a property and replay a fixed fuzz input

    Run the property suite. Explain its input domain and one boundary it does not cover. Run the seeded fuzz command and replay the supplied invalid timestamp exactly. Keep the seed, input, command and observed result together. A passing property or an empty fuzz report is evidence about that configuration only; it is not a proof of correctness.

    3. Move the method to M1

    On your own M1 test target, state an independent oracle, add one property, and replay one reproducible fuzz input. Do not copy the public timestamp function or any M1 seed fixture. Record the target revision, test command and result in the existing M1 functional baseline.

    Every command in tasks 1-3 runs through the course launcher; see where commands run.

    Start with the linked classroom activity: save a prediction, inspect its public fixture, and explain a result before revision. It rehearses the workshop method. For task 3, use the project bundle described in the M1 project route: it is the M1 test target and holds the mutation configuration (mutants.json and mutant_manifest.json) and the bounded fuzz corpus (fuzz-corpus.json). A classroom fixture result alone does not complete task 3.

    Deliverables

    M1 tests and before/after evidence. Reuse the existing work record; include the workshop commands, verification and your own short explanation, not an additional report. The public fixture catalog records the checked-in baseline runtime.

    Grading

    This workshop is part of M1. Keep its evidence in that milestone; there is no separate submission or course mark. Public mutation numbers and feedback_score provide feedback only; they never enter the course mark. M1 is assessed by reading your tests and before/after evidence against the project rubric; the number is not imported. See the syllabus.

    The general rubric's mutation-threshold wording in Testing strategy does not apply to M1 or to feedback_score; use the workshop's feedback goal and explain the evidence.

    AI use rules

    Use approved assistance for open work. Complete initial individual review, discovery notes and personal explanation/reflective reasoning yourself. Independent checks and oral defense are AI-off. Attach AI use once and reuse its ID. If a model proposes a test, read it first, run it as described in where commands run and keep the launcher result with the test revision.

    Estimated time

    Up to 4 hours inside the corresponding milestone budget, including verification, waiting and revision. This is not an additional homework quota.

    Commands

    Where commands run

    Run every command in this workshop through the course launcher, as in the Week 7 activity: the fixture runner, the project scripts, checks you wrote yourself and any model proposal. Read a model proposal as text before you copy it into a workspace, and never put a key in a workspace. Each launcher command takes about 40 seconds because it repeats the launcher's safety checks first. The uv run lines under teaching-team host check are for the teaching team's own machine; they are not a student route.

    Timestamp fixture

    From the course root, copy the public fixture into a new workspace and resolve the offline launcher profile once:

    testing_work=$(mktemp -d ./testing-workshop.XXXXXX)
cp -R capstone/testing-workshop/fixture capstone/testing-workshop/student "$testing_work/"
testing_profile=$(uv run --project infra/hosted --locked python infra/hosted/resolve_profile.py --profile offline --json)
testing_version=$(printf '%s' "$testing_profile" | python3 -c 'import json,sys; print(json.load(sys.stdin)["version"])')
testing_digest=$(printf '%s' "$testing_profile" | python3 -c 'import json,sys; print(json.load(sys.stdin)["digest"])')

    Run each command separately:

    sh scripts/course-sandbox --profile offline --version "$testing_version" --digest "$testing_digest" --workspace "$testing_work" -- python fixture/runner.py weak
sh scripts/course-sandbox --profile offline --version "$testing_version" --digest "$testing_digest" --workspace "$testing_work" -- python fixture/runner.py mutation
sh scripts/course-sandbox --profile offline --version "$testing_version" --digest "$testing_digest" --workspace "$testing_work" -- python fixture/runner.py property
sh scripts/course-sandbox --profile offline --version "$testing_version" --digest "$testing_digest" --workspace "$testing_work" -- python fixture/runner.py fuzz --seed 17
sh scripts/course-sandbox --profile offline --version "$testing_version" --digest "$testing_digest" --workspace "$testing_work" -- python fixture/runner.py replay --text '2026-02-30T12:00:00Z'
sh scripts/course-sandbox --profile offline --version "$testing_version" --digest "$testing_digest" --workspace "$testing_work" -- python fixture/runner.py fuzz --seed 17 --implementation calendar_check_removed
sh scripts/course-sandbox --profile offline --version "$testing_version" --digest "$testing_digest" --workspace "$testing_work" -- python fixture/runner.py replay --implementation calendar_check_removed --text '2026-02-30T12:00:00Z'

    Edit student/checks.py inside $testing_work, rerun the mutation command and retain both reports. A model-proposed check goes into the same file only after you have read it, and runs through the same command.

    M1 project route: ci-dashboard validation

    The project bundle in project/ is the runnable M1 target. It is a teaching snapshot of capstone/legacy/ci-dashboard/domains/validation.py, with the same public validation contract and no instructor seeds. The course uses a small deterministic standard-library mutator plus a bounded property helper. This route is selected because the launcher image has no mutation package, pytest or Hypothesis; fixed source replacements are auditable and accept --seed, with no package installation or network access.

    From the course root, copy the public project files into a new workspace (reuse testing_version and testing_digest from the timestamp fixture) and run the supplied calibration commands:

    m1_test_work=$(mktemp -d ./m1-test-work.XXXXXX)
mkdir "$m1_test_work/project"
cp -R capstone/testing-workshop/project/domains capstone/testing-workshop/project/fixtures capstone/testing-workshop/project/replay capstone/testing-workshop/project/tests "$m1_test_work/project/"
cp capstone/testing-workshop/project/*.json capstone/testing-workshop/project/*.py "$m1_test_work/project/"
sh scripts/course-sandbox --profile offline --version "$testing_version" --digest "$testing_digest" --workspace "$m1_test_work" -- python project/run_property.py
sh scripts/course-sandbox --profile offline --version "$testing_version" --digest "$testing_digest" --workspace "$m1_test_work" -- python project/run_fuzz.py --seed 17
sh scripts/course-sandbox --profile offline --version "$testing_version" --digest "$testing_digest" --workspace "$m1_test_work" -- python project/run_mutation.py --tests project/fixtures/weak_tests.py --seed 17
sh scripts/course-sandbox --profile offline --version "$testing_version" --digest "$testing_digest" --workspace "$m1_test_work" -- python project/score_submission.py --tests project/fixtures/weak_tests.py --seed 17

    Save your own test file as project/tests/student_tests.py inside $m1_test_work, whether you wrote it or a model proposed it, and score it the same way:

    sh scripts/course-sandbox --profile offline --version "$testing_version" --digest "$testing_digest" --workspace "$m1_test_work" -- python project/score_submission.py --tests project/tests/student_tests.py --seed 17

    The mutation runner applies every replacement in the fixed mutants.json configuration to a new clean copy and isolated child process, records the seed, and emits JSON. The scorer runs the same process and independently computes formative feedback; it never trusts a submitted score or model prose. A baseline is required before mutation runs. A timeout, skipped or missing dependency is one infrastructure failure and produces no feedback_score; it is never a kill, survivor or denominator reduction. The public project/mutant_manifest.json lists equivalent and control entries beside mutants.json, with a kind and contract reason. Only behavioral entries form the denominator. Equivalent mutants are removed from the denominator only when the published contract reason says their behavior is identical. Source-only equivalent controls are also run; killing one marks the report identity_probe and sets its feedback_score to null. A killed mutant is one for which the submitted tests fail against the changed implementation. A survivor remains a survivor until a test or a written contract explanation addresses it. An equivalent mutant is excluded only when the contract makes its observable behaviour identical (for example, a message-only change); the report must list its name and reason. A timeout, missing dependency, crash, or launcher failure is the same infrastructure failure rule, never a kill, survivor or denominator reduction. The denominator is every selected behavioral mutant from the fixed run configuration. Do not delete a test, edit the harness, alter the source snapshot, or hard-code a sample output to change it; the clean-copy scorer and independent oracle are what the teacher uses for feedback. The feedback goal for this workshop is 0.70. Equivalent mutants are listed by the teacher with a contract reason.

    Agent-generated tests and evidence

    Ask the approved model, or use the public frozen FAKE/replay response in project/replay/frozen.json, to propose tests for one M1 validation claim. Treat the proposal as untrusted text: inspect it, save the claim and expected counterexample, and execute it through the launcher. Run the resulting test file with score_submission.py. For every surviving mutant, record the mutant name, the observation that the test failed to make, and the model claim it disproves (or mark that the claim remains unverified). Then add one property with an independent oracle and rerun mutation and fuzz with the same seed. The model response is evidence of generation; mutation, property and replay outputs are the verification evidence. The scoring tool never reads or scores model prose.

    Keep a single work-record row for the target revision, test path, seed, mutation command, selected denominator, killed/surviving/equivalent names, infrastructure failures and the before/after feedback score. The weak, partial, strong and reference fixtures are calibration examples; they are not student answers or a grade.

    A frozen FAKE response is generation evidence only. The reference suite stays under project/instructor/ and is removed from the student package; the public manifest beside mutants.json is the only denominator declaration.

    Teaching-team host check

    On the teaching team's machine, these commands check the course-written project files directly from the repository root. catalog.json records the timestamp fixture commands run the same way with uv run --no-project python from this directory. Students use the launcher commands above.

    uv run --locked python capstone/testing-workshop/project/run_property.py
uv run --locked python capstone/testing-workshop/project/run_fuzz.py --seed 17
uv run --locked python capstone/testing-workshop/project/run_mutation.py \
  --tests capstone/testing-workshop/project/fixtures/weak_tests.py --seed 17
uv run --locked python capstone/testing-workshop/project/score_submission.py \
  --tests capstone/testing-workshop/project/fixtures/weak_tests.py
