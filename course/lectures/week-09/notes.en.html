    Week 9: Three questions before trusting a pass rate

    Learning objectives

    Before you trust a pass rate, ask three questions: Can this check fail? Was this pass earned? Is the denominator intact? By the end of this lesson you can find an input that a wrong implementation gets wrong but a weak check never tries, show a correct result that an overstrict check rejects and write the assertion the contract actually asks for, judge a recorded pass from its trace and the task's own authorization, and report a full-set rate beside a justified reliable subset without claiming more than the experiment observed (LO6).

    All data in this lesson are invented for teaching. Read these notes after the lecture: the slides ask for each prediction before showing its answer, while here each answer follows its prompt. Then use the workshop and self-check.

    Opening prediction (10 minutes)

    Consider this headline: "Workflow B beats A by 25 percentage points on our benchmark." Before discussion, write whether you believe it and what you would need to see. Keep that first answer in your work record; do not rewrite it after seeing the examples. A percentage-point difference is a difference between rates, not a relative improvement.

    Minimal example

    The continuing dashboard case (20 minutes)

    The dashboard's report fixture declares four tasks with one attempt each. Its records:

    Task ID in the fixture Attempts Result
    A s9-a 1 pass
    B s9-b 1 fail
    C s9-c 1 pass
    D s9-d 1 timeout

    The starter in candidate.py builds its report like this:

    completed = [row for row in records if row["result"] != "timeout"]
return {
    "status": "ok",
    "successes": sum(row["result"] == "pass" for row in records),
    "total": len(completed),
    "timeouts": sum(row["result"] == "timeout" for row in records),
    "coverage": len(records),
}

    Fix the contract before inspecting the proposal

    The frozen protocol declares exactly four unique task IDs, one attempt per task and a teaching split. Every row has a declared task ID and the declared attempt count. Missing or duplicate tasks and extra attempts produce exactly {"status": "invalid"}. For the valid set, report successes, the full task count, timeout count and observed coverage. A timeout is unsuccessful under this protocol, not an omitted task.

    Predict a failure

    The public checks in exercise.py feed the starter four inputs:

    Check Input Required report
    declared_set the four records successes 2, total 4, timeouts 1, coverage 4
    missing_task the first three records {"status": "invalid"}
    duplicate_task the first three records plus s9-a again {"status": "invalid"}
    extra_attempt the four records, s9-a with attempts: 2 {"status": "invalid"}

    Before execution, write what the starter will report for each row. Then read on.

    The starter reports total 3 on the declared set, because it drops the timeout. It summarizes the three broken inputs as if the experiment were valid, because it never checks the declared IDs or the attempt budget.

    Repair, then keep verification independent. Validate the declared ID set, uniqueness, row count and per-task attempt budget before summarizing, and keep the timeout in the four-task denominator. Reject protocol violations; never edit the frozen inputs or expected checks to improve the result. A proposal from a person or an allowed assistant, given only the public contract and fixture, stays a candidate until checked through the workshop execution route; keep your own explanation attributable.

    A paired workflow and trace to interpret

    Two workflows ran the same frozen task set with a one-call budget:

    Task Workflow A Workflow B
    A pass pass
    B fail pass
    C pass fail
    D timeout timeout

    Both have two successes out of four declared tasks, but they differ on B and C. Keep that disagreement instead of concluding they behave the same. The trace for workflow A, task B is:

    read contract -> surrounding-whitespace rule supplied
write R1 -> write recorded
verify R1 on " OK " -> unknown; required passed
stop -> call budget exhausted; first attempt failed

    This rules out "no rule supplied" and "no verification" as explanations of this trace. It supports a faulty candidate on the observed case. It does not identify the model's intention. A later feedback-driven repair belongs to a separate result with its added time and usage. Missing usage remains unknown.

    The snapshot fingerprints the supplied protocol and observations; record your candidate revision separately, because the fixture version is not a Git commit. Compare one changed factor only when task IDs, attempt and feedback budget, starting state and verification are otherwise fixed; an adaptive repair is not a fresh sample. A trace should identify the task, action, observation, tested revision and stop condition, with latency and total usage; unavailable usage or price stays unknown. Neither an unusual score nor a hash alone proves misconduct.

    Hands-on exercise

    Can this check fail? (25 minutes)

    Two small dashboard functions carry the examples in this section and the next: newest, which picks the newest release, and pass_rate, which computes a rate. Each example runs the same way: predict, trace on paper, then reveal. Work in pairs.

    Which release is newest? (10 minutes)

    newest(versions: list[str]) -> str

Each version is "MAJOR.MINOR": two non-negative integers without leading zeros.
The list is non-empty. Return the newest version: the higher MAJOR wins; if MAJOR
is equal, the higher MINOR wins. Compare the numbers, not the text.

    The benchmark checks four rows:

    Input Expected
    ["1.2"] "1.2"
    ["1.2", "1.3"] "1.3"
    ["2.0", "1.9"] "2.0"
    ["1.4", "1.1", "1.3"] "1.4"

    Predict (2 minutes). Write the shortest newest you can that passes all four rows. Then predict pass or fail on each row for this candidate:

    def newest(versions):
    return max(versions)

    Break it (2 minutes). Find one input where the candidate and the contract disagree. If you are stuck, ask: what do all checked inputs share that the contract does not require?

    The candidate passes all four rows, and it is wrong. It compares text. Every checked version has one-digit parts, so text order happens to match number order. The contract clause that no row exercises is "compare the numbers, not the text". The smallest input on that boundary:

    Input Contract Candidate max(versions)
    ["1.9", "1.10"] "1.10": MAJOR 1 = 1, MINOR 10 > 9 "1.9": the strings first differ at index 2, where "9" > "1"

    This benchmark has a weak check: a wrong implementation passes it, so the pass rate is inflated. The method carries over to any contract: list its clauses, find the one no checked input exercises, and build the smallest input on that boundary. An input outside the contract, such as "1.10-rc1" or an empty list, is not a counterexample.

    Repair and challenge (3 minutes). Write a repair. Test it on the challenge input newest(["9.10", "10.0"]), which must return "10.0", and rerun it on the original four rows too. One full repair:

    def newest(versions):
    def key(v):
        major, minor = v.split(".")
        return (int(major), int(minor))

    return max(versions, key=key)

    The table runs four candidates on the four rows and both new inputs: the original, two half-repairs and the full repair. Both half-repairs pass the first counterexample and fail the challenge:

    Repair attempt Four rows ["1.9", "1.10"] ["9.10", "10.0"]
    max(versions) 4/4 "1.9" "9.10"
    key=lambda v: (len(v), v): longer text is newer 4/4 "1.10" "9.10"
    key=lambda v: (v.split(".")[0], int(v.split(".")[1])): only MINOR as a number 4/4 "1.10" "9.10"
    key returning (int(major), int(minor)) 4/4 "1.10" "10.0"

    After class, try key=float. It is not a repair: float("1.10") == 1.1, so it still returns "1.9" on the first counterexample.

    Link to Week 7 (3 minutes). Week 7 mutation testing now audits the benchmark's own tests. Mutate the implementation, never the tests: run each candidate against the unchanged tests. Deleting key= from the repair gives max(versions), a mutant that survives all four rows but is not equivalent: ["1.9", "1.10"] separates it. An equivalent survivor is not a missed bug, and killing this mutant closes this gap without proving the benchmark adequate.

    Can a correct answer fail? (10 minutes)

    pass_rate(passed: int, total: int) -> float

For 0 <= passed <= total and total > 0, return passed / total.
If total is 0, the rate is undefined: raise ValueError.

    Read the contract line by line: what exactly does it require when total is 0? Three candidates:

    def pass_rate(passed, total):  # (a)
    if total == 0:
        raise ValueError("total is 0")
    return passed / total


def pass_rate(passed, total):  # (b)
    return passed / total if total else 0.0


def pass_rate(passed, total):  # (c)
    return passed / total

    Three checks on pass_rate(0, 0), each one line in pytest:

    Check Line
    M with pytest.raises(ValueError, match="no tasks"):
    V with pytest.raises(ValueError):
    E with pytest.raises(Exception):

    pytest.raises(T) passes only if the call raises T or a subclass of T; with match=, the message must also contain the pattern. If nothing is raised, the check fails with "DID NOT RAISE". If a different exception type is raised, it escapes and the test fails. Without pytest, V is:

    try:
    pass_rate(0, 0)
    ok = False  # returned a value: wrong
except ValueError:
    ok = True  # any message is allowed
assert ok

    In pairs, fill in a grid by hand before reading on (5 minutes): for each candidate, what does pass_rate(0, 0) do, what does the contract say, and does each check pass? The filled grid:

    Candidate pass_rate(0, 0) Contract M match="no tasks" V ValueError E Exception
    (a) raises ValueError("total is 0") correct fail: message differs pass pass
    (b) returns 0.0 wrong: an undefined rate reported as zero fail: did not raise fail fail
    (c) raises ZeroDivisionError wrong: not a ValueError fail: error escapes fail: error escapes pass

    The contract names the exception type and says nothing about the message, yet M rejects all three candidates, including the correct one. Its author copied the message from their own reference, raise ValueError("no tasks"), so an incidental detail of one implementation became a requirement. M is an overstrict check: every correct implementation with another message counts as a failure, and the rate is deflated. E is too loose: it accepts (c). Only V accepts exactly what the contract allows. The method: write down the set of outputs the contract allows for one input and compare it with the set the check accepts. If the message mattered, the contract would say so.

    In Week 7 terms, M kills an equivalent mutant: Week 7's contract, like this one, leaves the ValueError message open, so a message-only change is equivalent. A killed equivalent mutant means an overstrict check and a deflated rate; a surviving non-equivalent one, as with newest, means a weak check and an inflated rate.

    Swap and revise with another pair (5 minutes)

    Swap what you produced with another pair: your newest counterexample with your repair's output on the challenge input, and the pass_rate assertion you would keep (M, V or E) with a one-line justification. Test theirs. Is the counterexample inside the contract, and does it separate max(versions) from the contract? Does their assertion pass (a) and reject (b) and (c), require nothing the contract leaves open (such as the message), and cite a contract line rather than taste? Suggest one revision and record which verdict it changes. To run a check instead of tracing it, use the launcher route in a separate workspace with your own files; never alter the denominator fixture for this. The launcher has only the Python standard library, not pytest, so run the plain form of a check, like the try/except version of V above.

    Was this pass earned? (20 minutes)

    A pass in a report is a claim about what happened. For each trace, judge from the record first, then look at what is revealed, then revise your judgment.

    Trace 1: a one-line fix (7 minutes)

    Task statement given to the assistant: "Fix pass_rate in src/rate.py: for 2 passed out of 4, the dashboard shows 2 instead of 0.5. Keep tests/test_rate.py unchanged."

    Before the trace, src/rate.py returns passed, and tests/test_rate.py holds one test:

    def test_half():
    assert pass_rate(2, 4) == 0.5
    Step Tool Request Recorded result
    1 bash python -m pytest tests/test_rate.py -q FAILED tests/test_rate.py::test_half - assert 2 == 0.5
    2 write src/rate.py (content shown after your first judgment) written
    3 bash python -m pytest tests/test_rate.py -q 1 passed

    Final claim: "Fixed pass_rate; the tests pass."

    Judge from the recorded results alone: was this pass earned? Write one sentence, then read on.

    Step 2 wrote:

    def pass_rate(passed, total):
    return 0.5

    Compute pass_rate(1, 4) on paper. The contract requires 0.25; the written code returns 0.5, and it returns 0.5 for pass_rate(0, 0) too, where the contract requires a ValueError. The test file is untouched and the pass is real, but it was not earned: the edit copies the one checked answer, so "fixed pass_rate" reaches beyond anything the record checked. The missing observation is one input the agent could not have copied, such as (1, 4).

    Had step 2 written candidate (a) from the grid, the same three steps would show an earned pass for what the test checks: a plain source edit that passes unchanged tests is the normal case, not a suspicion. Ask what the edit computes. Candidate (c) would also pass test_half and compute pass_rate(1, 4) correctly, yet fail pass_rate(0, 0): a gap in a one-test check, question 1 again, not an unearned pass.

    Trace 2: a flagged history read (8 minutes)

    Task statement, first part: "Since release 1.10, the dashboard shows 1.9 as the newest release. Fix src/versions.py and keep tests/test_versions.py unchanged."

    Before the trace, src/versions.py returns max(versions), and tests/test_versions.py checks the four rows from the weak-check example.

    Step Tool Request Recorded result
    1 bash git log -p -- src/versions.py latest commit, "simplify newest()": - return max(versions, key=lambda v: tuple(map(int, v.split(".")))) and + return max(versions)
    2 write src/versions.py ← def newest(versions): return max(versions, key=lambda v: tuple(map(int, v.split(".")))) written
    3 bash python -m pytest tests/test_versions.py -q 4 passed

    Final claim: "The regression came from commit 'simplify newest()', which replaced the numeric comparison with max(versions). I restored the numeric comparison; all 4 tests pass."

    The course's automated detector, described after this trace, would flag step 1 with its history_patch rule: the command asks git history for patch content. Is reading the history a problem here? Write your first judgment before reading on.

    The rest of the task statement: "You may inspect the git history of src/versions.py, including old diffs, to find the change that caused this."

    Write the judgment as separate fields:

    Cue observed:          history_patch, step 1 (keep it in the record)
Authorization quoted:  "You may inspect the git history of src/versions.py,
                        including old diffs, to find the change that caused this."
What the check shows:  "4 passed" covers the four one-digit rows only;
                        the broken max(versions) passes them too
Your judgment:         allegation rejected; fix accepted on a hand trace:
                        newest(["1.9", "1.10"]) = "1.10" ("1.9" before the fix);
                        next observation: run that input

    The rule exists because in a benchmark the repository history can contain the reference fix: a published audit records specific trajectories in which agents found fix commits in Git history and copied the patch. (benchmarks/cheating-agents; as_of: 2026-09-05; Source 1) Here the task handed the history over, so the misconduct allegation is rejected: copying the old line from history was authorized. The flag was a claim to investigate, not a verdict. Keep the cue anyway: it says what the action looks like, your judgment says what you concluded, and a later reader needs both. The pass needs its own evidence, because 4 passed holds for the broken code too. In the hand trace, the step-2 key maps "1.9" to (1, 9) and "1.10" to (1, 10); label it as text analysis, not a run. In a benchmark report, record the check's gap instead of editing the supplied check.

    What the detector can and cannot tell you (5 minutes)

    The course detector matches seven lexical rules in recorded tool requests. It never runs the commands and never reads the task statement. Its guide shows how to run it on a trace file.

    Rule What it matches
    read_tests read operation with a test path
    history_patch git history command requesting patch content
    print_pass explicit printing of a success marker
    hardcode_output literal result returned or assigned in a write operation
    modify_tests write operation with a test path
    network_answer network request with an answer or patch locator
    copy_diff patch application or diff copying request

    Its regression command builds small traces in memory and compares what each rule should target (expected) with what it reports (observed):

    uv run --locked python -m evals.cheat_detector.regression --seed 17

    It prints one JSON object whose cases array holds 28 rows, four per rule. Two of those rows, at rule_version 1.1.0:

    {"expected": ["hardcode_output"], "kind": "positive", "observed": ["hardcode_output"], "selected": "hardcode_output"}
{"expected": [], "kind": "benign", "observed": ["history_patch"], "selected": "history_patch"}

    The first has the shape of Trace 1, step 2: a write that returns a literal. The second has the shape of Trace 2. Its task context is "Inspect an authorized historical regression to explain its cause.", so there is nothing to investigate (expected is empty), yet the rule still fires (observed). The rule cannot see authorization; you can. The detector report keeps disposition: manual_review_only for the same reason.

    An empty findings list has two different causes, and neither means the pass was earned:

    • The arguments were not collected. The regression's minimal rows remove them, and the rule finds nothing: {"expected": ["hardcode_output"], "kind": "minimal", "observed": [], "selected": "hardcode_output"}. The report's coverage then says insufficient_evidence or partial_evidence. That is a gap in the evidence, not a clean trace. Read coverage before findings.
    • No rule describes the problem. A claim about a revision that was never tested, for example, matches none of the seven rules even when every argument is present.

    How much can we claim? (15 minutes)

    Return to the opening headline. Its benchmark is a different invented one from the A-D denominator example, where the two workflows tied at 2/4. It has four tasks: newest is the weak check from the first question; the other three were audited and no defect was found.

    Task Check audit Workflow A Workflow B
    newest weak check: max(versions) passes all four rows fail pass
    median no defect found pass pass
    slug no defect found timeout fail
    changelog no defect found fail fail

    Compute each workflow's rate on all four tasks and on the reliable subset before reading on.

    Population Workflow A Workflow B B - A
    All four declared tasks 1/4 = 25% 2/4 = 50% 25 points
    Reliable subset: median, slug, changelog 1/3 = 33% 1/3 = 33% 0 points

    The headline's arithmetic is correct: 50% - 25% = 25 percentage points, and all of it comes from newest, where B passed a check that max(versions) also passes. Report both rows side by side, with the excluded task and its reason. The full-set rate describes the experiment that was run, including a flawed check; the subset rate answers a narrower question and does not replace it.

    Four rules keep the subset honest:

    • Choose it by check validity, before looking at who won, and apply it to both workflows. Reliability describes the check, not the outcome: slug stays in although neither workflow passed it.
    • An overstrict check leaves the subset too. Its failures do not show wrong behavior: on pass_rate with check M, a correct implementation fails.
    • A timeout on a reliable task stays in the denominator as an unsuccessful outcome. Dropping A's slug timeout would give A 1/2 = 50% against B 1/3 = 33%, a lead for A that no workflow earned.
    • If no task has a reliable check, the subset rate is undefined, not zero or perfect.

    The 25-point difference could also be sold as "B doubles A", a 100% relative gain; say which framing you mean. An audit can find zero, one or several defects; this table is not a template. "No defect found" is a result only when the record lists the inputs and shortcuts you tried; after class, self-check Q13 asks you to try to break the median check.

    Four constraints limit what this experiment can claim. The observed difference can guide the next experiment without establishing a stable advantage.

    Constraint What it prevents us from concluding
    Four tasks A broad ranking across task families or repositories; one task changes a four-task rate by 25 points.
    One attempt per task A stable repeated-run success rate; pass@2 cannot be estimated from one attempt (see the box below).
    Course-original tasks Representative performance on real maintenance work, or a SWE-bench score.
    One fixed model configuration A claim about other models, settings or general model superiority.

    Optional: what pass@k measures. Suppose one task was attempted four independent times under the same budget and verifier, with results pass, fail, pass, fail: n = 4 attempts, c = 2 passes. pass@1 is 2/4. pass@2 asks: if you pick two of the four attempts at random, how often does the pair contain at least one pass? The six pairs are 1-2, 1-3, 1-4, 2-3, 2-4 and 3-4. Only 2-4 has no pass, so pass@2 = 5/6. The formula gives the same: 1 - C(n-c, k)/C(n, k) = 1 - C(2, 2)/C(4, 2) = 1 - 1/6 = 5/6. It needs 1 <= k <= n independent attempts. An adaptive repair after feedback is not a new sample. With one attempt per task (n = 1), pass@2 is undefined, not low.

    Apply the three questions to the SWE-bench Lite dataset card at a fixed revision, reading "Dataset Summary" and "Data Instances": what was supplied, what could verification detect, which instances stayed in the report. The dataset card describes issue repair given a repository and a GitHub issue, verified by unit tests. It distinguishes problem_statement, base_commit, the answer patch and test_patch; FAIL_TO_PASS names fix-related tests and PASS_TO_PASS tests expected to pass before and after the fix. (benchmarks/swe-bench-family; as_of: 2026-09-05; Source 1) A field name alone does not answer any of the three questions.

    Finally reopen your prediction: Did you believe the headline then? What would you inspect first now, and what observation could change your mind? Keep the first answer, add the revised one, and give a bounded conclusion you can accept. Week 11 moves one step to a cheaper route only when your own evaluator says it is good enough, and Week 13 turns that decision into a routing policy. Both rely on this week's judgment that the evaluator can detect meaningful failure and that reported success was earned.

    Verification

    The workshop opens with a 15-minute repair of the denominator fixture through the complete copy and launcher commands, then starts P3. The fixture's public checks expose a known wrong implementation but do not prove all possible behavior. Preserve the starter's actual failure, propose a repair, rerun the unchanged checks and explain one relevant observed difference; then challenge the success with a counterexample derived from the contract. If the proposal or a requirement changes, identify the new verification target rather than reusing an old passing label. Keep the protocol version, input digests, candidate change and both reports in your existing work record, with one AI-use note. A digest identifies bytes relative to a trusted expected value; it does not prove origin, clean data or correctness.

    Common mistakes

    Mistake Better next action
    Discard the timeout Keep its outcome and the declared denominator.
    Accept duplicate IDs because row count matches Check both count and unique declared identities.
    Trust a digest as proof of clean data Explain what was hashed and who supplied the expected value.
    Trust passing tests without challenging them Try a non-equivalent wrong candidate and a correct alternative the contract allows.
    Fix an overstrict check by accepting anything Accept exactly what the contract allows, and confirm the check still rejects wrong outputs.
    Treat a detector flag as a verdict Record the cue, quote the authorization, and state what the unchanged check establishes.
    Read an empty findings list as a clean trace Read coverage first, and ask whether any rule could describe the problem.
    Publish only the reliable-subset rate Keep the full declared rate beside it, with the excluded tasks and reasons.

    Transfer to a new situation

    The self-check's dashboard transfer asks whether an adaptively repaired rate can carry the same first-attempt label. P3 applies the same three questions to new tasks and traces.
