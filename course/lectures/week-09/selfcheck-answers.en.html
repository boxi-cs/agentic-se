    Week 9 self-check answer guidance

    The examples below state the result and its limit; keep your own evidence beside each claim.

    Q1a–Q1b: First attempt

    Q1a. Two of four attempts pass, so the rate is 2/4 = 50%. Q1b. The timeout remains in the four-task denominator as an unsuccessful or incomplete outcome.

    Q2a–Q2b: Comparison

    Q2a. The extra repair opportunity changes the protocol, so the score cannot isolate model choice. Q2b. Everything except the model: task IDs, verifier, starting state, attempts, call budget and the repair or feedback policy. Then the model is the one changed factor.

    Q3a–Q3c: Hashes

    Q3a. The two files you run have the same bytes as the values recorded in snapshot.json; exercise.py stops with changed_snapshot otherwise. That is only as trustworthy as whoever supplied the recorded values, and it says nothing about your candidate, whose revision you record separately. Q3b. Matching bytes do not show where the records came from or whether a model saw these tasks or their answers before. Q3c. A hash does not show who may use the data or on what terms; that needs its own record.

    Q4a–Q4b: Pair counting

    Q4a. Two of the three unordered pairs contain the correct outcome. Q4b. Adaptive retries change later candidates and opportunities, so the fixed-pair count is not a future guarantee.

    Q5a–Q5b: Completion

    Q5a. A completed verifier observation on the current artifact supports success. Q5b. Missing usage remains unknown or incomplete; it must not be invented.

    Q6a–Q6b: Fixture scope

    Q6a. The reporting fixture is a small synthetic set, while the required P3 pool has its declared frozen tasks, records and evidence route. Q6b. It is not an external benchmark with an external protocol or population claim.

    Q7a–Q7d: Leap years

    Q7a. Yes. 2024 is divisible by 4, and 2023 and 2021 are not. No checked year is a century year, so the century exception is never exercised. Q7b. 1900 (or 2100). Q7c. The contract requires False, because 1900 is divisible by 100 but not by 400; year % 4 == 0 returns True. Q7d. It inflates the rate: a wrong implementation counts as a pass. Adding the row 1900 -> False closes this gap, not every gap: the half-repair year % 4 == 0 and year % 100 != 0 passes 1900 but returns False for 2000, where the contract requires True.

    Q8a–Q8d: Exact output

    Q8a. Yes. 10:30 at +01:00 is 09:30 UTC, and the contract allows +00:00 as the UTC marker. Q8b. No. The check pins one of the two allowed spellings, so it is overstrict and deflates the pass rate. Q8c. One assertion that matches the contract for this input:

    assert to_utc("2026-09-14T10:30:00+01:00") in {
    "2026-09-14T09:30:00Z",
    "2026-09-14T09:30:00+00:00",
}

    It still rejects "2026-09-14T11:30:00Z" (offset applied in the wrong direction), "2026-09-14T10:30:00+01:00" (not converted) and "2026-09-14T09:30:00" (no marker). Q8d. It would accept "2026-09-14T10:30:00+01:00", the same instant but not written in UTC, and reject "2026-09-14T11:30:00Z", a different instant. Comparing instants is too loose; a check should accept exactly the set of outputs the contract allows.

    Q9a–Q9c: Test observation

    Q9a. A run of the unchanged tests on the revision written at step 2. The last test run, step 1, failed, so "all tests pass" is unsupported. Q9b. print_pass: explicit printing of a success marker. Q9c. No. An empty findings list means no rule matched, not that a check passed; the test run would still be missing.

    Q10a–Q10c: Shared patch

    Q10a. One way to write the fields:

    Cue observed:          copy_diff, step 1 (keep it in the record)
Authorization quoted:  "You may apply it."
What the check shows:  the three tests now in tests/test_invoice.py pass on the
                       revision after the patch; the record does not show
                       whether the patch touched that file
Your judgment:         copying allegation rejected; the claim holds for what
                       those tests check only once the test file is shown
                       unchanged

    Q10b. The revision after the patch, with no later edit, passes the three tests now in tests/test_invoice.py. It does not show that this is the original test file: applying a patch can change any file the patch names, and the patch content is not in the record. Q10c. A list of the files the patch touches, such as the output of git apply --stat shared.patch, or a diff of tests/test_invoice.py against the starting revision.

    Q11a–Q11e: Reliable subset

    Q11a. A: 2/5 = 40%. B: 3/5 = 60%. B leads by 20 points. Q11b. The reliable subset is tasks 1, 3 and 4. A: 2/3 = 67%. B: 1/3 = 33%. The ranking reverses, because B's lead came from tasks 2 and 5, where B passed checks that a wrong shortcut also passes. On three tasks one task moves a rate by 33 points, so report both rows, not a ranking. Q11c. Yes. Reliability describes the check, not the outcome. Q11d. A would show 2/2 = 100%, widening its lead with an outcome that was observed as unsuccessful. A timeout on a reliable task stays in the denominator. Q11e. It is undefined, not zero or perfect.

    Q12a–Q12b: Limits

    Q12a. The experiment supports a bounded report for four synthetic tasks, one attempt and one fixed configuration. Q12b. It does not establish repeatability, external benchmark performance or general model superiority.

    Q13a–Q13c: Median

    Q13a. Each obvious shortcut fails a row. The upper middle, sorted(xs)[len(xs) // 2], returns 3 on [10, 1, 3, 2]. The mean, sum(xs) / len(xs), returns 4.0 on [9, 1, 2]. Skipping the sort, xs[len(xs) // 2], returns 1 on [9, 1, 2]. Others are caught too: the lower middle returns 2 on [10, 1, 3, 2], and removing duplicates with set returns 2.5 on [4, 4, 1]. Q13b. "None found; shortcuts tried: upper middle, mean, no sort", with the row that caught each. The record covers only the shortcuts and inputs it lists. Q13c. No. The contract says xs is non-empty, so median([]) is outside it.

    Spaced retrieval and transfer

    Retrieval 1. Require an allowed positive operation to succeed; denial of every attack is not enough. Retrieval 2. Reproduce the runtime behavior and retain a regression that failed before the repair.

    Dashboard transfer. No. An adaptive repair changes the opportunity, so keep the first-attempt outcome and report repaired success separately with its added time and calls. The discriminating check is the same tasks run once with no repair.
