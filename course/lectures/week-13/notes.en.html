    Week 13: Respond to findings and improve usability

    Learning objectives

    By the end of this session you can:

    • separate a raw observation of a user task from a hypothesis and a bounded interface change;
    • verify an agent's proposed interface change with one executable task check, and show when a plausible-looking change did not help;
    • turn each Week 12 audit disposition into an M4 response: repair, defer, no change or investigate; and
    • say what tool portals, model gateways, cost per accepted change and routing add when a whole organization uses agents, and which check would reveal each one failing (LO3, LO5, LO9).

    This packet is a 60-minute lecture followed by a 30-minute demo rehearsal. All examples below are course-authored synthetic practice. They are not M3, M4 or oral-defense instances, and a rehearsal record is never evidence of a real user test.

    Route and timebox

    Minutes Purpose Student output
    0-8 Name the interface, task and raw observation One observation with no inferred cause
    8-16 Separate a hypothesis and request a bounded change One falsifiable hypothesis and a change request
    16-32 Verify two agent proposals with one task check A prediction and the check's result for each page
    32-46 Carry the Week 12 audit into M4 One response per finding, with its evidence
    46-54 Agents across an organization For each piece, the problem it solves and the check that would reveal it failing
    54-60 Accept the iteration within its evidence A decision tied to a revision and a remaining question
    60-68 Rehearse a demo opening Need, scope and evidence in one outline
    68-82 Rehearse the change and verification Generation and verification shown as separate moves
    82-90 Take questions and revise the handoff One answer that names an input, expected effect and limit

    Minimal example

    Interface, task and raw observation

    Course-authored interface: visible controls are Overview | Options | Refresh. Inside Options, State offers All, Failed and Running. The page shows the two most recent builds. The synthetic task is "Find the most recent failed build in pipeline Alpha." The page is current.html in the fixture. A supplied record says:

    The user opens Overview, then returns.
The user selects Refresh twice.
The user asks where failed builds are shown.
The task is not completed before the rehearsal ends.

    Write an observation, a hypothesis and a candidate change before reading on. The record contains no real participant, timestamp or population-level finding. The query returns the correct failed records, so behavior correctness and locating the control are different questions.

    A hypothesis becomes a bounded change

    "Options may not communicate status filtering" is an interpretation. Exposing Status: All is one plausible change to test, not a proven solution. Request that small interface patch while retaining selection, order, permission and keyboard operation. An assistant may propose code within the assignment's rules; you own the discovery records and the interpretation of evidence.

    Unchanged query tests remain relevant to the query. A different control now supplies the filter value, so check that the request still carries the field name and value the query reads, then row order, focus, accessible label and keyboard selection. Repeat the neutral task on the new revision under the actual consent/equivalence arrangement. The old session cannot show that the new label is understandable. Retain minimal de-identified observations rather than names, raw media or unrelated personal details.

    Keep an evidence ledger

    Write the three layers in separate fields before asking an assistant for a patch:

    Layer Example from this packet What would make it stronger
    Observation The user opened Overview, returned and asked where failed builds were shown. The same action is recorded on the affected revision and task.
    Hypothesis The word Options does not reveal that status filtering is inside it. A neutral task can distinguish locating the control from query correctness.
    Change Expose Status: All while keeping the existing filter and ordering. A diff and an explicit acceptance check show the intended scope.

    The table is a reasoning aid, not a claim about a population. If the observation and hypothesis are written in one sentence, split them before implementation. If the change is larger than the hypothesis, narrow it or record why a product owner must decide.

    Generate, then verify

    Generation is the request for a bounded patch. The fixture records this request:

    Add a visible Status: All control to the existing build page. Preserve the current query contract, result order, permission check and keyboard operation.

    agent-replay.json holds two replies. They are a course-authored replay that stands in for an agent; no model wrote them. Both replies say that a labelled, keyboard-operable Status control now puts failed builds one step away. Proposal A adds a new select and leaves Options unchanged. Proposal B moves the existing select out of Options. Compare each page with current.html, then predict: will the task complete on each page?

    Verification is one task check. check_task.py tries the task the way a keyboard user would, with one narrow strategy. It presses Tab from the top, opens a menu or chooses an option only when its text shares a word with the task, follows no links, and then presses the first submit button it reached. The unchanged query answers whatever the form sends. The task is completed when the first row shown is #121, the most recent failed build in pipeline Alpha, and every control reached has an accessible name. The check reads HTML as text and never runs it, so the course file runs on the host with the locked course tools:

    uv run --project infra/hosted --locked python lectures/week-13/fixture/check_task.py lectures/week-13/fixture/current.html
uv run --project infra/hosted --locked python lectures/week-13/fixture/check_task.py lectures/week-13/fixture/proposal-a.html
uv run --project infra/hosted --locked python lectures/week-13/fixture/check_task.py lectures/week-13/fixture/proposal-b.html

    The current page and proposal A exit 1; proposal B exits 0. Proposal A prints:

    page: proposal-a.html
task: Find the most recent failed build in pipeline Alpha.
unchanged query check: pass; query(pipeline=alpha, status=failed) returns #121, #119
keyboard walk from the top of the page:
  1. link "Overview": not followed; the strategy does not follow links
  2. select "Status": chose "Failed"
  3. disclosure "Options" (closed): not opened; no task word
  4. button "Refresh": submit button
not reached: select "State" inside closed disclosure "Options"
reached controls without an accessible name: none
request sent: pipeline=alpha&state=failed&status=all
fields the dashboard ignores: state
fields sent more than once: none
rows shown: #123 running, #122 passed
expected first row: #121 failed
result: NOT COMPLETED - the first row shown is #123 running, not #121 failed

    Proposal A is the change that looks right and does not help. Its diff is small, its control is labelled and reached by keyboard, and the unchanged query check passes. The selection never reaches the query: the new select sends state, the dashboard reads status, and the old State select inside Options still sends all. That runnable observation refutes the reply's claim that failed builds are one step away. Proposal B sends status=failed, shows #121 first and completes the task. If a page sends the same field twice, the dashboard reads the first value, and the check lists the field under fields sent more than once.

    Each check answers a different question. The unchanged query check shows that the query still returns #121 and #119. The request line shows what the page actually sends. The keyboard walk shows that a named control is reached without opening a menu. None of them shows that a person can find the control without a hint; only a new authorized task observation on the accepted revision can show that. The check matches words literally, so a person may succeed where it fails, or fail where it succeeds. A green task check cannot certify a label, and a successful task observation cannot certify an unchanged permission boundary.

    Carry the check to your own page

    check_task.py reads only the fixture's pages and asks only the fixture's dashboard. It cannot read your ci-dashboard templates, whose options come from template loops, or the view that answers them. For the page you change in M4, cross-check the same three things as text. git grep reads tracked files and runs nothing, so these commands run on the host. Replace PROJECT_REPO with your repository and TEMPLATE with the page's template, for example legacy_app/templates/ci/builds.html:

    git -C PROJECT_REPO grep -n -E 'name="' -- TEMPLATE
git -C PROJECT_REPO grep -n -E 'request\.(args|form)\.get\(' -- '*.py'
git -C PROJECT_REPO grep -n -E '<label for=|<details|<summary| id="' -- TEMPLATE

    Then write one line for each comparison:

    1. Form names against view reads. Every field the form sends is a name the view reads, and every name the view reads comes from a control on the page or has a stated default. A name on only one side is the proposal A defect. A read through a helper, such as request.args.get(name, ...), needs the call that passes the name.
    2. Label pairs. Every <label for="..."> matches the id of exactly one control, and every control you changed has a label.
    3. Reach. The control you changed is not inside a <details> that starts closed, unless its <summary> names what is inside.

    If the template builds names or ids in a macro, or you cannot tell which view answers the form, use the manual route instead: write the page's Tab order from the template, mark each closed disclosure, write the request the form would send after a user chooses the task's option, and find each of its field names in the view that answers the form. Either route is text evidence about the revision you read. It is not a task run and not a participant session. To observe the rows the view returns, write a test that sends that request through your framework's test client and run it through the launcher like your other project tests.

    Carry the Week 12 audit into M4

    In Week 12 you marked each recorded finding confirmed, refuted or cannot tell (undetermined in the record) and added one check of your own: either a new defect or a scope check that observed no defect. M4 turns each of those results into a response. The findings came from a model. Where a finding came from is no reason to accept or dismiss it; the Week 12 evidence decides.

    Week 12 result M4 response What the response must show
    confirmed repair, or defer with an owner Repair: a test that fails on the frozen snapshot and passes after the fix, and the other cases of the rule rerun. Defer: who owns it, why it waits and what reopens it.
    refuted no change The refuting command and its output, kept with the snapshot label
    cannot tell (undetermined) investigate The missing observation, named, and the next check that would supply it
    Own scope check, no defect observed no change The command, the checked range and the remaining boundary, and what would reopen the question

    Apply the table to your own F1–F5 results from the Week 12 drill: one response per record, one per part where you split a record, and one for your own check. Your disposition chooses the response; this step does not reopen it. If writing a response shows that your evidence does not support the disposition, go back to the Week 12 check and change the input, not the response.

    A repair is written from the frozen requirement, not from the finding's wording. Requirement R1 of the Week 12 fixture reads:

    R1 access: a viewer or an owner can read a public report; no role reads a private report body.

    For a record you confirmed against R1, test the case the record is about before you touch the code. In a copy of the Week 12 fixture, test_private_report.py can be:

    from audit_packet import run_check

observed = run_check("private-report-view", {"role": "viewer", "private": True})
assert observed["status"] == "deny" and observed["body_visible"] is False, observed

    Run it through the launcher on the frozen snapshot first; the workshop's execution route gives the full commands. A confirmed defect makes the assertion fail there, and that failing output is your evidence before. If the test passes on the frozen snapshot, it does not reach the defect or the disposition needs another look: settle that before you change any code. Then fix the function from the rule in R1, not from the test alone, run the same test again and keep both outputs, each with its revision. Finally rerun the other three cases of the rule with the same private-report-view check, so that the fix neither blocks a permitted reader nor lets anyone else through:

    Arguments Required observation
    {"private": false, "role": "viewer"} allow
    {"private": false, "role": "owner"} allow
    {"private": true, "role": "owner"} deny

    A fix that only makes the one assertion pass can still break a case it does not cover. A test that has only ever passed cannot show that it would catch the defect.

    Keep one response record per finding:

    Finding ID and Week 12 result (disposition, or no defect observed)
M4 response: repair | defer | no change | investigate
Evidence before: frozen revision, command and output
Evidence after (repair): repair revision, the same test and its output
Owner and reopening trigger (defer), missing observation and next check (investigate),
  or checked range, boundary and reopening change (scope check)
Remaining question

    A label such as "fixed" or "won't fix" alone does not explain the engineering judgment. Do not turn a cannot-tell item into "no change" because nothing has failed yet, and do not change code for a refuted finding to make the record look busier. Your own M3 record follows the same mapping, including your own check: a new defect is confirmed and repaired or deferred, and a scope check keeps its range and boundary with no change. The user-test iteration above joins them in one M4 record.

    If you have an approved route, you may dispatch the repair of one confirmed finding as a background task: write the issue as in Week 6, let the agent return a change, and review it through the explanation gate. A plain-text issue and a hand-made change earn the same credit.

    Agents across an organization: portals, gateways, cost and routing

    Week 11 described one gateway you can read in full: the launcher's host broker keeps the key outside the work, fixes the destination, caps each run and keeps a minimal record (the Week 11 gateway jobs). It also compared a cheaper route against your frozen evaluator cases before trusting it. When a whole organization adopts agents, those jobs move into shared services. Four pieces recur. Each solves a real problem and each concentrates authority, so each needs a check that would reveal it failing. This course runs none of them as a shared service; you are asked to recognize them and to say what would test them.

    Tool portal. One service lists which tools exist, who may call each and with which arguments, and it records every grant. The Week 3 hook checked one tool call before its effect. The launcher's tool session is the course's one-person version: it knows four tools (read, write, verify and bash) with fixed argument names, it accepts only the exact call that the model's reply proposed, in order, within a per-run limit, and the program in the sandbox cannot add a tool or change a call. A portal applies that idea to everyone at once, so one review or revocation reaches every agent, and so does one mistaken grant. Tools that an agent discovers through MCP do not grant themselves permission. In one public demonstration, an agent's single GitHub MCP connection could reach both public and private repositories; injected text in a public issue led the agent to write private information into a public pull request, and the disclosers recommend limiting repository access (incidents/github-mcp; as_of: 2026-09-05; Source 1). Checking each call against the grant is therefore not enough: when the grant itself reaches more than the task needs, every call passes the check. Compare what each grant can reach with what the task needs as well. Treat each grant like code: it has an owner, a reason and a test showing that a call outside the grant is denied and leaves no effect.

    Model gateway. A shared gateway holds what individual developers should not: keys, budgets, rate limits and request logs. In LiteLLM, for example, virtual keys control model access and track spending, key settings can bound budgets, budget periods and request and token rates, and one logging setting keeps message content away from logging providers while request metadata is still tracked (tools/litellm; as_of: 2026-09-05; Source 1; Source 2). Those are the Week 11 broker's jobs at organization scale. Check them the same way: replay the policy over the gateway's own records, so that a request over a cap or on an unlisted route shows up as refused before it was sent, and a log on the sandbox side holds neither the key nor prompt text.

    Cost per accepted change. A trace total such as course-llm cost measures one run. At organization scale the useful number is what an accepted change cost: every run that led to it, including failed and retried attempts, plus the time people spent reviewing it. Runs spent on changes that were rejected count too, because the organization paid for them. Divide the total of all runs by the number of accepted changes, and report review minutes beside it in the same way rather than converting them into a price. Cost per token rewards cheap output that nobody can merge.

    Routing. A routing policy sends each task to the cheapest route that passes the evaluator and escalates when a check fails. Week 11 made that decision once, for one step of your M2 feature: a cheaper route is good enough only if it passes every frozen case that the current route passes. A policy makes the decision for many tasks at once, and a rule such as "passes 90% of the cases" can hide the one case a route loses. The frozen evaluator cases must also be rerun whenever a route or a model changes; a model's name does not guarantee unchanged behavior. Even a fresh, complete pass says nothing about inputs that are not among the frozen cases.

    The organization practice checks all four pieces on replayed, course-authored records: a portal's grants against one agent session, a gateway policy against six runs, the cost of three accepted changes and three route choices.

    Rolling model access out to a whole organization brings a gateway's failure modes with it. For each risk, name the check that would detect it:

    Risk Check that would reveal it
    Keys copied into repositories and CI instead of held by the gateway Secret scanning and key rotation; the gateway is the only holder
    Groups bypass the gateway with personal tools, so caps and logs miss that work Compare model use you can see with the work being delivered
    Logs quietly become a store of prompts holding code or customer data Minimal records by default, like the course trace
    One cap for everyone either blocks real tasks or protects nothing Set caps per task from measured runs; every refusal says what to do next
    A gateway or provider outage stops everyone at once A tested fallback, such as replay or a no-model path
    Adoption is judged by usage rather than results Evaluator results and incident records, not token counts

    Because each piece concentrates authority, apply the Week 8 boundary tests before trusting it: a denied call stays denied through every route, and permitted work still succeeds.

    Accept the iteration within its evidence

    If proposal B's page passes the task check, the unchanged query check and the affected keyboard checks, and an authorized new session completes the task without a navigation hint, accept the iteration for that checked scope. Record the revision, the inputs and the observed results. Do not claim that all users will now succeed.

    Run each scheduled user test

    The three user tests scheduled across Weeks 11-13 use one checklist. Prepare it before each session and fill it in yourself during the session.

    Before the session:

    • Consent route. Confirm the consent or approved equivalent route you set up under the Week 4 participation rules. The person may stop at any time; if they withdraw, follow the same rules for their material.
    • Neutral task. Write the task as a goal, as in Week 11, and give it exactly as written, aloud or on paper. It names no control and does not ask whether anything is easy.
    • Revision. Note the commit the person will use. A session on another revision is evidence about that revision only.

    During the session:

    • Actions and words. Record what the person did and said, in order. Put no cause on this line; the hypothesis goes on its own line afterwards.
    • Hint rule. Give no navigation hint. You may repeat the task or ask "What would you try next?" If the person cannot go on without a hint, give the smallest one, record its exact words and when you gave it, and record the task as completed with a hint.

    Record these fields for each session:

    Session: S<n> (no name), date, revision
Consent route: the Week 4 arrangement it uses
Task, as given
Actions and words, in order
Hints: none, or the exact words and when
Task result: completed | completed with a hint | not completed
Hypothesis, separate from the observation
Next check or change

    Keep names, raw media and unrelated details out of the record. Session notes never enter a model prompt, even after you remove names.

    Demo rehearsal: a short walk-through of evidence

    The expo demonstration is a communication exercise, not a second test or a substitute for the individual defense. Rehearse with the Week 13 fixture as the course-authored preview, or with your own approved, de-identified work; do not paste participant identities, raw recordings, private code or model transcripts into what you show.

    Oral defense appointments start this week. If yours falls in Week 13, work through the first 32 minutes of the Week 14 defense rehearsal before it, with a partner or on your own with the public practice packet.

    A compact demo arc

    Use this order and give each move a visible artifact:

    1. Need (one minute): state the user task and the agreed requirement. Name the evidence source without claiming more than it shows.
    2. Finding (one minute): show one observation and label the hypothesis separately.
    3. Change (two minutes): show the smallest generated change and say what stayed unchanged. If an assistant proposed it, say what you inspected yourself.
    4. Verification (two minutes): run or show the affected behavior, integration and accessibility checks on the same revision. Give the expected result before the output.
    5. Decision (one minute): say repair, defer, no change or investigate, with the requirement and remaining question.
    6. Limit (one minute): state what this evidence supports and what still needs a new test, user observation or product decision.

    Question drill

    The partner asks one changed-condition question: “What would you check if the label changed again?” Answer with the new input, expected effect and decision that would move. If the existing test cannot see the changed condition, name the different check. A good answer can be brief; it must be specific enough for another person to run.

    End the rehearsal by revising one sentence in the response record. Keep the demonstration separate from the three scheduled user tests and from your individual defense evidence.

    Hands-on exercise

    Work through the activity; it adds no separate report.

    1. Observe one rehearsal of the task on a page your partner has not seen. Your partner tries it from the --view output for rehearsal.html while you record only actions and words. If your partner opens a control, read them what is inside it from rehearsal.html, and record the action and their words. Write the observation, a hypothesis and one question.
    2. Predict whether the task check completes on rehearsal.html, run it, and compare its keyboard walk with what your partner did.
    3. With your partner, make one fixture variation: write the output line you expect to change, then run the check on your copy.
    4. Run the repair test on a copy of the Week 12 fixture through the launcher, fix from R1 and rerun the other three cases. Then write one M4 response record for each of your F1–F5 results and for your own check.
    5. Continue your actual M4 work: respond to your own verified M3 findings, carry the check to your own page, and continue the three scheduled user tests with the session checklist, using real de-identified records only under the established arrangements.
    6. After class, check the replayed portal and gateway records in the organization practice; its cost and routing parts are optional.

    Verification

    Run the task check on the page you would accept:

    uv run --project infra/hosted --locked python lectures/week-13/fixture/check_task.py lectures/week-13/fixture/proposal-b.html

    Expected evidence: exit 0, with request sent: pipeline=alpha&status=failed, rows shown: #121 failed, #119 failed and result: COMPLETED - the first row shown is #121 failed. Keep the output with the page it checked.

    Failure case: the same command on proposal-a.html exits 1 with fields the dashboard ignores: state and result: NOT COMPLETED, although its keyboard walk reaches a named Status control and the unchanged query check passes. When a change passes the query check but fails the task check, read the request line first: it shows exactly what the form sent.

    For an M4 repair, the evidence is a test that fails on the frozen revision and passes on the repair revision, with both outputs kept beside their revisions. For your own feature, observe the new interaction under the actual consent or equivalence arrangement and retain the affected revision; a task check on a fixture is not a participant session.

    All execution follows Week 0 setup. The classroom packet is authored practice; actual runs and participants need their own evidence.

    Common mistakes

    Mistake How to detect it Correction
    Writing an interpretation as the observation The observation line names a cause or a feeling, such as "could not recognize the filter" Rewrite it as what was done and said; move the cause to the hypothesis line
    Accepting a UI change because its diff, label and query check look right No task check output exists for that page, or nobody read its request line Run the task check and read request sent and fields the dashboard ignores
    Treating a completed task check as proof that people understand the label The usability claim cites only the script Limit the claim to the scripted strategy; observe a new authorized session on the same revision
    Counting a rehearsal or an old-label session as evidence for the new label The session's revision differs from the accepted one, or the record says rehearsal Record a new authorized session on the accepted revision
    Repairing a confirmed finding without a test that failed first The repair record shows only passing runs Run the new test on the frozen snapshot, keep the failing output, then fix
    Turning a cannot-tell item into "no change" The response names no missing observation Name the missing observation and the next check, and keep the item open
    Changing code for a refuted finding The diff touches the path the refuting command exercised Revert that change and keep the refuting command and output
    Quoting one run's trace total as what a change costs The figure leaves out failed, retried and rejected runs and review time Divide all runs and all review minutes by the accepted changes
