    Week 13 · CI dashboard

    Which observation should change the product?

    Correct records can still be hard to find

    The failed-build query returns the correct records. A user cannot locate the filter in the interface.

    Week 12 checked a reproducible software claim. This week we also inspect the interaction needed to use it.

    The interface and task

    Visible controls: Overview | Options | Refresh. Inside Options: State with choices All, Failed, Running. The page shows the two most recent builds.

    Task: "Find the most recent failed build in pipeline Alpha."

    Course-authored interface. The next record is a rehearsal, not a participant session.

    A raw observation for discussion

    The user opens Overview, then returns.
The user selects Refresh twice.
The user asks where failed builds are shown.
The task is not completed before the rehearsal ends.

    No claim about motivation or all users follows directly from this record.

    Observation, hypothesis, proposed change

    Write one sentence for each:

    • What happened?
    • Why might it have happened?
    • What small interface change would test that explanation?

    Use the visible control labels in your reasoning.

    One plausible hypothesis

    "Options" may not indicate where status filtering lives. A visible Status: All control could make the choice easier to locate.

    This is a hypothesis and a candidate change. An opinion, yours or an agent's, cannot establish that the new wording works.

    Keep an evidence ledger

    Layer Write down
    Observation The action and visible result
    Hypothesis A possible explanation that could be checked
    Change The smallest request that tests it

    Keep the three lines separate before asking for a patch.

    Generate: two recorded replies

    Add a visible Status: All control to the existing build page. Preserve query, order, permission and keyboard behavior.

    Both replies: "a labelled, keyboard-operable Status control; failed builds are one step away."

    Course-authored replay in fixture/agent-replay.json. No model wrote these replies.

    Predict before running

    Proposal A adds a new Status select and leaves Options unchanged. Proposal B moves the existing select out of Options.

    For each page: will "Find the most recent failed build in pipeline Alpha" complete? Which output line would decide it?

    Verify: one task check

    check_task.py tries the task the way a keyboard user would:

    1. Tab from the top; closed disclosures stay closed
    2. Open a menu or choose an option only when its text shares a task word; follow no links
    3. Press the first submit button reached; the unchanged query answers

    Completed: first row #121 failed, and every reached control has a name.

    Run it on all three pages

    uv run --project infra/hosted --locked python \
  lectures/week-13/fixture/check_task.py \
  lectures/week-13/fixture/proposal-a.html

    Run the same command on current.html and proposal-b.html. State your prediction for each exit code before the output appears.

    Proposal A looks right and does not help

      2. select "Status": chose "Failed"
request sent: pipeline=alpha&state=failed&status=all
fields the dashboard ignores: state
result: NOT COMPLETED - the first row shown is #123 running, not #121 failed

    Labelled, reached by keyboard, query check green. The selection never reaches the query.

    Proposal B completes the task

    request sent: pipeline=alpha&status=failed
rows shown: #121 failed, #119 failed
result: COMPLETED - the first row shown is #121 failed

    Exit 0. The same field name keeps the query contract.

    What the task check cannot show

    It follows one literal strategy, not a person. A person may succeed where it fails, or fail where it succeeds.

    Only a new authorized observation on the accepted revision shows whether people find the control without a hint.

    Carry the check to your own page

    check_task.py reads only the fixture. For your own page, cross-check as text:

    1. Form names against the names the view reads
    2. Each <label for> against one control's id
    3. The changed control outside any closed <details>

    The text search commands and a manual route are in the notes. Text evidence is not a task run.

    Behavior and interaction require different checks

    Question Evidence to seek
    Are the correct rows selected? Contract-based query regression
    Does the selection reach the query? Task check: request line and first row
    Can the user locate the filter? Neutral task observation
    Can the control be used by keyboard? Focus, selection and label check

    One result does not automatically answer the other questions.

    What should be rechecked?

    The patch changes only the filter control and label. The query function is unchanged, but a different control now supplies its value.

    Which old evidence can remain useful? Which interaction and integration results must be obtained on the new revision?

    Preserve unaffected evidence; check changed paths

    The query's unit evidence remains relevant to that unchanged function. Check that the request still carries the field and value the query reads, and the row order.

    Repeat the affected keyboard check and observe the changed interaction. An earlier session cannot establish that the new control is understandable.

    Carry the Week 12 audit into M4

    Week 12 result M4 response
    confirmed repair, or defer with an owner
    refuted no change; keep the evidence
    cannot tell (undetermined) investigate; name the missing observation
    own scope check, no defect observed no change; keep the range and boundary

    The finding came from a model. Its source is no reason to accept or dismiss it.

    Your F1–F5 results and your own check

    • Apply the mapping to your own Week 12 result for each record
    • A record you split gets one response per part
    • Your own check: a new defect (confirmed) is repaired or deferred; a scope check (no defect observed) is no change

    Write the M4 response and the evidence each one keeps.

    Confirmed: a test that fails first

    For a record you confirmed against R1: no role reads a private report body.

    from audit_packet import run_check

observed = run_check("private-report-view", {"role": "viewer", "private": True})
assert observed["status"] == "deny" and observed["body_visible"] is False, observed

    Run it on the frozen snapshot first: a confirmed defect makes it fail. Fix from R1, run it again. Then rerun the rule's other cases: viewer and owner on a public report allow, owner on a private report deny.

    Refuted and cannot tell

    Refuted: no code change. Keep the refuting command and its output with the snapshot label.

    Cannot tell (undetermined): investigate. Name the missing observation and the next check that would supply it.

    "No change" is not a response to a question nobody has answered.

    A useful response record

    Finding ID and Week 12 result (disposition, or no defect observed)
M4 response: repair | defer | no change | investigate
Evidence before: frozen revision, command and output
Evidence after (repair): repair revision, same test and output
Owner and trigger (defer), missing observation and next check (investigate),
  or checked range, boundary and reopening change (scope check)
Remaining question

    Mechanism: from audit finding to verified response

    The Week 12 result selects one of four responses; each keeps its own evidence.

    Agents across an organization

    The Week 11 broker's jobs become shared services. Each decides before an effect or a send, and each concentrates authority.

    A tool portal grants tools in one place

    One review or revocation reaches every agent; so does one mistaken grant.

    In one public demonstration, a single GitHub MCP connection reached public and private repositories, and injected issue text led the agent to leak private information. The disclosers recommend limiting repository access (incidents/github-mcp; as_of: 2026-09-05; Source 1).

    Every call can pass a grant that is itself too wide: compare what it reaches with the task. Test each grant: a call outside it is denied and leaves no effect.

    A model gateway at organization scale

    Keys, budgets, rate limits and logs held in one place.

    A gateway product can bound budgets and request and token rates per virtual key. It can keep message content out of the logs it sends (tools/litellm; as_of: 2026-09-05; Source 1; Source 2).

    Check: an over-cap request is refused before sending; a log record holds no prompt text.

    Cost per accepted change

    Count every run behind an accepted change, failed and retried ones included, plus the time people spent reviewing it.

    All runs, rejected changes included, ÷ accepted changes; review minutes beside it.

    Cost per token rewards cheap output that nobody can merge.

    Route by the evaluator

    Send each task to the cheapest route that passes the evaluator; escalate when a check fails.

    Supported only if it loses no case the current route passes; "90% pass" can hide one. Rerun the frozen cases whenever a route or a model changes.

    Rollout risks need checks

    Risk Check that would reveal it
    Keys copied into repositories Secret scanning; the gateway is the only holder
    Logs become a prompt store Minimal records by default
    One outage stops everyone A tested replay or no-model fallback

    The full table is in the notes.

    Practice: check four replayed records

    Part Generated record Your check
    1 Portal Grants and one agent session Which grant reaches beyond the task?
    2 Gateway A policy and six runs Which runs should have been refused or capped? Where is the key?
    3 Cost (optional) Runs and review minutes behind four changes Cost per accepted change vs one trace total
    4 Routing (optional) Route choices and evaluator results Does each cheaper route lose a case?

    Predict by hand first, then run org_check.py through the launcher.

    The three user tests form one iteration

    Use the actual or approved equivalent work scheduled across Weeks 11-13. Each session: consent route, neutral task, actions and words, no navigation hint. Retain the task, observation and revision; the checklist is in the notes.

    Compare what changed; avoid turning three small sessions into an unsupported population-wide claim.

    Workshop: one observed obstacle, one verified change

    Observe a partner on a page they have not seen, make one variation, run the repair test, then write one M4 response record per audit result.

    The synthetic record supports practice, not a completed participant requirement.

    Exit: a supported iteration

    On the current revision, the task check, affected behavior and keyboard checks pass. In the new authorized session, the participant finds the filter and completes the stated task without a navigation hint.

    What can you accept about this iteration? What claim about every user would go beyond the observation?

    Assumed evidence for this decision exercise.

    Demo rehearsal: one short arc

    1. Need and requirement
    2. Finding and separate hypothesis
    3. Small generated change
    4. Expected checks and observed output
    5. Decision: repair, defer, no change or investigate
    6. Evidence limit and next step

    Preview: the Week 13 fixture, or your approved de-identified work.

    Demo rehearsal: generation and verification

    Show the request or diff first. Then name the input and expected effect before showing the check output.

    Unchanged query evidence does not establish a new label. A successful task observation does not establish an unchanged permission boundary.

    Demo questions and handoff

    Partner prompt: “What would you check if the label changed again?”

    Answer with the changed input, expected effect and decision that would move. Revise one sentence in the response record before handing off.

    M4 explains the response, not just the patch

    Connect verified findings and user observations to the changes made. Keep the evidence behind every no-change and every open investigation.
