    Week 2: Build a small coding agent

    Learning objectives

    By the end of this week, you can:

    • LO1: trace an observation, a proposed action, a tool result and a stop decision, and predict how a loop fails when its context or stopping rule is wrong.
    • LO2: define narrow read / write / bash contracts, run a synthetic repair through the approved launcher, and account for its finite calls and verification evidence.
    • LO7: show that a refused call reaches the model as a result and has no effect, and name which limits the launcher enforces that your Python dispatcher cannot.

    These are this week's contributions to the broader course outcomes. The activity and self-check exercise all three. P1 provides individual LO1 evidence. LO2 practice here prepares for your individual work in the repository-context workshop and the portfolio evidence specified by the syllabus. LO7 starts here with execution boundaries; Week 8 continues it with attack and defense, and CP2 and the security segment of the individual defense assess it. A pair's classroom result cannot replace either person's individual assessment.

    Use the approved hosted or replay route in Week 0 setup. Run code only after that page's check shows you can run the practices. Independent assessments remain AI-off.

    Minimal example

    The continuing dashboard case

    An agent is asked to repair the dashboard status formatter. Its trace stops right after writing a file. No check appears.

    assistant  tool_calls: c1 read {"path": "status.py"}
tool c1    (the file text)
assistant  tool_calls: c2 write {"path": "status.py", "content": candidate}
tool c2    "written"
assistant  "done", with no tool calls

    Decision: Which observation is missing before anyone may report verified success?

    The loop stopped with final: the model made no further calls. That ends the conversation; it says nothing about whether the file is right. The write records a side effect. Nothing observed the acceptance checks on that revision. Success needs an allowed verification call and its passing result in the history.

    Specify accepted tools, arguments, allowed paths and the turn budget. Send the model its history, including every actual tool result, and let it choose the next call.

    Acceptance decision: Report verified only when a passing check appears in the history after the last write. Report the stop reason (final or step_limit) separately; a summary must keep the last failed check.

    The public result.txt exercise below isolates the call/result mechanism used when an agent edits dashboard code. Its small file is a teaching fixture, not the dashboard implementation. All examples on this page are course-authored; actual execution evidence comes from your own checks.

    One task, three tool calls

    A model produces text or a structured proposal. An agent controller decides whether to call a tool, records the actual result, sends it back and lets the model choose again. Here, think means selecting a next call from the goal and the observations so far. A short explanation may help a person inspect that choice, but a claimed explanation does not prove what happened inside a model or that the call is correct.

    Our synthetic task is to repair result.txt: it initially contains 5 followed by a newline, and should contain 4 followed by a newline. No private repository, personal data, service or benchmark is involved.

    Turn Model's call Tool message sent back Controller
    1 c1 read {"path": "result.txt"} tool_call_id: c1, 5\n Continue
    2 c2 write {"path": "result.txt", "content": "4\n"} tool_call_id: c2, written Continue: a completed write is not a test
    3 c3 bash {"command": "verify"} tool_call_id: c3, verified Continue
    4 No calls; text "Verified." None Stop with final

    The check result is the tool message under c3, not the model's last sentence. First predict the outcome of writing 5\n instead. The verification subprocess exits nonzero, the c3 result becomes check_failed, and a final reply cannot change it.

    You write the loop; the protocol is P1's

    Open fixture/loop.py as plain text. It supplies the tool contract (tool), the reply check (checked) and the evidence reader (last_check). The loop itself, run(), is yours. In the workshop the instructor builds steps 1-3 as a live demonstration while you type the same three, steps 4-5 you write alone, and the public checks tell you when it meets this contract, which is the message protocol of P1's controller tasks:

    1. Start with one user message holding the task.
    2. Send a copy of the whole history to the model (chat). Check the reply's shape before any tool runs (checked): text content, and a tool_calls list whose items each have an id, a name and an arguments object. A malformed reply, or an ID that an earlier call already used, raises an error: no result could be matched to it.
    3. Append the reply as an assistant message. With no tool calls, stop with final, even if the text is empty.
    4. Otherwise run each call through tool and append one role: "tool" message per call, with the call's own tool_call_id and the actual result as string content. A missing file or a timed-out check becomes a failed: ... result.
    5. When the turn budget (max_steps, four by default) is spent, stop with step_limit.

    Until you write it, run() raises NotImplementedError and the public checks stop with "Write run() in loop.py first". final means the conversation stopped, not that the task is correct. last_check reads the evidence separately: the newest verify result, or not_run when a later write made it stale. Two P1 differences matter: P1 passes a compacted copy of the history through the supplied compact, and its tools come from the supplied runtime. The P1 README remains the exact contract for your own Agent.run.

    The contract has no repeat detector. A reread after a write can be useful; the same read four times only spends the budget. The turn budget bounds both. A general agent may add a state-aware progress check, but it still needs an absolute budget. The launcher separately owns wall time, process, memory, output and model-call limits; the first bound reached ends the run.

    Tool Accepted arguments Result
    read {"path": "result.txt"} The actual file text
    write {"path": "result.txt", "content": ...}, text of at most 32 characters written
    bash {"command": "verify"} Runs a fixed assertion; verified or check_failed

    Any other tool, argument name, path or command, or content that cannot be written as text, gets a short refused: ... result under the call's ID, before any effect, and the model sees it on its next turn. last_check counts only the exact verify call, so a refused bash call never stands in for a check. The name bash does not grant a model an unrestricted shell: the adapter selects the literal verification program and never interpolates model text into a shell command. The 32-character write limit is a course exercise choice. The four-turn default matches the launcher's cap of four model requests per run. Neither is a product limit or a model-token budget.

    This small dispatcher assumes the launcher copied a clean synthetic workspace with no links or concurrent writers. It cannot contain a hostile replacement of its own Python code. The launcher supplies the external isolation boundary. These public assertions are practice feedback, not a trusted hidden grader.

    ReAct and its limits

    The ReAct structure discussed in the course alternates reasoning about a next action, acting through a tool, and observing its result. Our loop makes those transitions inspectable. It does not reproduce a research experiment or claim a benchmark result. A model-driven proposer can choose poorly, invent a tool or repeat a call. Neither the structure nor a fluent explanation guarantees progress, factual accuracy or safe permissions.

    Once your run() passes the public checks, the demo driver puts two proposers behind it:

    • Scripted practice (python demo.py): a course-written function that reads the latest tool result and picks the next call: read, write the candidate, verify, then stop and report the last result. Its candidate is fixed text, so this is practice, not a model.
    • Model route (python demo.py hosted, or replay): each turn sends the tool contract and the whole history as one prompt through the launcher, at most four requests per run. The model therefore receives every observation: the file text, written and the check result. Its JSON reply becomes the next assistant message.

    The model-route adapter numbers the model's calls (t1-1, t2-1, ...), as a provider API assigns call IDs. It removes a leading <think>...</think> block or one json code fence. It does not repair a wrong argument or add a missing call. A reply that is not one JSON object is reported as unusable_reply and the run fails; the check still decides whether result.txt is right.

    Context is a bounded working record

    The window is a budget. Every request carries the history so far: the task, every reply and every tool result. A context window caps how much one request can carry, and each turn sends every earlier byte again. The contract resends the whole history each turn. That fits four turns over a one-line file; it would not fit a repository repair. P1 sends a compacted copy instead and keeps the full history in the returned trajectory.

    What accumulates. The history grows with every call, and three kinds of content take most of the room. Tool output, such as file reads, test logs and search results, is usually the largest part and goes out of date first. Failed attempts stay, with their edits and error output. Repeated reads of the same file add a copy each time. The instructions and tool definitions are sent with every request as well. In the session dissection, find what accounts for most of the growth in request size from the first request to the last.

    How a long history misleads later steps. Overflowing the window is the obvious failure. Three others come first:

    • Stale observations. An early read of a file stays in the history after the agent has changed the file. Nothing marks it out of date, so a later step can act on old text.
    • Contradictions. A failed attempt and the decision that replaced it both remain. The history holds both and does not say which one stands.
    • Buried instructions. A constraint that arrived once, for example in a file the agent read, sits under everything that came after it. Nothing in the loop makes the model give it weight many turns later, and clearing old tool output removes it with the rest.

    What compaction does. Compaction replaces older turns with something smaller before the next request. Clearing replaces old tool results with a short stub, as the recorded session in the dissection does for two earlier file reads. Summarising replaces older turns with written text. A useful summary keeps:

    • the task and its acceptance check;
    • each constraint and decision, with where it came from;
    • what was tried and how it failed, so the next step does not repeat it;
    • open failures: the last failed check and the file version it ran on;
    • the paths of the files involved, and the current state of each one touched;
    • the next step.

    It drops raw tool output, because the agent can read the file or run the check again.

    What compaction can lose. Whatever the summary leaves out is gone for the model, and reading the summary alone will not show you the gap. The usual losses are a constraint that arrived in a tool result, the version a check ran on, a refusal, and an attempt that already failed, which the agent may then try again. If a summary says "test passed" but omits which file revision it tested, that claim cannot justify a later edit. Check a summary like any generated work: confirm each required fact against the transcript, then confirm that the next step still passes the same check. In Week 3 you run that comparison on one long session.

    Compact or restart. Compact when the task continues and the newest raw results still matter. Restart with a fresh context and a written handoff when most of the history is stale or contradicts itself, when one phase of the work has ended, or when the agent keeps failing in the same way. A handoff holds the same items as a summary, written so that a new session can act on it alone. After either one, reread the files the next edit touches before editing.

    P1 supplies compact, so you do not write one. It keeps the task, shortens long tool results and, while the copy is still too large, drops the oldest call/result groups whole; it writes no summary. Design a working record of your own first: the goal, permitted tools, current file state, last verification result and remaining budget, with older observations summarized as claims tied to evidence and unresolved failures kept. Then compare it with what compact keeps, and name one item of your record that the model loses when compact drops a group, such as an early refusal or a failed check. Character limits in this fixture do not measure tokens. Use the shared model contract and the actual broker trace for model limits and observed usage, without copying its parameters into a second configuration.

    Reading a production agent's instructions

    For reading purposes, a production coding agent shares an outline with your run(): a loop that sends the history, a set of tool definitions and instructions to the model, and answers each call under its ID. The outline is where the resemblance ends. Yours resends a four-turn history with no compaction, no progress check and three fixed tools, so it cannot stand in for a production controller's state, history and progress handling. When a vendor or an open-source project publishes its instructions, read them as an engineer reads a configuration file, not as a description of guaranteed behavior. Sort every sentence into one of four bins: a role or goal, a tool contract (name, arguments, when to call it), a stopping or escalation rule, and a request for caution. Then ask of each one: what enforces this? A schema validator, a sandbox and an approval prompt enforce. A sentence that begins "never" only asks. Our controller makes the same split visible in miniature: the shape and argument checks before any effect enforce, while the contract text in the model-route prompt merely proposes.

    To practise on real text, the optional comparison activity puts two open-source coding agents side by side at fixed commits. The Codex CLI base instructions tell the agent, for example, to keep going until the query is resolved and not to git commit unless asked; its update_plan schema limits each step's status to pending, in_progress or completed, while "at most one step in progress" appears only in the description text. (tools/codex-base-instructions; as_of: 2026-10-09; Source 1; Source 2; Source 3) The Qwen Code prompt builder asks the agent to run the project's own checks before reporting a change complete and to say so when a check failed or was not run; its edit tool rejects a relative path and fails when the text to replace matches more than once, while "at least 3 lines of context" is only asked. (tools/qwen-code-system-prompt; as_of: 2026-10-09; Source 1; Source 2; Source 3; Source 4; Source 5; Source 6; Source 7) Sort sentences from both before deciding which ones anything enforces.

    Two habits carry over to P1. First, a tool definition is part of the prompt, so a vague tool description is a vague instruction. Second, long instructions are not evidence of safety: count what is enforced, not what is written.

    Hands-on exercise

    Follow the 60-minute activity, including prediction, the instructor's steps 1-3, verification, feedback and revision. It fits inside Week 2's class and P1 work. The required session dissection is another part of P1; its page estimates about two and a half hours and does not create a second submission. Do its steps 1-4 before the workshop, swap tables with a partner there, and do step 5 once your P1 runs have produced a trajectory. Week 2's published estimate is 12 total hours and P1's combined Weeks 1-2 time box is 11 hours. These are planning and help checkpoints, not measured completion claims, penalties or automatic stops.

    Type steps 1-3 of run() while the instructor builds them on screen, then write steps 4-5 yourself against the contract above. Run the public checks after each step; they are the target, and their names tell you which part of the contract a failure breaks. After step 3, four pass; all fifteen pass once steps 4-5 are right. Then generate the synthetic candidate and verify it. After the workshop, change one stopping decision: set MAX_STEPS in demo.py to 2 and then to 3, predict each run's stop reason and check, run both, explain the observed effect and restore 4. Keep your work product, relevant verification and short explanation together. Add AI use once and reuse the same evidence ID in P1 if relevant. Keep only the loop fragments required to explain a failure or verified stop. Do not export an unrelated conversation. Any required personal reflection is written without AI.

    At the help checkpoint, use the activity's hint ladder, the instructor's steps 1-3 and the check names, or an approved equivalent interaction path. The model route is optional for full marks. P1's own task remains individual: a minimal agent of at most 300 lines, its five tasks, required JSONL trajectory and calibration record. This classroom fixture does not replace those tasks.

    Verification

    Use the exact resolver and launcher sequence in the activity. The workspace contains only fixture/ public files. Every executable example, including the public tests and your loop.py, runs through the same course launcher. It refuses profile drift and reruns its safety suite. Do not mount the private course checkout or teacher answers. The supplied tests run with Python's standard library inside that sandbox.

    Until run() is written, verify_loop.py stops with "Write run() in loop.py first" and the demo prints "error": "write run() in loop.py first", both before any model request. With your run(), the scripted demo should print generation: scripted-practice, stop_reason: final, check: verified and eight messages. In the exported completion.json, the three tool messages answer c1, c2 and c3 with 5\n, written and verified. The exported result.txt must contain exactly 4\n. All fifteen public checks must pass, including: a reply with no tool calls is final; the proposer receives each result under its call's ID; two calls in one reply are answered in the order listed, each under its own ID, even when the first is refused; a wrong candidate ends final with check_failed; a write followed by a final reply leaves the check not_run; a later write makes an earlier check stale; a repeated read runs until step_limit; refused calls are returned to the model with no effect; malformed replies and reused IDs stop before any tool runs; and a missing file and a simulated timeout become results. The timeout test checks controller handling; the course runtime suite tests containment.

    In the budget experiment, MAX_STEPS = 2 ends with stop_reason: step_limit, check: not_run, five messages and a nonzero exit. MAX_STEPS = 3 ends with stop_reason: step_limit, check: verified, seven messages and a zero exit: the check passed, but the budget ended before a final reply. The demo's exit status follows the check, never the stop reason.

    On the model route the launcher's result and trace show one request per turn, up to four. A malformed, oversized or wrong reply is a failure to inspect, not a reason to alter the expected answer or increase resource limits. completion.json is an exercise-local view, not the shared course_llm JSONL schema. Keep the launcher's minimal JSONL separately when a model call is required. Neither scripted practice nor a FAKE broker response is real-model acceptance or proof that you can run the practices.

    After peer feedback, rerun the failing case and the correct case. Explain the changed check result with reference to the call and its actual result. That explanation, plus your own self-check, demonstrates individual understanding.

    Common mistakes

    Mistake Observable symptom Small correction
    Treating a write or a final reply as success final with no passing check after the last write Read the check result from the tool messages before reporting verified
    Answering a call under the wrong ID A result sits under another call's tool_call_id, or a call has no answer Append exactly one tool message per call, with that call's own ID
    Retrying forever Repeated calls until step_limit with no new evidence Keep the absolute turn budget; add a progress check only alongside it
    Trusting an invented tool upload or a model-chosen shell string causes an effect Refuse it before any effect and return the refusal as the result
    Losing constraints during compression Summary forgets a denied path or the tested revision Keep constraints and failure evidence, then reread current state
    Trusting a summary nobody checked After compaction the next step repeats an attempt that already failed Check each required fact against the transcript, then rerun the same check
    Treating a prompt as containment Permission dialogue exists but process has broad access Keep external launcher isolation and test denied effects
    Running on the host to fix setup The Week 0 runtime check has not passed Stop execution and use the approved support/equivalent path
    Equating model text with a passed task Real call succeeded but assertion failed Report generation and verification separately

    Low-resource and accessibility routes retain the same task, verification and evidence. Use the current fallback status when the hosted route is unavailable; replay keeps the same learning requirements and score ceiling. The course team can approve equivalent equipment or interaction arrangements with unchanged learning and attainable marks.

    Transfer to a new situation

    An agent repairing the dashboard status formatter writes status.py, runs the acceptance tests and sees them fail, writes status.py again, and then the turn budget ends. Read afterwards, the new file looks right. What stop reason and check status does the record show, what must a summary of the run keep, and which observation would let you report the repair verified?

    Write the expected behavior and the next check before comparing with a partner.
