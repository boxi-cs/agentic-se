    Week 2 self-check answer guidance

    Use these explanations after your first attempt. Each conclusion is limited to the fixture and observation named in the prompt.

    Q1a–Q1c: Cycle and verification

    Q1a. Success requires a verify call after the write whose tool message returns verified, from a check that observed result.txt == "4\n". Q1b. written records an effect, not the required output. Q1c. final only means the reply had no tool calls; “done” is model text, not a tool observation. Neither is a check result.

    Q2a–Q2c: Stopping

    Q2a. step_limit: the contract has no repeat detector, so the turn budget ends the loop. Q2b. not_run: no verify call ever ran. Q2c. Neither stop reason proves the repair; a requirement check in the history is still needed.

    Q3a–Q3c: Tool boundary

    Q3a. Only bash with {"command": "verify"} runs. ./result.txt names the same file, but the contract accepts only the literal path result.txt: the dispatcher compares the text and does not resolve paths. The write carries an argument name, mode, that the contract does not list, and argument names must match exactly. Q3b. The fixture's tool function decides before any effect. The read and the write each get refused: tool, argument or path outside the contract under their own IDs. The refused write changed nothing, so the file still holds 5\n and the verify call returns check_failed. The model sees all three results on its next turn. Q3c. tool only limits calls that pass through it. It is ordinary Python in the same process as your run(), which you edit and the launcher runs, so code that skips or changes it is not held back by it. The launcher limits files, network, processes and resources for everything in the run, whatever that Python code does.

    Q4a–Q4c: Context and budget

    Q4a. Preserve the goal, allowed operation, artifact and tested revisions, last result, unresolved failures and remaining budget. Q4b. Reread the changed file and rerun the relevant check on the new revision. Q4c. A summary can be stale or wrong because it is not the observation itself.

    Q5a–Q5c: Safety state

    Q5a. Reading, planning and text reasoning may continue. Q5b. Code execution and model calls stop until the Week 0 runtime check passes and an approved model or replay is available. Q5c. The offline check is preparation feedback, not proof that you can run the practices, and it observed yesterday's state. The launcher reruns its safety checks on every run, and today's failed check is the current observation. Execution resumes only after those checks pass again through the Week 0 route.

    Q6a–Q6d: Boundaries

    Q6a. Approval decides whether an operation may proceed. Q6b. Containment limits what a running process can access. Q6c. A stopping rule decides when the controller ends. Q6d. A scripted driver does not prove model choice or feature parity.

    Q7a–Q7b: Call IDs

    Q7a. The model believes the read returned verified and the check returned the file text, so it may report success without having seen a check of the current file. Q7b. The public check test_two_calls_in_one_reply_are_answered_in_order: its replies each hold two calls, and it compares the call IDs, in order, with the answering tool_call_ids and checks each call's own result. A check whose replies hold only one call cannot catch the swap, because a single call has nothing to be swapped with.

    Q8a–Q8c: Asked or enforced

    Q8a. The edit fails and the file is unchanged. The error text, which gives the number of matches, comes back as the tool result, so the model can retry with more context or with replace_all. Q8b. Neither of these two rules stops it: the text matches once, so the single-match rule is satisfied, and nothing checks the three-line request. The single-match rule is enforced by the tool's own code; the three-line request sits only in the description. The tool's code makes other checks that this question does not cover. Whether the one match was the intended place is a question for the next read or test. (tools/qwen-code-system-prompt; as_of: 2026-10-09; Source 1; Source 2; Source 3; Source 4; Source 5; Source 6; Source 7) Q8c. tool refuses ./result.txt, an extra mode argument or any command other than verify, before any effect. The task's "Run the verify check, then report" only asks: nothing makes the model call verify. last_check does not enforce it either, but it makes the missing check visible as not_run.

    Q9a–Q9d: Compaction

    Q9a. The failure survives, but only in the agent's own sentence "the strip-only lookup fails"; the check output itself is cleared. The view.py constraint is lost: it arrived once, inside a tool result, and the agent never restated it. Nothing in the compacted history shows that it is missing, so the next step can edit view.py without any visible contradiction. Q9b. The six items from the notes: (1) the task and its acceptance check; (2) the constraint not to edit view.py, with NOTES.md as its source; (3) the strip-only attempt and how it failed; (4) the open failure: the last check failed on "OK", run on the strip-only status.py; (5) the paths status.py and view.py and their current state: status.py holds the edited version, so the first read is stale, and view.py is as shipped; and (6) the next step. It may drop the raw file contents and the full check output, which the agent can read or run again. Q9c. Check each required fact against the transcript, citing the message it came from, then let the next step run and rerun the same check on its result. The check alone is not enough: a summary can pass one check and still miss a fact a later step needs. Q9d. For example: most of the history is stale or contradicts itself; one phase of the work has finished; or the agent keeps failing in the same way. Reread the files the next edit touches before editing.

    Spaced retrieval

    Retrieval 1. Read the relevant contract through the permitted tool to supply the missing context, record its revision and rerun a requirement check. Retrieval 2. "OK" should map to passed; normalize with raw.strip().lower() and retain both padded and mixed-case regressions.

    Dashboard transfer

    The stop is step_limit. The check status is not_run: the failed test run checked the earlier revision, and the later write made that result stale. A summary must keep that failure and the revision it tested; "looks right" is a reading of the file, not a check. Only the acceptance tests run on the current revision, with a passing result in the history, would let you report the repair verified. That later run adds evidence; it does not change the earlier step_limit stop.
