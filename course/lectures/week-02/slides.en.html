    Build and inspect a small agent

    Week 2 · CI dashboard

    When is a repair actually finished?

    A write without a test

    Last week, we separated a proposal from an observation.

    assistant  c1 read {"path": "status.py"}
tool c1    (file text)
assistant  c2 write {"path": "status.py", "content": candidate}
tool c2    "written"
assistant  "done", no tool calls

    What do we know? What result is still missing?

    The controller owns the stop decision

    A completed write tells us that files changed.

    A verification result tells us what the specified check observed.

    Today you will trace a controller, predict its stopping behavior, and explain one limitation of its implementation.

    A file small enough to trace completely

    The workshop isolates the loop in result.txt.

    Initial bytes:   "5\n"
Required bytes:  "4\n"

    The smaller fixture lets us inspect every call before returning to a dashboard repair. It does not execute the dashboard.

    The tool contract

    Tool Accepted arguments Effect or result
    read {"path": "result.txt"} Read that file
    write path and content, at most 32 characters Replace that file
    bash {"command": "verify"} Run a fixed assertion

    The name bash does not permit an arbitrary shell command.

    Which calls reach a tool?

    {"id": "c1", "name": "bash", "arguments": {"command": "verify"}}
{"id": "c2", "name": "bash", "arguments": {"command": "echo 4 > result.txt"}}
{"id": "c3", "name": "read", "arguments": {"path": "../outside.txt"}}

    Classify each using the contract. Point to the argument that decides it.

    A refusal is also a result

    Only c1 matches an accepted tool and argument.

    reply -> shape check -> tool/argument check
                          |              |
                      permitted     refused: ...
                          |              |
              tool message under the call's own ID

    The model sees the refusal on its next turn. Nothing changed on disk.

    The bounded agent loop

    This map names the hand-offs only. Use it to orient the trace before inspecting the next fixture result.

    One successful path through the fixture

    Turn Model's call Tool message back
    1 c1 read c1: 5\n
    2 c2 write 4\n c2: written
    3 c3 bash verify c3: verified
    4 no calls stop: final

    Every request carries the whole history, so the model sees each result.

    The contract for the run() you write

    1. History starts with one user message: the task.
    2. Each turn: send a copy of the history; check the reply with checked.
    3. Append the reply. No tool calls: stop with final.
    4. Otherwise one tool message per call, under that call's ID.
    5. Turn budget spent: stop with step_limit.

    tool, checked and last_check are supplied. The public checks test your run().

    The same write, a different value

    The proposer reads 5\n, writes 5\n, then calls verify.

    What result comes back under the verify call's ID? What may anyone conclude when the next reply has no calls?

    Keep the required bytes fixed while tracing the changed proposal.

    The assertion supplies the failure

    assert Path("result.txt").read_text() == "4\n"

    The wrong write returns written, but verification returns check_failed.

    The loop still stops with final. The check result, not the stop reason, says the repair failed.

    Two stop reasons, one separate check

    Field Meaning
    final A reply had no tool calls
    step_limit The turn budget ended
    last_check Newest verify result after the last write, or not_run

    A malformed reply or a reused call ID raises an error before any tool runs.

    Is a repeated call always a loop?

    c1 read result.txt
c2 write "4\n"
c3 read result.txt

    The contract has no repeat detector. Is the third call useful? What stops a proposer that reads forever?

    The budget bounds what a heuristic cannot judge

    The reread after a write shows the new state, so it is useful.

    Four identical reads only spend the turn budget; the loop stops with step_limit.

    A progress check can help, but it never replaces an absolute budget.

    A working record for the next action

    Goal: result.txt must equal "4\n"
Latest write: "5\n"
Latest check: check_failed, after that write
Allowed next steps: still subject to tool and turn limits

    Which line would be lost in a summary saying only "file updated"?

    The context window is a budget

    Every request resends the task, every reply and every tool result.

    What piles up Why it matters
    File reads, test logs Largest part; out of date after the next write
    Failed attempts Still visible next to the fix that replaced them
    An instruction read once Buried under every later turn

    A summary replaces the older turns

    The history holds the task, a file that says "do not edit view.py", a strip-only fix, its failed check and two rereads.

    Which lines must a summary keep? Which raw output can it drop?

    Compact, or restart with a handoff

    Keep: the task and check, constraints and where they came from, what failed, open failures, file paths and state, the next step. Drop: raw output the agent can read or run again.

    Restart when the history is mostly stale or one phase has ended. Then check the summary against the transcript, and rerun the check.

    Public code and an external execution boundary

    The dispatcher restricts its own tool calls. Editable code could bypass that dispatcher.

    The course launcher separately contains execution and resources. Use the Week 0 setup page for the supported invocation.

    A production prompt: which rules are enforced?

    Two open-source coding agents publish their instructions and tool definitions.

    Rule Asked, or enforced by what?
    Qwen Code edit: file_path must be absolute ?
    Qwen Code edit: include 3 lines of context ?
    Codex CLI update_plan: status is one of three values ?
    Both: at most one step in progress ?

    Count what is enforced, not what is written

    Rule Enforced by
    Absolute path; a second match fails without replace_all the tool's code, error sent to the model
    3 lines of context nothing visible: description only
    Three status values the schema
    One step in progress description and prompt text only, in the files linked

    Live demonstration: building the loop

    The instructor builds steps 1-3 on screen; you type them too. Steps 4-5 are yours: the failing check names say what is still missing. In P1 you build the whole controller yourself.

    Then trace one correct write and one wrong write through your loop. The learning task is to explain its decisions and limitations.

    Feedback on the working record

    A peer removes the last failed check from your summary.

    Explain which next decision becomes harder to justify. Restore the needed observation in your own words.

    Use the existing P1 record for the code and actual result.

    Exit: correct-looking code, exhausted budget

    The file appears correct, but max_steps ends before verify runs.

    Name the stop reason your run() returns, the check status, and a supported next action. Answer independently.

    A later supported run verifies the current file. What can you now accept, and which earlier stop record stays unchanged?

    P1 and the next repository

    Your P1 Agent.run uses this protocol, with the supplied compact. Your P1 record keeps its code, verification and your own explanation.

    Next week, the controller is no longer the main unknown. You must discover which files give it useful context.
