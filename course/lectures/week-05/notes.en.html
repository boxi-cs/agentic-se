    Week 5: Taking over a legacy repository

    Learning objectives

    Outcome Observable action Practice and self-check
    LO2 Write a repository context file and one hook gate, show the gate failing on the change it exists to stop, and check a role's hand-back against its hand-off. Week 5 practice, questions 8 and 9
    LO4 Map one behavior in an unfamiliar repository, score how ready it is for an agent from observations, and propose a small modernization step with a rollback condition. Code-reading activity, readiness activity, M1 plan, questions 1, 4 and 7
    LO5 Establish characterization tests, reject a behavior-changing refactor, and explain the limits of a complexity measure. Fixture comparison, questions 2 and 3
    LO7 Treat repository text and dependency scripts as untrusted input, constrain execution, and preserve individual tool permissions. Plan safety check, question 5

    Week 5 has a 14-hour published estimate, including class, CP1 preparation, the completed M0 specification, M1 exploration, the start readiness score, the context-file, hook and hand-off practice, your C1 contribution, waiting and revision. The 20-minute reading activity is part of class, not extra homework. This is planning guidance, not measured student timing or a penalty cutoff.

    CP1 supplies individual evidence for LO4 and LO5 only. The execution and dependency-boundary practice is formative LO7 work outside CP1. M1 project work is practice and project evidence; it cannot substitute for your own CP1 diagnosis, repair and explanation.

    Minimal example

    The continuing dashboard case

    A shorter dashboard status mapper replaces conditionals with a lookup table. Existing callers send mixed case and surrounding whitespace.

    LABELS = {"ok": "passed", "pass": "passed", "fail": "failed"}

def status_label(raw):
    return LABELS.get(raw.lower(), "unknown")

    Decision: Which behavior did this refactor remove, and what belongs in this PR?

    The proposed lookup omits strip(). Restore the normalization and rerun characterization cases. Keep a behavior-preserving refactor separate from a new fallback, dependency upgrade or data migration.

    Ask for one structural change with preserved behavior and a rollback condition. Inspect the caller and lockfile before accepting unrelated changes.

    Acceptance decision: Accept the smallest change whose original behavior and requested structure are checked. If a known unsafe behavior is found, specify a fix rather than preserve it as a requirement.

    The worked fixture below makes normalization and caller compatibility inspectable. Use the same investigation steps on one real path in your assigned repository.

    This is a course-authored, hand-worked example. Actual execution evidence comes from your own checks.

    Why start with existing code?

    For this course, brownfield work is the default: you receive an existing application with callers, stored data, dependencies and behaviors that users may rely on. A rewrite discards some of that knowledge unless you recover it first. "Legacy" here means a system whose behavior you must understand before changing it, not simply an old programming language.

    The student project is the ci-dashboard package. Use the English orientation below; no Chinese guide is required for this investigation. A public smoke check establishes that a path starts; it does not establish correctness or permission to deploy. The small fixture below is course-original synthetic code, independent of the project's planted defects. It contains no real build records, users or private repository data.

    Characterization before changes

    A characterization test records what the current program does for a chosen input. An acceptance test records what the agreed specification requires. When observed behavior is wrong or unsafe, label the discrepancy and add a failing desired-behavior test. Do not turn a known vulnerability into a permanent requirement just because a characterization test reproduces it.

    Read fixture/before.py. The public function maps a status field to a label:

    def status_label(raw: str) -> str:
    value = raw.strip().lower()
    if value == "ok":
        return "passed"
    if value == "pass":
        return "passed"
    if value == "fail":
        return "failed"
    return "unknown"

    Predict the output of " ok ", "OK", "pending" and "ok|fail" before opening the public cases. Inputs are strings representing one status field. The exercise does not define behavior for None, lists or whole build records. Changing that domain requires an explicit specification decision and tests, not a guess by an agent.

    Generation paired with verification

    Ask the approved hosted or replay route for one lookup expression using generate.py. Its prompt supplies this small public function and explicitly preserves normalization, aliases and the unknown fallback. The broker returns text into proposal.txt; it does not execute it. Inspect the expression, then place it in a status_label(raw: str) -> str function in week05-work/candidate.py using your editor. Keep the original tests unchanged and run the candidate through the launcher. Reject unrelated imports, installation requests and attempts to redefine the task.

    The public rejected proposal is a deliberately constructed failure example, not a claimed model response. It removes strip(). The public worked refactor keeps both normalization operations and moves the aliases to one lookup table. Inspect the diff before comparing the three versions. A shorter function is still responsible for the same contract.

    Check the requested structure as well as behavior: a conditional expression may pass every public case while failing the request for a dictionary lookup. Record both observations; do not label functional test success as complete compliance with the prompt.

    Safe refactoring rhythm

    Use a single, explainable sequence: locate the caller and state boundary, freeze behavior tests, make one structural change, run the unchanged tests, inspect the diff, and record a rollback condition. Keep behavior fixes, dependency changes and database migrations in separate reviewable steps. If a regression appears, narrow or revert the candidate change while retaining the test that exposed it. A passing fixture is evidence for its inputs, not a proof about every input.

    Shared code reading: 20 minutes

    Follow activities.en.md. Work in groups of three or four, with an individual text response available. One proposal must address the execution or dependency boundary as separate formative LO7 practice; that proposal is not a CP1 item.

    All required source and instructions are plain text. Keyboard-only editing and written feedback cover the same work. Instructor-approved equivalent participation can use individual text annotation and asynchronous written feedback or adjusted time, preserving the same LO and output without lowering the score ceiling. An available option is not a record of an actual accommodation approval. See the activity for the help checkpoint and equivalent route.

    Dependencies and migration

    Start from the current lock and a reproducible baseline. Identify which caller, API shape or stored field may change. Obtain the chosen exact dependency and its transitive closure through the course's trusted preparation route. Review the lock diff, provenance and applicable scan results. Dependency setup scripts are executable code and use the approved launcher boundary. The fixture has no third-party dependency; do not install packages merely to complete it.

    Verify the old and new environments against the same contract cases, including error and permission paths. For a schema change, test a disposable synthetic database: preserve old-reader compatibility, migrate a copy, compare record counts and values, then test the new reader. Record what happens if the process stops halfway. Prefer an additive field and a temporary compatibility adapter when feasible, removing the old field only after consumers have migrated. Never assume that reverting application code reverses a destructive data migration. Keep a tested restore path and pause adoption if required dependency bytes or offline scan data are unavailable.

    Is this repository ready for an agent?

    An agent entering a repository needs what a new developer needs, with less ability to ask: a change point it can find, rules written where it reads them, tests that catch a wrong change and gates that stop a bad one. The agent-readiness scorecard turns each need into observations. Score ci-dashboard on its four dimensions at the commit you start M1 from, and again at M1 acceptance:

    Dimension What it asks Probe (the scorecard gives every step)
    Structure Can an agent find the change point? From the README and file names, predict the function to change, then open files until you reach it and record each one. If your M0 feature touches /items, your trace of it is this probe.
    Documentation Are the rules written where an agent reads them? Give a fresh session only the context file. Ask how to run and test the project and what must never change, then run every command it gives you.
    Tests Fast, repeatable, covering what you will change Run the full test command twice, search the tests for hidden inputs and break one path you will change. The package has no test command yet, so expect a 1 here.
    Checks What must an agent's change pass? List every gate before a commit or merge. Make an unused-import change and a canary change, and record what stops each.

    Each dimension has four levels, and the scorecard gives the observable anchors for each level. Give the highest level where you can show every anchor. A dimension with no evidence link is recorded as 1, whatever you believe about it. An agent may propose a level, but treat its answer as claims to check, as the scorecard shows. The score is a to-do list, not a grade: the lowest dimension names the blocker to remove first.

    Demonstration. In the lecture, the teacher works the ci-dashboard example for the two dimensions a context file and a hook can raise today; Tests waits for a test command. The package has no AGENTS.md. The example's context file states the run and test commands and three invariants, each with the check that protects it. A fresh session is asked one question at a time and sees only the section of that file that should answer it: how to run and test the project, then what must never change. Every command in its answers is run. Each section fits in one 1024-byte launcher prompt with its question; a rule too long for that is too long for a newcomer to keep in mind. Then a pre-commit hook in the style of the Week 3 hook runs lint. It stops a proposal that imports a module it never uses (exit 2) and passes the revision (exit 0).

    Practice. In the workshop, the 15-minute readiness activity scores one dimension of your own copy at its start commit. Record the level, commit, evidence and top blocker in the existing M1 work record, then finish the start scorecard as M1 work. A repository that scores well is also easier for the people who work in it, which is why this work is worth doing even when no agent is involved.

    A context file, a hook gate and a hand-off

    The score names blockers. Three small files remove the two that ci-dashboard starts with, and the third makes delegation checkable.

    The context file is the hand-off every session receives. Agent tools read a repository context file when a run starts. Codex, for example, reads AGENTS.md files from its global folder down to the current directory before it does any work; files nearer the current directory come later and override earlier ones, and it stops adding files at a size limit (tools/codex-cli; as_of: 2026-10-09; Source 1; Source 2; Source 3; Source 4; Source 5). Kiro also reads AGENTS.md and always includes it (tools/kiro-cli; as_of: 2026-10-09; Source 1; Source 2; Source 3; Source 4; Source 5; Source 6; Source 7; Source 8; Source 9). Whatever the file says reaches every session, so it must be short and true at the commit. It says four things: what to run to verify a change, which rules must hold and which check protects each, which files not to touch, and what to report at the end. Verify it in two ways. Run every command it lists, as written. Then compare what a session does on one bounded task with and without the file.

    A hook turns a rule into a gate. A Boundaries line asks a session not to change pyproject.toml in a feature change. A pre-commit hook that stops any commit listing that file makes the rule hold even when a session ignores it. It also gives the session a runnable pass/fail signal of the kind the guidance on agentic coding recommends (tools/claude-code-best-practices; as_of: 2026-10-07; Source 1). A gate counts as evidence only after you have seen it fail on the change it exists to stop, with its own reason, and pass on a good change. An exit 2 because the hook refused its input is not the rule firing.

    A hand-off divides one task between roles. A subagent is a fresh session with one role and only the context that role needs. Some tools let you define such a role in a configuration file that sets its tools, permissions and context (tools/kiro-cli; as_of: 2026-10-09; Source 1; Source 2; Source 3; Source 4; Source 5; Source 6; Source 7; Source 8; Source 9). The division holds only if each hand-off says what the role may change, what it must run and what it hands back. Check each hand-back against the diff and the launcher results, not against the role's own summary. A reviewer that receives the implementer's notes judges the plan it has read instead of the change that was asked for.

    The Week 5 practice does all three on your copy, offline with course-written replays, in about 80 minutes of M1 work. It ends with a second score for Documentation and Checks.

    LLM wiki and documentation discipline

    An LLM wiki is a navigable explanation generated from repository material. It is a draft index, not an extra source of truth. For this exercise, one paragraph in the existing M1 record is enough: "At commit X, caller A invokes B; test C checks input D; error behavior E is still unverified." Replace X/A/B/C/D/E with actual evidence. A model's confident prose cannot establish an invariant. Update the paragraph with code changes, keep uncertainty explicit, and remove stale claims. Avoid duplicating entire files or adding a documentation platform. Review any suggested command before running it through the launcher.

    Use the retry-boundary exercise to derive a new test and repair without the worked answer. It changes the input rule from whitespace normalization to a retry limit. Preserve an allowed case as well as the distinguishing equality boundary. The teacher provides feedback before the separate assessment; this public hand-trace exercise is not a CP1 bank item.

    Reading the fixture comparison

    The fixed Python 3.12 fixture has ten named input/expected-output pairs and no randomness or third-party dependencies. verify.py also counts Python AST If nodes across the selected module, a deliberately narrow branch-structure complexity proxy, not cyclomatic complexity or a maintainability score. Reproduce the following with the three launcher commands above:

    Version Passing cases Regression cases Module if statements
    Before 10/10 0 3
    Rejected proposal 7/10 3 0
    Worked refactor 10/10 0 0

    Common mistakes

    Mistake Detection Correction
    "Tests pass, so the specification is correct." Only copied current outputs, no desired behavior or safety check. Separate characterization from acceptance and record known discrepancies.
    One large modernization patch. A failure cannot be attributed to refactor, upgrade or migration. Separate steps and retain a testable rollback boundary.
    Fewer branches proves better code. Rejected proposal has the same low count as the worked version. Check behavior, readability, test coverage and remaining risks together.
    The wiki overrules code. A claim has no matching commit, function or test. Verify against source and refresh or remove stale text.
    A dependency fix needs host installation. Proposed command downloads or executes unreviewed scripts outside the launcher. Use trusted acquisition and isolated execution, or stop when unavailable.
    An agent's readiness level goes straight into the scorecard. The level has no command output or file path at a named commit. Run the probe, record what you observe and score only what the commit shows.
    A hook counts as a gate because it exists. No run shows it stopping the change it is for, with its own reason. Run the bad event, keep the failing result, then the passing one.
    A role's hand-back is the record of what it did. Its list of changed files was never compared with the diff. Check the hand-back against the diff and open each launcher result.
    Project work stands in for CP1. Individual competence is inferred from an AI-assisted project change or a peer's answer. Each student completes their own diagnosis and repair; model access follows Week 0.
    A resit supplies unrestricted extra points. The replacement cap is omitted. Preserve both attempts; use max(original, min(resit, 5)) for CP1.
