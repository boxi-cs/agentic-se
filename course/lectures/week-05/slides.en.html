    Deliver a small change without breaking callers

    Week 5 · CI dashboard

    What must a refactor preserve?

    The requirement is already in use

    Week 4 made desired behavior explicit. Now a caller depends on a working implementation.

    The task is to replace conditionals with a lookup table, while preserving this function's behavior.

    The original function

    def status_label(raw):
    value = raw.strip().lower()
    if value == "ok":
        return "passed"
    if value == "pass":
        return "passed"
    if value == "fail":
        return "failed"
    return "unknown"

    Public Week 5 fixture. Its contract adds the pass alias to Week 1's example.

    What do callers receive?

    Inputs are strings naming one status. Predict:

    Input Output
    " PASS " ?
    "pending" ?
    "ok\|fail" ?

    What would be a different task from this refactor?

    The observable behavior to protect

    " PASS " becomes passed. "pending" and "ok|fail" become unknown.

    Supporting non-string input or changing unknown to failed would change the contract. It needs its own decision and checks.

    Mechanism: A safe brownfield change

    Protect callers by freezing a baseline, making one bounded edit, and checking the unchanged contract before accepting it.

    Characterization and acceptance

    A characterization test records what the existing code does. An acceptance test states what the agreed requirement demands.

    They can disagree. An existing security defect is a defect to repair, not a behavior to preserve indefinitely.

    A proposed refactor

    LABELS = {"ok": "passed", "pass": "passed", "fail": "failed"}


def status_label(raw):
    return LABELS.get(raw.lower(), "unknown")

    This is the public, course-authored rejected candidate.

    Which existing behavior disappeared?

    Compare the original and candidate on " PASS ".

    Name the lost operation and a regression assertion. Would removing if statements alone justify acceptance?

    A structural change can preserve the rule

    return LABELS.get(raw.strip().lower(), "unknown")

    The lookup now retains normalization and aliases. Rerun the original cases unchanged, then inspect the diff.

    A behavior check and the requested dictionary structure answer different questions.

    One path through the real repository

    GET /items -> current-user check -> query -> template

    The notes locate items in ci-dashboard's legacy_app/views.py. Trace the input and owner filter before editing.

    An HTTP 200 smoke result does not establish the returned records are correct.

    A wiki paragraph needs evidence

    The list is isolated to the current user and handles every search correctly.

    The only cited check asserts HTTP 200 after login.

    Which claim is still untested? Propose one input and expected result.

    Is ci-dashboard ready for an agent?

    Score Structure, Documentation, Tests and Checks from observations, not belief.

    Demo: a fresh session reads one AGENTS.md section per question; run every command it gives back. Then a lint hook stops an unused import (exit 2) and passes the revision (exit 0).

    The lowest score names the first blocker to remove.

    The context file every session reads

    AGENTS.md says what to run, which rules hold and which check protects each, what not to touch, and what to report.

    Verify it twice: run every command as written, then compare one task done with and without the file.

    Has this gate ever failed?

    Paths in the event Output
    domains/labels.py, pyproject.toml pyproject.toml: protected by AGENTS.md; ... exit 2
    domains/labels.py PASS: no protected file and no unused import ... exit 0
    domains/label.py (a typo) REFUSED: ... exit 2

    Which runs show the rule working? Which exit 2 is not evidence?

    A hand-off is a contract

    Role May change Hands back
    Explorer nothing callers, open questions
    Implementer domains/labels.py changed, ran, not checked
    Reviewer nothing findings, each with its check

    Check each hand-back against the diff and the launcher results, not its summary.

    A bounded first PR

    Record the caller, candidate revision and protected behavior. Ask for one structural change, with no dependency upgrade.

    The review needs the original failure or baseline, the actual retest, and a rollback condition tied to a regression.

    A dependency change introduces another boundary

    A new dependency may change API shape or persisted data. Compare locked old/new environments against the same behavior cases.

    Installation scripts are executable code. Use the trusted preparation and launcher routes from the notes.

    Reverting code may not restore data

    A migration replaces stored status names with numeric codes. Old code still expects names. The new deployment is rolled back.

    What must a recovery plan restore or keep compatible?

    Compatibility needs its own check

    Test old and new readers on a disposable migrated copy. Check interrupted migration as well as the completed path.

    An additive field can keep old readers working during transition. A destructive transformation needs a tested restore path.

    Independent diagnosis before CP1

    A retry is allowed exactly when used < limit. Inputs: nonnegative integer used, positive integer limit.

    def can_retry(used, limit):
    return used <= limit

    Derive a test, predict the fault and propose a repair independently. Keep one allowed case. Use the activity's ten-minute practice block.

    Three proposals in the reading activity

    Use the existing 20-minute activity:

    • One behavior-preserving structural change.
    • One missing contract check.
    • One concrete execution or dependency risk.

    For each, state a test and a stop or rollback condition.

    Feedback that narrows the change

    A peer asks whether your PR also changes the unknown fallback.

    Revise the scope or split the behavior decision from the refactor. Explain which original checks stay unchanged and why.

    Exit: a "safer" fallback

    The author changes unknown statuses to failed in the same PR.

    Is this still only a refactor? Give one input that distinguishes the old and new behavior and name the decision still needed.

    CP1 and the first M1 change

    CP1 is the separate 30-minute individual AI-off session in the workshop. Use public practice for preparation; the assessment uses a different task.

    The first M1 PR reuses your bounded investigation. Next week, a model reviews it and you verify each point it raises.
