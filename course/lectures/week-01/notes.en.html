    Week 1: Coding models, agents and verification

    Learning objectives

    By the end of this week, you can:

    • LO1: distinguish training from inference-time context, and describe the roles of pretraining, supervised fine-tuning (SFT) and reinforcement learning (RL) at a high level.
    • LO1: distinguish a model's proposed action, a controller's permission decision and a tool's actual result.
    • LO5: derive a test from a requirement that distinguishes a plausible faulty candidate from a correct implementation, then explain the limits of the result.
    • LO9: preserve a prediction, compare it with the observed first attempt, and explain a mismatch or missing outcome using your own evidence.

    You already know functions, strings, conditionals and basic tests. This lesson uses that knowledge to examine a new workflow: a model proposes changes and tools act on its requests. No prior machine-learning course is assumed.

    The 90-minute class includes a 20-minute calibration activity. The subsequent workshop continues the same P1 work. P1's 11-hour estimate spans Weeks 1 and 2; there is no extra first-week submission. Use the approved hosted or replay route in Week 0 setup.

    Minimal example

    A product problem with a small implementation

    A developer uses a CI dashboard to find builds that need attention. The build service reports " OK ", but the dashboard shows unknown. The developer needs a reliable label before deciding whether to investigate the build.

    The helper is a short warm-up. We then inspect its caller, where the list of builds and the failed-build count can disagree even after the helper is repaired. Our engineering question is broader: what information must an agent acquire, what checks support its repair, and what can the engineer legitimately conclude? The continuing course case expands this product in later weeks. All dashboard candidates and action sequences in this lesson are course-authored. The helper demonstration can produce actual scripted execution observations, with zero model requests. The repository walkthrough uses printed source and hand-derived expectations; it does not report an executed repository test or a recorded agent run. Neither example establishes how often a model makes an error or a productivity gain.

    One repair from contract to regression

    The dashboard's exact teaching contract is:

    • Input is a Python string. Ignore surrounding whitespace and letter case in the ASCII status names.
    • Normalized ok means passed. Normalized fail means failed.
    • All other strings, including the empty string, mean unknown.

    Non-string input is outside this exercise. Supporting it would require an additional agreement rather than an invented default.

    The supplied proposal is:

    def status_label(raw):
    labels = {"ok": "passed", "fail": "failed"}
    return labels.get(raw.lower(), "unknown")

    Two existing assertions accept it:

    assert status_label("ok") == "passed"
assert status_label("fail") == "failed"

    Before examining the repair, derive another check from the contract. A useful test has an expected output independent of the proposed implementation and can expose an omitted rule. The input " OK " should return passed. Candidate A lowercases it to " ok ", fails to find that exact key and returns unknown.

    Adding an unfamiliar input is not enough by itself. For example, "cancelled" returns unknown in both the faulty and repaired versions. It exercises the fallback but does not distinguish their handling of whitespace. Both kinds of case can belong in a regression suite for different reasons.

    The bounded repair is:

    -    return labels.get(raw.lower(), "unknown")
+    return labels.get(raw.strip().lower(), "unknown")

    Now compare both candidates against the same explicit expectations:

    Input Required Candidate A Repaired
    "ok" passed passed passed
    "fail" failed failed failed
    " OK " passed unknown passed
    "\tfAiL\n" failed unknown failed
    "cancelled" unknown unknown unknown
    "" unknown unknown unknown

    The public demonstration executes these functions through the course launcher, checks the entire matrix and exports the actual observations with source hashes. Candidate A passes four of the six contract cases; the repair passes all six. The overall demonstration expects the first candidate's two failures. An unexpected result fails the demonstration instead of silently updating the answer.

    Retain the original two checks as well as the new regressions. The six cases provide observations about those behaviors, not an exhaustive proof over all strings. For example, internal whitespace and additional unknown strings still deserve thought. For a larger program, checking callers and integration behavior would also matter.

    Why an agent's own tests need examination

    Suppose the candidate and its generated tests both assume unpadded input. The two can agree with each other while jointly missing a requirement. This is a possible shared omission, not a numerical claim about any model. Independent expected results come from a different basis: the product contract and deliberately chosen cases.

    The model, controller and tool have different jobs

    A coding agent combines a model with an execution workflow. The model may propose reading a file, writing a patch or running a test. The controller checks the tool name, arguments, permissions and budget before deciding whether the action may run. The tool performs the permitted operation and returns an observation. The controller can then supply that observation to the model for another step.

    Event in a schematic trace What is established
    Model requests a file read An action has been proposed
    Controller allows that read The action passes this permission decision
    Tool returns file contents The tool observed those bytes
    Model proposes a patch Candidate text has been produced
    Tool writes the patch A write occurred
    Tool runs tests on the resulting code The returned test outcome is available
    Model says the work is finished The model made a completion claim

    A permission decision does not establish program correctness. A write result does not establish a test result. If a test request is denied or never finishes, a later “all tests passed” message cannot supply the missing observation. A safe next action is to inspect the refusal or missing result and obtain an allowed check through the course's supported route. Week 2 implements this loop explicitly.

    How a coding model generates a program

    A language model processes tokens, which are units of text such as word fragments, punctuation and code characters. At each generation step, it computes a distribution for the next token given the available context and selects a token. The selected token becomes part of the context for subsequent generation.

    This mechanism can produce a sequence that expresses a useful multi-step algorithm. It does not mean the model has executed that algorithm. Syntactically valid Python can still implement a different rule from the one the user needs. Two valid Python expressions can implement different input rules. Syntax alone does not tell us which behavior is appropriate; that decision requires the contract.

    A token's likelihood is also different from a probability that the resulting program satisfies the specification. Even a clear explanation of a patch leaves its behavior unobserved until an appropriate check actually runs.

    Inference uses the context the workflow supplies

    During ordinary inference, the workflow supplies a request and other context. It does not ordinarily update the model's parameters just because the user pastes a file or corrects an answer. Training changes learned parameters; prompting changes what is available for the current response.

    For our repair, useful context might include the existing function, a status contract, callers that rely on the fallback, and a recent test result. A file existing on disk is not enough: a tool or another part of the workflow must make its content visible. The context has finite capacity. Missing requirements, stale observations and omitted earlier decisions can affect later proposals.

    Imagine two context packets. One contains only “fix the label” and the implementation. The other also contains “ignore surrounding whitespace” from the product contract. The second packet supplies an explicit constraint for reasoning and test design. We cannot conclude that the model will certainly succeed with it, or that a failure proves the model lacked all relevant knowledge. We can identify what evidence the workflow made available and which constraint a candidate failed to implement.

    What training contributes

    Pretraining changes learned parameters using text and code, commonly through next-token prediction. It can develop knowledge of syntax, APIs, algorithms and recurring problem-solving patterns. General learned knowledge does not automatically include the current versions or private conventions of this repository.

    Supervised fine-tuning changes parameters using demonstrations of desired responses. For example, training pairs can show an instruction followed by a useful coding answer. Learning the form of a helpful response does not by itself prove that every condition in a new task has been handled.

    Reinforcement learning adjusts behavior using reward or feedback on sampled responses. The reward supplies a training signal; it is not an execution result for today's repository.

    These are distinct training methods. They are not a guaranteed three-stage pipeline used by every model. Their success can improve coding ability while still leaving requirements, versions and execution conditions to check at use time.

    Optional: what a training reward can distinguish

    In a hypothetical coding exercise, a reward might depend on passing tests. Consider two candidates that both satisfy checks for "ok" and "fail". If the reward never checks padded input, those outcomes do not distinguish the candidates' behavior on it. This explains a limitation of the signal, not a claim that training necessarily produces a faulty program.

    This extends the high-level training explanation. The main lesson requires the training/context distinction, not training a model or deriving an RL algorithm.

    From a helper to a repository change

    The repository walkthrough contains a complete five-file teaching snapshot: contract, sample records, label helper, dashboard caller and existing test. Read it as text. It is separate from the executed helper demo and from your later project repository.

    The developer needs correct labels and a matching failed-build count, with all build IDs retained in their original order. In the initial caller, the rows use the helper, but the count compares each raw status directly to fail. Repairing only the helper therefore leaves a disagreement for a padded mixed-case failure: the row says failed while the count remains zero. Even all six helper tests would miss that caller defect.

    Before seeing a proposed patch, derive the complete expected sample result from the contract. Then follow the authored read, edit and check sequence. Ask at each step what information a tool would return, how it would change the next proposal, and which observation an actual run would still need. The final proposed repair counts the already-computed labels. A full-output regression must check both the count and the unchanged IDs/order. An extra empty-list case checks the same rule with no rows.

    This illustrates why delegating more than a one-line function can be useful. An agent can gather relevant context, navigate from a caller to a helper, propose a bounded edit and use permitted test results to investigate the next issue. Its workflow can carry evidence between these steps. Useful delegation still needs a defined task: "make tests pass" alone does not specify the product behavior to protect.

    The example does not measure a model's ability to perform those actions or the time saved. Its outputs are hand-derived expectations. In an actual run, we would need the completed relevant test results on the current files and a scope review before acceptance. A tool result on an earlier candidate cannot verify a later edit.

    For a new judgment, suppose a patch returns only failed rows and tests only the count. Decide whether to accept or revise it, and write a distinguishing expected result before reading a peer's explanation. Refer to the original repository contract as well as the proposed test. Self-check Q7 lets you revisit your reasoning.

    What a production harness adds

    Today's loop has one model, one controller decision and one tool result. A production coding agent wraps the same loop in more machinery, which Weeks 2 to 4 examine layer by layer:

    Added around the loop What it changes Where you work on it
    Tool definitions, argument checks, budgets and stop rules Which proposed actions may run, and when the loop ends Week 2: the controller you write
    A compacted working record of earlier steps Which earlier observations stay in the context Week 2
    Repository context selection, context files, skills and tool servers Which files and procedures reach the model Week 3
    Hooks and a sandbox around tool effects Which effects happen, and what a misbehaving process can reach Week 3
    A specification and a staged plan with checkpoints What the agent is asked to do, and when a person decides Week 4

    Each layer changes what the model sees or what an action may do. None of them checks the result for you: a richer harness still needs a completed check on the current files.

    Hands-on exercise

    Follow the 20-minute activity. Start one of the existing P1 first attempts with your own time and binary pass prediction. The class uses task 001 and may discuss task 002 if time remains. Do not read the complete calibration catalog before making an unseen-task prediction. If you have already seen a task, record that exposure in your explanation.

    After the task is revealed, derive one expected input/output pair. Generate one candidate using the approved hosted route or frozen replay, preserve that candidate and inspect the public result. Do not change a first attempt after feedback. A repair uses a separate practice session. Each student writes their own short explanation and revises one claim after feedback.

    If startup or waiting consumes the activity, use the supplied text path for discussion and continue the required actual work during P1. You are not expected to complete all four model runs within twenty minutes. This lesson adds no new report or task set. The workshop finishes the selected tasks 001, 002, 003 and 005 within the existing P1 budget. The other sixteen tasks remain optional practice.

    For a transfer question, consider a new service that sends completed. Our current contract maps it to unknown. A request to support this status does not explain whether it means success, failure or merely termination. Identify what current behavior you can test and which domain fact is needed before changing the mapping. Write the question you would ask the product owner, rather than guessing a new label.

    Verification

    Reproduce and interpret the dashboard example

    Use the exact preparation and launcher commands in the demonstration instructions. A successful invocation reports zero model requests, Candidate A's expected two failures and the repair's six successes. Inspect the per-case JSON and source hashes alongside the launcher result. Read these as public practice observations. A hand trace, a reference transcript and an actual run have different provenance.

    If an actual invocation fails to complete, retain the absence of a result. The printed expectation in the lesson cannot replace that observation. Safety failures follow the Week 0 stop/support route; classroom discussion can continue from code.

    Interpret your calibration record

    Use the existing eight CSV columns: task_id,date,predicted_minutes,actual_minutes,predicted_pass,actual_pass,tool,notes. The calibration controller fills the actual fields and result references. predicted_pass is binary: 1 predicts every public case will pass, and 0 predicts at least one will fail. It is not a confidence percentage. The configured time measurement runs from the saved prediction to verification, including waiting and interruptions. Record earlier setup/help in the same explanation. Belief and record can diverge: in one randomized trial, experienced developers took longer when AI was allowed while believing afterward that they had been faster (studies/metr-2025; as_of: 2026-09-05; Source 1; Source 2); the optional reading gives that study's limits.

    The validator checks structure, result references and hashes; it does not execute an exported candidate. Matching hashes show internal consistency, not authenticity. The editable public report is feedback and does not award official grades. Retain the shared resolver's public configuration output once with your work so the actual profile identity, version and digest are available. The journal itself does not save those model-profile fields. Commands are on the activity sheet.

    For the four required tasks, report the successful first candidates out of that identified sample together with completed coverage and unknown outcomes. If there are two successes, one failure and one unknown, say exactly that, with 3/4 completed. With one first attempt per task, pass@1 is the fraction of tasks whose first candidate passes, counted over every task in the sample. The completed subset has 2/3 successes; it is not a complete four-task pass@1 result. A later manual repair cannot replace a first-attempt failure.

    An optional complete experiment over all twenty tasks uses its own denominator of twenty. A completed-only fraction, such as twelve successes from eighteen completed attempts with two unknown, is not the completed twenty-task pass@1. Separate retries, manual practice and reference runs. Neither sample establishes performance on all coding work.

    Calculate an error before interpreting it

    The existing synthetic reporting fixture contains two invented rows. Both predict five minutes and record seven. Both predict pass; one records pass and the other fail.

    • Mean signed time error, actual minus predicted: (2 + 2) / 2 = +2 minutes.
    • Mean absolute time error: 2 minutes.
    • Binary pass-prediction error: one mismatch out of two, or 0.5.

    The activity's data-only commands reproduce these calculations. They demonstrate arithmetic, not real model or student behavior. For your actual records, inspect the hosted and replay groups and their coverage separately. Explain a mismatch by examining the task, candidate and execution evidence before attributing it to the model. A missing requirement, failed execution and time spent waiting are different explanations.

    Complete the self-check independently. P1 in Week 2 reuses the existing work, verification, short explanation and revision with one reused AI-use note. No separate disclosure document or full conversation export is required.

    Common mistakes

    Mistake Diagnostic question A useful correction
    Assume a likely continuation must be correct Which requirement and observation support it? Derive a check independently of the candidate
    Treat prompting as repository-specific retraining Did parameters change, or did context change? Identify the actual inference inputs
    Assume the agent has seen every file Which event supplied the relevant bytes? Inspect the context acquisition step
    Treat a tool request as execution Is there a completed tool result? Obtain or inspect the missing observation
    Treat two green tests as full correctness Which contract rules do those cases exercise? Add a case for an omitted rule and retain regressions
    Guess that completed means success Where does the new service define that meaning? Clarify the domain contract before changing it
    Infer broad capability from one success Does the next task preserve the same constraint? Predict and verify the new case separately
    Rewrite a first prediction after seeing feedback What did the saved record say before the attempt? Preserve it and explain the prediction error
    Turn an unknown attempt into a pass or failure Did a relevant check actually finish? Report the missing outcome and follow recovery instructions

    During peer feedback, challenge one claim by naming the missing case or observation. The author then revises that claim in their own words. The goal is an explanation that survives a new input, not a repetition of the instructor's repair.
