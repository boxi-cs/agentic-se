    Verify a model audit with reproducible evidence

    Week 12 · LO7, LO9

    Which of the review's claims can this snapshot decide, and with which input?

    M3 is individual verification

    You push a frozen tag by the end of Week 11; the teaching team records one review of it.

    You mark every finding confirmed, refuted or cannot tell, and add one check.

    The model text is evidence to inspect, never a score.

    Freeze before reading

    snapshot: week12-audit-snapshot
feature: report view, status, export, archive and scoring
requirements: R1-R6
source revision: <frozen revision>
inputs: <the check and input you chose for each claim>
outside scope: production-only configuration

    A clean label keeps evidence attached to the intended revision.

    Frozen requirements

    • R1 access: a viewer or an owner reads a public report; no role reads a private body
    • R2 status: only ready and queued are accepted
    • R3 paths: every exported or archived path stays under /srv/reports
    • R4 secrets: no export configuration exposes a secret directory
    • R5 scoring: the private-count scorer gives 1 only for the right count
    • R6 root: the report root is written once, as REPORT_ROOT

    Judge each claim against these, not against the review's wording.

    A review is a hypothesis

    A plausible sentence is not an observation.

    Preserve the requirement, input, expected effect and protected state.

    Run the exact question before saying confirmed.

    The mechanism

    Why over-assertion happens

    A salient token can trigger a shortcut.

    The review may miss an allowlist, a guard that covers only one branch, or a sibling that does it right.

    Run the exact input and state before accepting the claim.

    Why omissions happen

    A named route is only one path.

    Probe a sibling path, boundary value or protected-state change.

    A clean result is bounded by the range you checked.

    The recorded review: five claims

    Security, evaluation and maintenance claims, each with an id.

    Most point at a function. One is prose only.

    No check, input or answer is given: you choose them.

    Course-authored practice record; no model wrote it.

    One worked row

    Claim (not in the review): an owner can read the body of a private report.

    • Requirement: R1
    • Check and input: private-report-view, {"private": true, "role": "owner"}
    • Prediction: if the claim holds, the body is visible
    • Observation: deny, body_visible: false
    • Disposition: refuted, for this one input

    What one run can decide

    The claim is about One run can
    one input confirm or refute it
    some input confirm it, with a witness
    every input refute it, with a counterexample
    each member of a listed set decide that member only
    something outside the snapshot show it cannot be read

    An unfinished search is not a disposition

    Inputs that behave do not refute a claim about some input.

    The snapshot still decides it, so it is not cannot tell either.

    Read the rule the code applies; probe its edges; keep every input you tried.

    Turn a prose claim into a check

    1. Name the requirement it says is broken.
    2. Find the check that exercises that behaviour.
    3. Write the input that would show the problem, and the expected observation.
    4. Choose inputs at the rule's edges, not typical values.

    Split an overstated claim

    "Every function does X" often holds for one function and not another.

    Record one part per member, each with its own evidence and disposition.

    One word would either hide a real defect or assert a false one.

    Bound the unknown

    A claim about something outside the snapshot cannot be decided from it.

    Disposition: undetermined; name the missing input.

    A check of a different path does not decide it.

    Add an own check

    Probe a path that no claim is about: a sibling of the one the review followed.

    A defect: record the input, command and observation.

    Or: “I checked this range; no defect was observed; this boundary remains outside scope.”

    Evidence record

    finding_id    the id in model-audit.json
requirement   R1-R6
disposition   confirmed | refuted | undetermined
evidence      the check and args you chose, and the printed command
parts         one per member, for a claim about a listed set
missing       required for undetermined
scope         the range checked and what stays outside

    Run one check

    sh scripts/course-sandbox --profile offline --version VERSION --digest DIGEST \
  --workspace week12-audit-work \
  -- python audit_packet.py --check private-report-view --args '{"private":true,"role":"owner"}'

    Copy the command the check prints: it starts at python and uses compact, sorted JSON.

    A runnable command has identity

    The verifier checks:

    • frozen snapshot
    • check name and arguments
    • that the input tests the claim
    • canonical command
    • observation against the disposition

    Changing an argument changes the question.

    The verifier is deterministic

    The verifier derives the supported disposition from the public observation.

    No model output enters a scoring path.

    Run through the approved launcher

    sh scripts/course-sandbox --profile offline --version VERSION --digest DIGEST \
  --workspace week12-audit-work --output week12-audit \
  -- python verify_audit.py --submission student-audit.json

    Use resolver values and a fresh output directory.

    What the verifier rejects

    • an input that does not test the claim
    • a disposition the observation does not support
    • an observation that cannot decide the claim: choose another input
    • a listed-set claim without one part per member
    • missing evidence or an empty reason for undetermined
    • a changed command, or missing, extra or wrongly typed argument keys
    • a missing own_check

    Your M3 timeline

    When You
    End of Week 11 push the frozen tag
    After the deadline receive a copy of the audit
    Week 12 workshop plan every finding; run the first check
    Rest of Week 12 verify every finding; add your own check
    M3 deadline submit the record

    Tag one version for M3

    By the end of Week 11:

    git status --porcelain   # keep the output empty
git tag -a m3-freeze-12 -m "M3 snapshot"
git rev-parse m3-freeze-12^{commit}  # record this revision

    Run the evidence against this tag, then keep the tag and output together.

    Check the tag, then push it

    git ls-tree -r --name-only m3-freeze-12   # every path the audit receives
git push origin m3-freeze-12              # a plain push does not send tags

    Scan the tagged tree for secrets before you push.

    Protected state matters

    A response can say deny while still changing a report or path.

    Record the state as well as the response.

    Real M3 boundaries

    The audit reads only your frozen snapshot: your own work.

    No participant material, including de-identified notes; no credentials or unrelated session logs.

    Evidence conflict

    An evidence conflict goes to the human integrity process.

    An authorship detector does not decide responsibility from style.

    Workshop sequence

    0–10 freeze · 10–20 plan · 20–40 run · 40–50 mark and split

    50–60 own check · 60–65 verify · 65–90 start your own M3 record

    Exit question

    A claim says some input breaks a rule, and your first three inputs behave.

    What do you write, and how do you choose the fourth input?

    Transfer to M3

    Your tag was pushed by the end of Week 11.

    Verify every audit finding, split any whose parts differ, and add one check the review missed, or bound a clean range.

    Keep the model record separate from the evidence you submit, and keep your user tests going.
