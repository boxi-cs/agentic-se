    Week 12: Verify a model audit with reproducible evidence

    Learning objectives

    By the end of this session you can:

    • label a clean, frozen snapshot and its requirements before reading a recorded model review;
    • turn each review claim, including one written only in prose, into a check and an input you choose yourself;
    • tell from a claim's wording what one run can decide;
    • split a claim that overstates its scope into the part that holds and the part that does not;
    • write undetermined only when the snapshot lacks what would decide the claim; and
    • add one reproducible check for a defect the review missed, or bound a checked scope with an honest no-finding statement (LO7, LO9).

    M3 is individual work. You push a frozen tag of your project by the end of Week 11. The teaching team runs one model review on that tag and sends you a copy, and in Week 12 you verify every finding in it. The model text is evidence to inspect, never a score. The M3 timeline lists each step.

    Minimal example

    Freeze the question and snapshot

    The supplied fixture is labelled week12-audit-snapshot. Copy that label and the frozen requirements into the audit record before opening the review. For each item preserve the requirement, input, expected effect, observed effect, source revision and command. A hand trace is a prediction; a launcher observation is evidence.

    These are the snapshot's frozen requirements. Every disposition is judged against them, not against the wording of the review:

    R1 access: a viewer or an owner can read a public report; no role reads a private report body.
R2 status: the status endpoint accepts only the labels ready and queued.
R3 paths: every exported or archived report path stays under /srv/reports.
R4 secrets: no export configuration exposes a secret directory.
R5 scoring: the private-count scorer gives 1 only when the answer's first word is the number of private sample reports; every other answer scores 0.
R6 root: the report root is written once, as REPORT_ROOT; no function repeats the literal path.

    Production configuration is not part of this snapshot, so no check here can read it.

    The recorded review is course-authored practice material; no model wrote it. It holds five claims about security, evaluation and maintenance. It gives each claim's id, its area and, for most claims, the function it points at. It does not say which check to run, which input to use or what the answer is. Choosing those is the exercise.

    One worked row

    This claim is not in the review. It shows the steps once, from claim to disposition:

    An owner can read the body of a private report.

    1. Requirement. R1 says no role reads a private report body, so the claim asserts an R1 defect.
    2. Check and input. The claim names one case: an owner and a private report. The private-report-view check takes private and role, so the input is {"private": true, "role": "owner"}.
    3. Prediction, written before the run. If the claim holds, allowed and body_visible are both true.
    4. Run. The launcher command is in the exercise below.
    5. Observation. {"allowed": false, "body_visible": false, "status": "deny"}.
    6. Disposition. Refuted. The claim is about one input, and that input is denied with the body hidden, as R1 requires.

    The record the verifier reads shows this row as JSON.

    What one run can decide

    A claim's wording sets what one observation can show. Read it before you choose an input.

    The claim is about One run can One run cannot
    one input ("an owner on a private report") confirm or refute it
    some input ("can", "an input exists") confirm it, if the run shows the problem refute it: an input that behaves shows only where the problem is not
    every input ("any", "always") refute it, with one counterexample confirm it: an input that behaves is one case of many
    each member of a set you can list ("every function in this file") decide that member decide the others; check each member
    something outside the snapshot show that the snapshot cannot read it decide it

    An unfinished search is not a disposition. If the inputs you tried for a "some" claim all behave, the snapshot still holds what decides the claim, so cannot tell is wrong too. Read the code for the rule it actually applies and choose inputs at that rule's edges. Keep each input you tried; they record where you looked. undetermined means the snapshot lacks the input or configuration, and the row names it. It does not mean you stopped looking.

    A claim often overstates its scope: it holds for one member of a set and not for another. Do not force it into one word. A single "refuted" would hide the part that holds, and a single "confirmed" would assert the part that does not. Split the claim, give each part its own evidence and disposition, and the part that holds still reaches M4.

    Turn a prose claim into a check

    Some claims point at a function and name an input. Others only describe behaviour, such as "the search page can show another user's reports". To check one:

    1. Name the requirement the claim says is broken.
    2. Find the check that exercises that behaviour. Running audit_packet.py with no --check lists every check and its argument keys.
    3. Write the input that would show the problem, and the observation you expect.
    4. Read the code for the rule it applies, then choose inputs at that rule's edges rather than typical values.

    Why reviews over-assert

    A model tends to turn a salient token into a conclusion. It may see a value that looks dangerous and skip the allowlist that stops it. It may see one function that breaks a rule and assume every similar function does. It may also fill a missing file with a plausible assumption. Test the exact input and protected state before using words such as "confirmed". A successful command supports only the path and revision it exercised. The test should fail before a repair; a passing test after a repair cannot prove the frozen defect was absent.

    Why reviews miss defects

    Review attention is finite. A model may follow the route it named and never probe a sibling: a second function that builds the same kind of path, a denial side effect, or a boundary value. Choose one path the review did not cover and run a small check of your own. If the checked path is clean, say which range you examined and which paths remain outside scope. Do not silently rewrite the recorded review.

    Label a clean snapshot

    Use a small label before inspection:

    snapshot: week12-audit-snapshot
feature: report view, status, export, archive and scoring
requirements: R1-R6 above
source revision: <frozen revision>
inputs: <one line per claim: the check and input you chose before running>
outside scope: production-only configuration

    This label prevents evidence from a repaired or unrelated revision being attached to the review. It also makes a bounded "no defect observed" statement possible.

    Hands-on exercise

    Work through the public fixture in a fresh directory. Copy each file explicitly, then edit the empty student record:

    mkdir -p week12-audit-work
cp lectures/week-12/fixtures/audit_packet.py week12-audit-work/
cp lectures/week-12/fixtures/model-audit.json week12-audit-work/
cp lectures/week-12/fixtures/verify_audit.py week12-audit-work/
cp lectures/week-12/fixtures/student-audit.json week12-audit-work/

    Read model-audit.json. Before you run anything, write one plan line for each of the five claims: the requirement, the check, the input and the observation you expect.

    Run one check at a time through the launcher. Replace VERSION and DIGEST with the resolver values from Week 0. This command runs the worked row:

    sh scripts/course-sandbox --profile offline --version VERSION --digest DIGEST \
  --workspace week12-audit-work \
  -- python audit_packet.py --check private-report-view --args '{"private":true,"role":"owner"}'

    The launcher prints one JSON record, and the check's own output is in its stdout field. That output names the args the check ran with, the observation and the canonical command. Record that command exactly as printed: it starts at python, without the launcher prefix, and its arguments are compact JSON with sorted keys. End the same launcher command with just -- python audit_packet.py to list each check and the argument keys it takes. A check refuses a missing, extra or wrongly typed argument instead of guessing.

    Mark each recorded claim confirmed, refuted or cannot tell, as in Week 6. The M3 record calls cannot tell undetermined. When an observation does not decide a claim, change the input, not the disposition. Retain the command output with the snapshot label.

    The record the verifier reads

    student-audit.json holds the snapshot label, a verifications array with one row per recorded claim, and one own_check object. This is the worked row in that shape:

    {
  "finding_id": "worked-example",
  "requirement": "R1",
  "disposition": "refuted",
  "evidence": {
    "check": "private-report-view",
    "args": {"private": true, "role": "owner"},
    "command": "python audit_packet.py --check private-report-view --args '{\"private\":true,\"role\":\"owner\"}'"
  },
  "scope": "Checked an owner on a private report on week12-audit-snapshot: denied, body hidden. The claim is about this one input."
}
    • finding_id is the id of the claim in model-audit.json. The worked claim is not in the review, so its row would not pass the verifier as it stands.
    • disposition is confirmed, refuted or undetermined. An undetermined row also needs missing (the input the snapshot lacks) or why_undecidable.
    • evidence names the check and the arguments you chose, and the printed command.
    • requirement and scope are for the person reading your record. The verifier does not judge prose, but M3 is marked on whether each conclusion states its boundary.

    A claim about each member of a set you can list takes a parts array instead of one disposition. Each part is about one member and has its own disposition and evidence:

    {
  "finding_id": "<id>",
  "requirement": "R<n>",
  "parts": [
    {"part": "<the member>", "disposition": "<disposition>", "evidence": {...}, "scope": "<sentence>"},
    {"part": "<the next member>", "disposition": "<disposition>", "evidence": {...}, "scope": "<sentence>"}
  ]
}

    The own check takes one of two shapes:

    "own_check": {
  "finding_id": "own-<short-name>",
  "kind": "new-defect",
  "requirement": "R<n>",
  "disposition": "confirmed",
  "evidence": {"check": "<check>", "args": {<its keys>}, "command": "<printed command>"}
}

"own_check": {
  "finding_id": "own-<short-name>",
  "kind": "scope-check",
  "requirement": "R<n>",
  "result": "no-defect-observed",
  "scope": "<the range you checked>; <the boundary that stays unchecked>",
  "evidence": {"check": "<check>", "args": {<its keys>}, "command": "<printed command>"}
}
    • new-defect: an input that no recorded claim and not the worked row is about, whose observation breaks a frozen requirement; or
    • scope-check: such an input whose observation shows no defect, with a sentence naming the checked range and its boundary.

    When the five rows and the own check are filled, run the verifier. Use a fresh output name on every retry:

    sh scripts/course-sandbox --profile offline --version VERSION --digest DIGEST \
  --workspace week12-audit-work --output week12-audit \
  -- python verify_audit.py --submission student-audit.json

    Your M3 timeline

    When What you do
    By the end of Week 11 Tag a clean revision of your project, check the tag and push it, as in Tag your M3 snapshot
    After the tag deadline The teaching team runs the model audit on your tag and sends you a copy of its output and run record; keep the copy unchanged
    Week 12 workshop, last 25 minutes Start your own record: label the tag, write a plan line for every finding and run the first check
    Rest of Week 12 Verify every finding and add your own check; plan about five hours for it
    Published M3 deadline Submit your verification record

    Week 12's published estimate is nine hours. The class, the user test scheduled this week and the self-check take most of the rest.

    Your own audit follows the same steps as the drill. Check out the tag in a separate worktree, so that every observation comes from the frozen revision, and run each check through the launcher as in the project workshops:

    git -C PROJECT_REPO worktree add ../m3-check m3-freeze-12

    For each finding in your copy, write the requirement from your project's acceptance criteria, then the check, input and expected observation. The M3 instructions say what each disposition needs: a test that fails on the tag or a repeatable reproduction to confirm, runnable evidence against the claim to refute, or the missing input named for cannot tell. Split a finding whose parts differ. Your own check probes a path the audit did not cover, or bounds a clean range.

    Tag your M3 snapshot

    In a real M3 audit the model reads only your frozen snapshot. The M3 instructions require that it holds only your own work: no participant material, including de-identified notes, and no credentials, session logs or unrelated personal data. By the end of Week 11, confirm the tree is clean, create an annotated tag and record the commit it names:

    git status --porcelain       # empty output
git tag -a m3-freeze-12 -m "M3 snapshot"
git rev-parse m3-freeze-12^{commit}

    List every path the tag contains; the audit receives exactly these:

    git ls-tree -r --name-only m3-freeze-12

    Then scan the tagged tree, not your working copy. From the course root, with PROJECT_REPO replaced by your checkout, copy the security workshop's scanner and the tagged files into a new workspace and run the scan through the launcher:

    mkdir -p m3-scan-work/tagged
cp -R capstone/security-workshop/student/scan m3-scan-work/scan
git -C PROJECT_REPO archive m3-freeze-12 | tar -x -C m3-scan-work/tagged
sh scripts/course-sandbox --profile offline --version VERSION --digest DIGEST \
  --workspace m3-scan-work -- python scan/run_scans.py --target tagged

    In the report, which is the launcher's stdout, the secret entry under counts must be 0, or each secret finding must be an sk-EXAMPLE value you recorded as an exception. If a path holds participant material or a real credential, do not submit that tag: revoke a leaked key with its provider and tell the teaching team. Otherwise push the tag by the end of Week 11, because a plain git push does not send tags:

    git push origin m3-freeze-12

    The M3 rubric shows how your verification is marked. Keep the user tests scheduled across Weeks 11-13 going while the audit runs; M4 needs all three (preparing user tests).

    Verification

    verify_audit.py exits zero only when all five recorded claims and the own check have reproducible evidence. It accepts exactly these meanings:

    • confirmed: the runnable observation demonstrates the stated defect on this snapshot;
    • refuted: the runnable observation contradicts the stated defect; or
    • undetermined: the snapshot lacks the input or configuration needed to decide, and the missing item is named.

    The verifier holds each claim as the check and inputs it is about and as its reach: one input, some input, every input, or each member of a listed set. That is the question, not the answer. It checks the snapshot, the check name, the arguments and the canonical command, then runs the deterministic check and derives the supported disposition from the observation. Arguments must be exactly the keys the check takes, with private a JSON true or false and role either viewer or owner, so the verifier judges the same input the check ran.

    It rejects an input that does not test the claim, a disposition the observation does not support, an observation that cannot decide the claim's reach, an item with no evidence, an empty undetermined reason, a claim about a listed set without one part per member, a different command and a missing own check. Each rejection names the key, the command or the observation it used. It does not call a model and model output never enters a scoring path.

    Evidence conflicts go to the human integrity process; an automatic authorship detector does not decide responsibility.

    Common mistakes

    • Treating a hand prediction as a run.
    • Running the first check that looks related instead of the input the claim describes.
    • Recording the launcher-prefixed command, or spaced JSON arguments, instead of the command the check printed.
    • Refuting a claim about some input because the inputs you tried behaved.
    • Confirming a claim about every input from one input that showed the problem in one place.
    • Marking a claim with an overstated scope with one word instead of splitting it.
    • Calling a claim cannot tell because a search was unfinished, when the snapshot holds what decides it.
    • Calling a false positive confirmed because its wording sounds plausible.
    • Using a different revision or changing the evidence arguments after the run.
    • Calling missing production configuration a defect, or "deciding" it with a check of a different path, instead of undetermined.
    • Forgetting to probe one path the recorded review did not mention, or failing to bound a clean path.
    • Reusing evidence from a repaired revision to close a finding on the frozen revision.
