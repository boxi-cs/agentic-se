    Recover a user path after an incident

    Week 11 · CI dashboard

    Did the operation fail, or did its reply disappear?

    Today's sequence

    CP2 occupies its separate 30-minute individual AI-off session. After collection and transition, we reason through the incident, predict how a draft diagnosis fares against a request log, then turn to the gateway that every model call passes.

    The workshop continues actual incident work through the supplied route and prepares the user tests scheduled across Weeks 11-13.

    A user retries after a timeout

    A developer requests a retry of build 42. The client does not receive a reply, so the developer retries. Two jobs now exist.

    Course-authored incident. The event table is a reasoning input.

    What does the timeout establish?

    Possible histories:

    A. The request never committed. B. The request committed, but the reply was lost.

    Which observation could distinguish them?

    The stored effect survives a lost reply

    Event Request Persisted state
    Request received req-a No job yet
    Transaction commits req-a J81 queued
    Reply lost; client times out req-a J81 still queued
    Retry commits req-b J82 also queued

    The job state and request association supply evidence the client lacked.

    Request identity and operation identity

    req-a: operation retry-B42-7, build 42
req-b: operation retry-B42-7, build 42

    These are two deliveries of one intended operation. A later intended retry would use a new operation key.

    Mechanism: Retry with an operation identity

    A timeout leaves two possibilities; a same-key lookup either creates the operation once or returns its stored result.

    A check followed by an insert

    Request A: no existing job for this key
Request B: no existing job for this key
Request A: insert J81
Request B: insert J82

    Why is "check for the key first" insufficient under concurrency?

    Uniqueness belongs at the persistence boundary

    Store the unique (pipeline, operation_key), canonical payload and job creation in one transaction.

    A matching repeat returns the existing job ID. A reused key with a different payload returns a conflict.

    The operation is idempotent for matching repeated requests.

    Replay the repaired operation

    Input sequence Required result
    Commit, lost reply, matching retry ?
    Concurrent matching requests ?
    Same key, different build ?
    New key, a genuinely new retry ?

    Predict job count and response, not just an HTTP status.

    The repair protects both repetition and new work

    Matching repeats produce one job and return its ID. Different payload under the same key conflicts without a new job. A new intended operation with a new key may create a new job.

    Denying every retry would stop legitimate work too.

    Recovery includes the user's view

    A healthy process is one observation. A queued job is another. The build detail must eventually display the required state for that job.

    A green health endpoint does not establish the full user path recovered.

    A bounded mitigation hypothesis

    Associate matching retries with one persisted job. Preserve new authorized retries and reject key/payload conflicts. Check the event chain and replay cases before accepting the repair.

    Rollback if new authorized operations fail or existing mappings are corrupted.

    A useful runbook entry

    Symptom: client timeout; possible duplicate jobs
Inspect: request, operation key, persisted job and displayed state
Check: repeat same payload/key; then test a new operation
Recovery: one intended effect and visible completion

    Attach actual revision and observations after the drill executes.

    Observe before you repair

    R2 went live at 10:05. A user says the project page is slow. An agent's draft root-cause analysis claims:

    • H1: R2 broke imports; server errors since the deploy.
    • H2: the project page slowed from 10:05; other pages held.
    • H3: the cause is one database query per build.

    Confirmed, refuted or cannot tell? Which line or field decides each?

    Course-authored draft; no model wrote it. You check it against the request log with check_rca.py.

    What a request log can show

    One line per request: time, request ID, method, path, status, duration. No query string, form fields or body.

    It can show when, where and how slow. It cannot show why.

    A cited line counts only if its time, path and status say what the claim says.

    Every model call already passes a gateway

    Job The course launcher's broker
    Key outside the work Sandbox code sends prompt text only
    Fixed destination Broker builds the request; no retries
    Per-run caps Launcher: four requests. Hosted broker: request, input-token and output-token caps, and one Budget shared across requests; FAKE has no monetary cap and costs 0
    Rate One request at a time, under a deadline
    Minimal log Length and keyed hash, not content

    Predict: five requests against a cap of four

    gateway_probe.py 5 runs through the launcher with the FAKE model.

    How many requests reach the broker? What does the launcher print? Which progress lines come back? How many records does the trace hold?

    Write your prediction now. You run the probe and check it in the separate 30-minute after-class gateway practice.

    User tests start with a neutral task

    Find the most recent failed build in pipeline Alpha.

    Compare with:

    Click the red Failed button and tell us whether it is easy.

    The first states a goal. The second supplies the interaction and invites praise.

    Observation before interpretation

    Synthetic rehearsal: the user opens Settings, returns to the list, then asks where failed builds are shown.

    Write one observation and one hypothesis separately. What should remain out of the shared project record?

    Preparation for the three user tests

    Before actual participation, confirm consent or the approved equivalent from Week 4, the neutral task, and minimal de-identified recording.

    Use the same feature through the scheduled tests. Rehearsing the prompt does not count as one of those sessions. Session notes never enter a model prompt.

    Exit: a recovered path and a remaining question

    Matching retries now return J81 without duplicates; a new key creates J82. The dashboard displays each completed result on the current revision. The declared replay cases pass.

    What recovery claim can you accept? What broader concurrency or failure conditions remain outside this evidence?

    Assume these observations for this decision exercise.
