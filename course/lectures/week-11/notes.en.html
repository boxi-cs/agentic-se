    Week 11: Recover a user path after an incident

    Learning objectives

    Walk the event chain, name a discriminating observation and write a recovery assertion before using the supplied local incident drill. Explain the reasoning independently (LO8).

    Before repairing anything, check each claim of a draft root-cause analysis against a request log. Mark each one confirmed, refuted or cannot tell, with the line or the missing field that decides it, and act only on what you confirmed.

    Operating a product also means operating its model access. Explain what a model gateway enforces, using the course launcher's host broker as the example. Predict how a run behaves when it reaches a cap, then verify the prediction with the launcher's FAKE route and its trace. Decide whether a cheaper route is good enough only from your own evaluator's results.

    Minimal example

    The continuing dashboard case

    The dashboard acknowledges a retry request, then times out before the UI sees completion. The operator retries and a second job is created.

    The following table is synthetic. retry-B42-7 identifies one user operation; req-a and req-b identify two delivery attempts for that same operation.

    Time Request Operation key Observation Stored effect
    00:00 req-a retry-B42-7 Server receives retry for build 42 None yet
    00:01 req-a retry-B42-7 Transaction commits Job J81 queued; build 42 retrying
    00:02 req-a retry-B42-7 Reply is lost; client times out J81 still queued
    00:03 req-b retry-B42-7 Client repeats the same operation Unprotected handler creates J82
    00:04 query-c retry-B42-7 Operator reads stored state Two jobs: J81 and J82

    The client timeout alone cannot distinguish a lost reply from a failed commit. The persisted job and its operation key provide the discriminating observation.

    Decision: Which evidence separates a failed request from a successful effect whose reply was lost?

    Correlate the request ID, queued job and state transition. A timeout describes an observation boundary; it does not prove nothing happened. Use an operation identity to prevent duplicate effects and verify the actual user path after mitigation.

    Ask for a bounded repair hypothesis tied to the event chain. State a rollback condition and compare the hypothesis against logs before changing the service.

    Proposed repair: store a unique (pipeline, operation_key) and its canonical payload together with job creation in one transaction. A repeated matching request returns the existing job ID; the same key with a different build is rejected. A genuinely new retry uses a new operation key. A check followed by a separate insert can still race, so uniqueness and atomicity belong to the persistence boundary. The dashboard's import API applies the same ideas to build records: identity is scoped to the pipeline, the greatest attempt for each pipeline and external ID is kept, and one invalid row stops the whole batch from being saved.

    Compare three handlers: no protection, a lookup followed by an insert if the key is absent, and the proposed repair.

    Replay input Unprotected result Check-then-insert result Expected repaired result
    req-a commits, its reply is lost, then req-b repeats J81 and J82 Only J81; req-b finds it Only J81; req-b returns J81
    req-a and req-b arrive concurrently with the same payload/key Two jobs Both lookups find nothing, so two jobs One committed job; both return its ID
    Same key is reused for build 43 Another unintended effect Conflict; no job for build 43 Conflict; no job for build 43
    A later intended retry uses retry-B42-8 New job New job New job permitted

    The three result columns are predictions. Cover them, write your own result for each row and handler, then run the course's replay fixture in all three modes and compare. It plays the four rows against an in-memory database. Row 2 forces the race: its two requests run in two threads, and each handler pauses just before its first write, so both finish any lookup before either one writes. The shared connection runs one statement at a time, and no lock is held across a lookup and an insert, so only the database's own rules can stop a duplicate. The repaired handler applies the import rule's ideas to retries: an operation key unique within its pipeline, one statement for the whole batch so a conflicting row saves nothing, and the dashboard showing a build's greatest attempt. The replay makes no model call, so run the unchanged file from the course root with the locked course tools:

    uv run --project infra/hosted --locked python lectures/week-11/fixture/retry_replay.py unprotected
uv run --project infra/hosted --locked python lectures/week-11/fixture/retry_replay.py check-then-insert
uv run --project infra/hosted --locked python lectures/week-11/fixture/retry_replay.py repaired

    The unprotected run meets the repaired requirement on one row of four and check-then-insert on three, failing row 2 with two jobs; both exit 1. The repaired run exits 0 and prints:

    mode: repaired
row  replies       jobs (build/attempt)  build 42 shows
1    J81 J81       J81 42/7              J81
2    J81 J81       J81 42/7              J81
3    J81 conflict  J81 42/7              J81
4    J81 J82       J81 42/7, J82 42/8    J82
rows meeting the repaired requirement: 4 of 4

    In rows 1, 3 and 4 the first reply answers req-a, and in row 1 that is the reply the client never saw. Row 2 lists its two replies in sorted order, because either request may write first. Where an observation differs from your prediction, keep both and find the handler line you misread. Check the stored jobs as well as the replies, then the user's view in the last column. The optional variation in the fixture README removes the forced order and shows why a concurrency check must control it. Roll back if the change rejects a new authorized operation or corrupts the existing job mapping.

    Acceptance decision: Declare recovery only after the user can observe the required state and duplicate effects are excluded for the tested path. Preserve remaining uncertainty in the runbook.

    Use this synthetic incident as a reasoning rehearsal. Actual M2 execution follows the local incident-drill handoff; use its accepted assignment bundle when supplied by the instructor.

    The replay is course-authored and synthetic: it runs this lesson's reasoning on an in-memory table, not on your preview. Evidence that your own service recovered comes from checks on your build.

    Observe before you repair

    A second course-authored incident on the same dashboard: revision R2 went live at 10:05:00, and a user then reported that the project page was slow. Before anyone changes code, an agent drafts a root-cause analysis. The draft in agent_rca.json was written for this lesson; no model produced it. It cites lines of request_log.jsonl, ten synthetic minutes of request records in the format the deployment preview documents. Each line is one request with its time, request ID, method, path, status and duration, and nothing from the query string, form or body:

    {"timestamp":"2026-11-24T10:05:41+0000","event":"request","request_id":"w11-23","method":"GET","path":"/domains/ci_dashboard/projects/2","status":200,"duration_ms":884.1}
    ID The draft claims Cites lines
    H1 R2 broke imports: the import endpoint has returned server errors since the deploy. 6, 14, 31
    H2 From 10:05 the project page's p95 rose from about 60 ms to about 900 ms; other pages held. 23, 28, 34
    H3 The cause is R2's project page running one database query per build. 23, 28, 34

    It proposes: "Roll back R2, and add automatic retries to imports."

    Predict before running. For each claim, write confirmed, refuted or cannot tell, and the field or line you expect to decide it. Then run the course's check_rca.py. It reads the two files, makes no model call and writes nothing, so run the unchanged file from the course root with the locked course tools. The second command summarises only the paths that begin with the prefix you give:

    uv run --project infra/hosted --locked python lectures/week-11/fixture/check_rca.py
uv run --project infra/hosted --locked python lectures/week-11/fixture/check_rca.py --path /domains/ci_dashboard/projects/

    The first command starts with this summary, then prints each claim and the lines it cites:

    request log: 40 request records from 10:00:02 to 10:09:58 UTC
window       requests  5xx  error rate  p95 ms
10:00-10:05  20        2    10.0%       58.9
10:05-10:10  20        0    0.0%        884.1
p95: nearest rank, the ceil(0.95 x n)-th smallest duration in the window

    The script counts and prints; it does not judge. Give each claim one outcome, as in Week 6:

    • Confirmed: the log shows the claim as stated, for the path, window and effect it names.
    • Refuted: the log shows something the claim rules out, such as a cited line from before the time the claim names, or a window without the effect it asserts.
    • Cannot tell: no field in this log could show the claim either way. Name the missing observation and the check that would supply it.

    Three cautions apply to any request log:

    • A cited line supports a claim only if its time, path and status say what the claim says. Open every one; a draft that cites lines has not yet been checked.
    • Over a few requests, a percentile is the slowest one or two. Each window here holds six project-page requests, so their p95 is the slowest of the six. Read the lines behind a summary.
    • A change that starts when a revision goes live confirms the timing, not the cause. Timing can justify a reversible mitigation; it does not tell you which code to repair.

    Act only on what you confirmed. A mitigation that rests on timing alone, such as rolling back a revision, must be reversible, state its rollback condition and end with a check of the user path. A code repair waits until a check that can see its cause has run. Drop any part of a proposal that rests on a refuted claim, but keep the claim's lines if they show something else worth following up. Next week you give the same three outcomes to the teaching team's model audit of your own snapshot. Push the frozen tag for that audit by the end of this week, as Tag your M3 snapshot shows.

    Agents that keep running after deployment

    An agent that acts in a deployed system, for example by triaging alerts or proposing a rollback, is one more service to operate. Give it credentials scoped to its task, a spending and action budget, and a switch that stops it without a deploy. Log what it read, what it proposed and what it changed, so that a postmortem can separate the agent's action from the incident it responded to. Keep irreversible operations behind a person's approval. In Replit's public account of one incident, its agent deleted data from a user's application database while development changes could still reach production, and the user restored the database through a rollback feature the agent did not know about (incidents/replit-db; as_of: 2026-09-05; Source 1). Put the agent in the runbook: who is paged when it misbehaves, how to disable it, and how to recover what it changed. Retried agent actions need the same idempotency you just examined for retried requests.

    The model gateway you have been using all term

    A gateway is one controlled place between code that wants a model and the service that answers. Every model call in this course already goes through one: the launcher's host broker. Describe a gateway by what it refuses, and check each refusal in code you can read.

    Job What the course broker does Read it in
    Keep the key outside the work Code in the sandbox can send only prompt text. It cannot name an endpoint, model, header, key or sampling setting; a real key, when one is used, is read on the host and never enters the container. scripts/sandbox_model.py, Week 0 setup
    Fix the destination The broker builds the request itself from the approved configuration and refuses one that differs. It forwards no student-chosen URL and sends no automatic retry. scripts/hosted_broker.py
    Cap each run The launcher admits at most four model requests per run. On the hosted route, scripts/hosted_broker.py creates one course_llm.Budget for the run and shares it across requests; it reserves a worst-case cost before each request, and it refuses, before sending, a request that could take the run past its request, input-token or output-token cap. FAKE runs have no monetary cap and cost 0. scripts/sandbox_policy.json, scripts/hosted_broker.py
    Limit the rate Requests are serial, one at a time, each under the run's remaining deadline. scripts/course_sandbox.py
    Keep logs minimal The trace records provider, model, status, cost and token counts. Prompt and reply appear only as a length and a keyed hash. src/course_llm/src/course_llm/tracing.py

    Two refusal messages in budget.py matter. Before sending, a request that could exceed the cap gets Request exceeds the remaining budget. After a reply, usage above the cap gets Observed usage exceeded the budget; further calls are blocked. A gateway that only reported spending after the fact would protect nobody's money.

    Predict before reading on. The course fixture gateway_probe.py asks for replies one at a time and prints a line after each. Run through the launcher with the FAKE model and asked for five replies, how many requests reach the broker? What does the launcher print? Do the request 1 to request 4 lines come back? How many records does the trace hold?

    The launcher admits four requests. It refuses the fifth before the broker sees it, stops the container and prints only a generic failure:

    {"status": "failed", "admission": false, "error": "Sandbox refused or failed; inspect the reviewed setup and limits.", "phase": "execution", "failure_category": "CONTRACT-VIOLATION"}

    The four progress lines are lost with the discarded run. The trace keeps exactly four records, one per admitted call. Here is one, shortened, from an actual course FAKE run:

    {"run": {"provider": "fake", "model": "fake-v1", "status": "ok", "cost": "0", "trace_policy": "minimal", "sequence": 0},
 "steps": [{"role": "user", "content": {"state": "not_collected", "length": 61, "hash_algorithm": "hmac-sha256", "sha256": "4caa…"}}, …]}

    Which limit stopped the run? CONTRACT-VIOLATION says only that the run broke one of the launcher's limits; the same line appears, for example, when a run prints more than its output limit. Count the trace records instead. Four records, one per admitted call, followed by this failure mean the fifth request met the request cap. Fewer records mean another limit stopped the run first.

    A cap is a hard stop, not a warning. Design the agent so that its required work finishes inside the published cap, or so that it stops and reports. The evidence of what was spent lives in the gateway's record, not in the program's own output.

    A budget reserves before it spends. The course publishes no money cap for hosted runs, only per-run request and token caps, but a budget that reserves before it spends is easier to reason about with synthetic numbers. These are course-made units, not prices. A run's cap is 10 units. Each request reserves 4 units, the worst case for its prompt and output limits. Each reply actually costs 1 unit.

    Request Spent before Reservation check Result Spent after
    1 0 0 + 4 ≤ 10 Sent; reply costs 1 1
    2–7 1–6 at most 6 + 4 = 10 Sent; each reply costs 1 7
    8 7 7 + 4 > 10 Refused before sending 7

    Three units remain, but the eighth request is refused because it could cost four. Now let request 2 lose its reply. The gateway cannot tell whether the provider charged for it, so it keeps the whole reservation. That is the same reasoning as the retried job above: a timeout marks where observation stopped and does not show that nothing happened. budget_ledger.py drives the real course_llm Budget through both ledgers so that you can check your table.

    Route to a cheaper option only when your evaluator says it is good enough

    You keep one approved model configuration all semester, so switching providers is not the choice here. A cheaper route means fewer requests, a smaller output limit, the replay route, or no model call at all. Whether it is good enough is a measurement, not an assumption. Run the same frozen cases from your M2 evaluator on both routes. Compare them case by case, including Unknown and unsafe cases. Read the cost from the trace with course-llm cost.

    Synthetic example: the Week 10 contract asks whether a supplied status is exactly failed.

    Route Evaluator result on 12 frozen cases Model requests
    Model-backed answer 12 of 12 12
    Rule on the status field 11 of 12; a missing status returns no instead of Unknown 0

    A higher pass count would not settle it, and neither does lower cost. The rule fails a case the current route passes, so it is not yet good enough. Generate a repair that returns Unknown for a missing status, rerun all 12 cases, then switch only if no case gets worse. M2 is frozen in Week 10, so in Week 11 this is a plan with its comparison written down, not a change to the frozen build.

    Preparing user tests before they start

    Use a goal-based prompt such as "Find the most recent failed build in pipeline Alpha." Avoid "Click the red Failed button and tell us if it is easy," which supplies navigation and invites praise. In a synthetic rehearsal, the user opens Settings, returns, then asks where failures appear. "Opened Settings" is an observation; "could not recognize the filter" is a hypothesis to investigate.

    Before the first actual session, confirm the consent or approved equivalent route you established under the Week 4 participation rules, the task wording, the revision and the minimal de-identified record. Schedule the three tests across Weeks 11-13 on the same path, allowing observed problems to inform a bounded iteration. Rehearsing the prompt does not count as participation. Keep names, raw media and unrelated details out of shared course records. Session notes never enter a model prompt, even after you remove names: write them up and analyse them yourself.

    Hands-on exercise

    Walk the event chain, name a discriminating observation and write a recovery assertion before using the supplied local incident drill.

    Use the activity sequence, save your prediction and allow time for peer feedback and revision. Add the actual drill evidence to M2. If no incident bundle has been supplied, the workshop's drill block runs the observe-before-you-repair exercise instead, and M2 execution stays pending. CP2 is a separate individual assessment; prepare with the public CP2 examples before the session.

    Then complete the gateway practice. Write your predictions for the probe and both ledgers before running anything. Run the probe through the launcher with the FAKE model, inspect one trace record, and replay both ledgers. Finish with a written routing comparison for one model-backed step on the path you changed in M1, using your own evaluator's frozen cases. Tool-permission portals and the risks of rolling model access out to a whole organization come in Week 13. Keep the predictions, the actual outputs and the comparison with your M2 operation notes; no separate report is required.

    Verification

    Declare recovery only after the user can observe the required state and duplicate effects are excluded for the tested path. Preserve remaining uncertainty in the runbook.

    Keep the replay, the log check and the user-test rehearsal apart from actual runs and actual participant observations. Use Week 0 setup for all executable work.

    For the log check, every claim carries exactly one outcome and the line, or the missing field, that decides it. A claim the log cannot decide stays cannot tell, with its next check written beside it; your rewritten repair acts only on confirmed claims and names its rollback condition and the user-path check that ends it.

    For the gateway practice, a four-request probe exits 0 and reports model_requests: 4. A five-request probe exits 1 with the generic failure shown above, and its trace holds four records whose content fields say not_collected. The default ledger admits seven requests and refuses the eighth. With the second reply lost, it admits four and refuses the fifth. If your observation differs from your prediction, keep both and explain which part of the code you misread. FAKE replies show the gateway's mechanics only; they say nothing about a real model's quality or cost.

    Common mistakes

    Mistake Better next action
    Accepting a draft's claim because it cites log lines Open each cited line and compare its time, path and status with the claim
    Treating a slowdown that starts with a deploy as its cause Record the timing as confirmed and the cause as cannot tell until a check that can see the cause has run
    Retrying around a gateway refusal Count the trace records to find which limit stopped the run, then shrink the work or stop and report
    Reading spend from the program's own output Total the gateway's trace with course-llm cost
    Treating a timed-out request as free Count its reservation until the outcome is known
    Calling a cheaper route good enough because its pass count is close Compare case by case on the same frozen evaluator cases, including Unknown
    Deduplicating retries with a lookup followed by a separate insert Put a unique operation key and the job insert in one statement or transaction, then force the concurrent order and count stored jobs

    The health endpoint is green but the build detail never updates. Has the user-facing incident recovered?

    No. Liveness is insufficient. Check the state transition and displayed result for the affected operation.

    A source citation, a fluent explanation or a successful demonstration does not supply a missing observation. State the next check and why it would change your decision.
