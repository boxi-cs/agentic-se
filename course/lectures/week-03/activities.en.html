    Week 3 activities

    Required workshop path: repository-context workshop

    The 80-minute classroom block rehearses each move of the week on fresh variants of the lecture's examples, then starts the workshop:

    Minutes Activity Counts towards
    0-15 Repository map of the project-list path The workshop's estimated time
    15-30 Activity 1: a packet of your own Week 3 class time
    30-45 Activity 2: would it fire, and could an agent use it? Week 3 class time
    45-55 Activity 3: watch an agent use both servers Week 3 class time
    55-80 Start the workshop's Part A The workshop's estimated time

    After the block, Activity 4 practises reading a mature coding agent's run and checking its final summary, in about 20 minutes, and Activity 5 compares one long session before and after compaction, in about 25 minutes. Both are optional practice outside the published weekly hour estimate, and neither carries marks.

    The workshop's own fixed health-path comparison, boundary check, skill and tool server are the required work; the activities below use different examples and add no second pair of required calls. The workshop's skill-use step ends with observe, adjust, recheck: what your skill's one use showed comes first, your P1 failure record second.

    Repository map: the project-list path (LO4)

    Spend 15 minutes reading the public source of your ci-dashboard package; no application needs to run. If you do not have the package yet, get the student repository first. Follow GET /domains/ci_dashboard/:

    1. domains/ci_dashboard.py, function overview: where is the current user checked, which query selects the projects, and which template renders them?
    2. legacy_app/views.py, function require_user: what happens without a signed-in user?
    3. legacy_app/templates/ci/overview.html: what does the table show for no projects?

    Record the checkout revision and three confirmed file/function references. Mark one unanswered behavior question and the test you would seek before editing. A peer checks each reference against the same revision.

    The map may start as a drawing from the approved hosted or replay route, for example a Mermaid flowchart of the same path. Treat each arrow as a claim, not as an answer. Write the arrows as a text list and label each one confirmed (file:line at your revision), refuted (what the code does instead) or cannot tell (what you would need to read or run). A drawing can hide a condition, a data change or the order of calls, so add any branch the arrows leave out. Your peer chooses one arrow labelled confirmed and tries to show from the code that it is wrong; record whether it held. A map you draw yourself uses the same labels. Label only this path, inside the same 15 minutes. Reuse this map when selecting M0 scope.

    Activity 1: A packet of your own (LO2)

    Design time: 15 minutes of class time. Materials: your ci-dashboard source, the "Build a packet of your own" section of the notes, question-2.txt and step 2 of the fixture guide. Grouping: pairs; each student builds, predicts and explains their own packet.

    1. Minutes 0–2: recall. Without the notes, write which field packet B's answer got wrong in the lecture, and which file decides it.
    2. Minutes 2–8: build. Read question-2.txt. From your ci-dashboard source, write packet-own.txt of at most 400 bytes: whole lines, each excerpt under a header line that names its file, as packet B does.
    3. Minutes 8–10: predict, then check. For status and limit, write whether your packet holds the lines that decide it. Then run packet_check.py through the launcher, or, without launcher access, have your partner check each line against the source with you. Mark each prediction against the result.
    4. Minutes 10–15: revise once. Change the packet once, within the same 400 bytes, and check it again. Your partner asks: "Which bytes did you trade for which lines, and what changed?" Write the answer in one sentence.

    Output: the recall line, two predictions, both check results and one sentence on context choice, in the workshop work record. Running packets A and B through the model route is optional; use step 3 of the fixture guide, and keep each answer as it came.

    Activity 2: Would it fire, and could an agent use it? (LO2)

    Design time: 15 minutes of class time. Materials: the skill and tool sections of the notes, label_tools.py and the launcher command in the fixture guide. Grouping: the same pairs. This rehearses the workshop's skill and tool-server parts on examples the workshop does not use.

    1. Minutes 0–5: trigger. Partner A reads only the name and description of the notes' check-label-tools skill. Partner B writes four requests the lecture did not use: two that should load it, one in different words that should, and one near miss. B records a prediction for each; A then says, for each request, whether they would load the skill. Compare, and rewrite one phrase of the description that caused a mismatch.
    2. Minutes 5–13: tools. The lecture showed four calls. These three are new:
    Tool Arguments
    search_labels {"query": "re", "limit": 2}
    delete_label {}
    delete_label {"label_id": 12, "force": true}

    Read the DRAFT and REVISED definitions. For each call, predict what each version returns, whether a label is deleted, and which rule the call tests. Add the three calls as rows in verify(), as step 4 of the fixture guide shows, run the example through the launcher and mark each prediction right or wrong. 3. Minutes 13–15: revise. Name the one change to the draft you would make first, and the call that would show it worked.

    Output: the four trigger predictions and observations, and the six tool predictions marked against the run, in the workshop work record. The workshop then applies the same moves to your own skill and to the ci-dashboard tool server.

    Activity 3: Watch an agent use both servers (LO2, LO7)

    Design time: 10 minutes of class time. Materials: the "Watch an agent" section of the notes, agent_replay.py and step 5 of the fixture guide. Grouping: the same pairs.

    The lecture showed ticket IDs 21 and 9. Here the old ticket gives two new IDs: 12, which really is red-team, and 7, which is red-blue.

    1. Minutes 0–3: predict. For each ticket ID and each server, write yes or no for: carries an ID from a result into its next call; recovers from a wrong ID; previews before it deletes. Also write which label, if any, ends up deleted.
    2. Minutes 3–7: observe. Run agent_replay.py --ticket-id 12 --summary and agent_replay.py --ticket-id 7 --summary through the launcher. The first line says the agent is course-written, not a model. Fill the rows for each server from the calls and results, then check them against --summary.
    3. Minutes 7–10: explain. With ticket ID 12, the draft deletes the right label. Does that make the draft safe to use? Name the call in the ticket 7 run that answers it, and the rule whose fix made the difference.

    Output: twelve yes-or-no predictions and the label each run deletes, the observations with the call that shows each, and your answer, in the workshop work record. When available, your instructor's recorded run with the course's hosted model shows what a model does with the lecture's request; read its calls with the same three questions, as they came, including a guessed ID, a wrong deletion or a step_limit stop. Until then, the course replay and its tables are the comparison.

    Activity 4: Dissect a mature agent's run (LO2, LO4)

    Design time: about 20 minutes, after the classroom block. Materials: the "Dissect a mature agent's run" section of the notes, the record below, your ci-dashboard source and its launcher commands. Grouping: alone or in the same pairs. This activity is practice: it carries no marks and adds nothing you must submit. It needs no key, and it is the same for everyone.

    Which record. When the teaching team publishes its frozen Codex CLI run on ci-dashboard, use that and keep its events exactly as they are. Until then, use the placeholder below. The course team wrote it by hand; no agent or model produced it. It uses the course's own layout, not any tool's output format, and says nothing about how any product behaves. The source lines it quotes are real ci-dashboard lines.

    record: course-written placeholder; no agent or model produced it
task:   What does GET /domains/ci_dashboard/ return to a signed-out visitor, and what does
        a signed-in user with no projects see? Name the file that decides each. Run the
        project's smoke check before you answer. Do not change any files.
setup:  sandbox limited to the workspace, network off; the agent asks before anything else

e1   context    loaded AGENTS.md (workspace root):
                "Run `python -I manage.py smoke` before you report. Never install packages."
e2   plan       1 find the route  2 read the sign-in check  3 read the empty-list branch
                4 run the smoke check  5 answer
e3   call c1    shell: grep -rn "def overview" domains
e4   result c1  exit 0
                domains/ci_dashboard.py:29:def overview() -> str:
e5   call c2    read: domains/ci_dashboard.py, lines 28-38
e6   result c2  @bp.get("/")
                def overview() -> str:
                    """List the caller's projects in stable order."""
                    projects = (
                        get_db()
                        .execute(
                            "SELECT * FROM ci_dashboard_projects WHERE owner_id=? ORDER BY id", (require_user(),)
                        )
                        .fetchall()
                    )
                    return render_template("ci/overview.html", projects=projects)
e7   call c3    read: legacy_app/views.py, lines 50-54
e8   result c3  def require_user() -> int:
                    """Require an authenticated user for data and profile operations."""
                    if g.user is None:
                        abort(401)
                    return g.user["id"]
e9   plan       1-2 done; 3 skipped ("the route renders the list"); 4 in progress
e10  call c4    shell: pip install pytest
e11  approval   c4 needs network outside the sandbox; asked the operator; operator denied
e12  result c4  refused by the operator; the command did not run
e13  call c5    shell: python -I manage.py smoke
e14  result c5  exit 0
                PASS: login, list, detail, and local job smoke
e15  final      (no tool calls)
                A signed-out visitor gets 401: require_user() in legacy_app/views.py aborts
                when there is no signed-in user. A signed-in user with no projects sees
                "No projects yet."; domains/ci_dashboard.py decides this when the query
                returns no rows. The smoke check passed, so both behaviours are covered by
                the project's tests. I did not install anything or change any files.
stop:   final, after 5 calls; 1 approval asked, 1 denied
    1. Minutes 0–4: predict. Read only the task and e15. Split e15 into single claims; there are at least seven. For each, predict whether the rest of the record will confirm it, refute it or leave it open.
    2. Minutes 4–10: map. Copy the five rows of the notes' mapping table (context, plan, tool calls and results, approvals and containment, stop). For each row, write the events that show it, or "not in the record". Answer two questions with event numbers: which line of AGENTS.md did an approval enforce, and which did the agent simply follow? Where did the run leave its own plan?
    3. Minutes 10–14: label against the record. Label each claim confirmed, refuted or cannot tell, and cite the event for every confirmed or refuted label. Mark each prediction right or wrong.
    4. Minutes 14–20: verify against the source. For every claim the record could not decide or refuted, check the source at your revision: the template the route renders and the smoke branch of manage.py. Run python3 -I launch.py smoke through the ci-dashboard launcher once and compare its output with e14. Give each claim a second label against the source, and keep it apart from the first.

    Contrast. Suppose the same run had been made with Kiro CLI in a workspace you had not yet trusted. Using the notes and its documentation card (tools/kiro-cli; as_of: 2026-10-09; Source 1; Source 2; Source 3; Source 4; Source 5; Source 6; Source 7; Source 8; Source 9), name the first row of your mapping table that would look different, and the event you would expect instead. This is a question about the documentation, not a recorded run.

    Output: the claim list with predictions and two labels each, the five-row map with event numbers, and one sentence on which claim you would most want an agent to stop making. Keep it with your Week 3 notes; you may cite it in the repository-context workshop if you choose.

    Activity 5: Compact a long session, then check (LO2)

    Design time: about 25 minutes, after the classroom block. Materials: the "Compaction" section of the notes, long-session.json, compaction.py and step 6 of the fixture guide. Grouping: alone or in the same pairs; each student writes their own checklist and summary. AI use: write the summary and the checklist yourself; choosing what to keep is the skill being practised. This activity is practice: it carries no marks, adds nothing you must submit and needs no key.

    1. Minutes 0–8: read and list. Run compaction.py full --show and read the 19 messages. Copy the notes' five-row checklist and fill the second column with the message index that holds each fact. Mark which read of status.py is stale.
    2. Minutes 8–12: predict, then run auto. Predict which facts the supplied compaction keeps and which file the next edit touches. Run compaction.py auto --show, fill the auto column and mark each prediction right or wrong. Name the message that held the lost fact and its role.
    3. Minutes 12–20: write, predict, run. Write summary.txt of at most 600 bytes. Predict the next edit, then run compaction.py summary summary.txt and compaction.py fresh summary.txt. Fill the last column from your file, not from the result line.
    4. Minutes 20–25: verify both ways. For each fact, does your file keep it, and did the check notice when it did not? If the check failed, change one line of the summary and run it again; keep both outputs. Then write one sentence: for this session, would you compact or restart, and what would the next session reread first?

    Output: the checklist with predictions and three columns, the outputs of auto, summary and fresh (and the revised run if you made one), and your compact-or-restart sentence. Keep it with your Week 3 notes; if a P1 compaction failure appears in observe, adjust, recheck, you may cite this record there.

    Access and repository-context workshop handoff

    All materials are plain text and commands work from a keyboard. Diagrams have text equivalents. Students may use the course team's approved additional time, partner operation or verified-record replay route while preserving their own predictions, verification interpretation and LO2/LO7 explanation. An access failure does not authorize personal paid models or unsandboxed execution.

    Reuse the map, predictions, failure analysis and AI-use note in the repository-context workshop work record. The required path is one repository map, one fixed-context comparison, one boundary check, one skill that you write, trigger-test and use once on ci-dashboard and once read-only on your candidate contribution project (if you have no candidate yet, on one of the workshop's listed repositories or another that meets the same criteria), and the ci-dashboard tool server revised against the five rules with your own protocol test. Additional skills and parallel worktrees are optional extensions; the optional reading has an in-memory permission example you may run.

    Observe, adjust, recheck

    Start from your one use of the skill. In P1 you also explained one loop failure, its fix and the repeat check; if you draw on it, cite that record by its evidence ID rather than rewriting it. Planned time: the last 10 of the 30 minutes in workshop step 6, where you already choose one step to change. Nothing is added to the workshop's estimated time.

    1. Observe. If the use showed a weak or skipped step, that is your risk; say which P1 failure it resembles, if any. Otherwise reread your P1 failure and name the risk it matches on ci-dashboard; the table gives examples.
    2. Adjust. Change one thing only: one skill step or the skill's verification.
    3. Recheck. Follow the changed part again on the same request and revision. Record what you observed; "no difference" is a valid result.
    Your P1 failure A matching risk on ci-dashboard
    Final answer before the check ran The trace is called done before its check was observed
    Ran to the step limit without finishing Reading goes on file after file with no stopping rule
    Tool result lost its tool_call_id A reference or test result is not tied to its file, command and revision
    Compaction dropped an earlier observation A shortened handoff drops a file or result read earlier that a later step relies on

    When you start from P1 and have no failure record of your own, or yours matches no row, take the nearest row and say so. The workshop's third line gives the P1 evidence ID if you used one, the risk, the one change and what the recheck showed. Follow the skill with or without an approved agent; the record is the same either way.

    Practitioner guest

    A practitioner from a partner organization joins the first class this week for up to 45 minutes to describe how their organization chooses context and tools for coding agents; the rest of the class runs as usual. Before class, write one question for the guest. After class, write one sentence comparing one claim the guest made with this week's evidence, such as your two context packets or your skill's trigger test. Keep both in your Week 3 work entry. The talk is not assessed and adds no time outside class. A guest speaks about their own organization's practice; the course endorses no product. The talk is recorded only with advance notice and the consent of those present. If no guest is available, the class runs as usual.

    Your contribution project

    The open-source contributions (C1 in Weeks 3-6, C2 in Weeks 7-13) start this week. Pick a candidate project from the approved list the teaching team publishes before Week 3, or one you will propose on the same conditions, and use it for the workshop's read-only skill transfer; you confirm the choice in Week 4. The rules, including the course-hosted route, are in the syllabus.

    Dashboard transfer

    Packet B's answer gets every field right only after a second call that adds the template file. Can you attribute the result to B's content? State the comparison you would rerun and what must stay fixed.
