    Week 3 fixtures: context packets, a long session and two tool servers

    These are course-authored synthetic files. The two packets quote the public ci-dashboard source; nothing here holds personal data or real credentials. The scripts give public formative feedback; they are not a workshop grader or a complete MCP server. Read the Week 3 notes first.

    Preparation and fixed budget

    Use the trusted Week 0 setup and approved route guide. From the course root, resolve the offline profile for every step that makes no model call:

    uv run --project infra/hosted --locked python infra/hosted/resolve_profile.py --profile offline --json

    In the commands below, replace VERSION and DIGEST with version and digest from that result. A model run uses the approved-hosted profile and your key instead: replace HOSTED_VERSION, HOSTED_DIGEST and HOSTED_CONFIG with the values Week 0 setup gives. Do not change model, sampling or resource settings. The resolver's shared contract owns the model and its limits; the launcher policy owns CPU, memory, process, disk, output and execution limits. Save the resolver JSON with your small evidence record so the complete configuration is explicit.

    The comparison adds these equal limits to both packets: the same question, 639 bytes of context, one model call, one answer, one check, no automatic retries or repairs. Each packet plus the question is at most 1,022 bytes, within the offline profile's 1,024-byte prompt limit, which the course tests check. The hosted item's own limit is set when that item is enabled; a refusal there is a result to record. The launcher's safety probes add waiting time; count that in your activity time, separately from model-call latency.

    Use your editor or file manager to create week3-work under the course root and copy only these public files from this directory into it:

    ab-replay.json
agent_replay.py
boundary.py
compaction.py
generate.py
label_tools.py
long-session.json
packet-a.txt
packet-b.txt
packet_check.py
question-2.txt
question.txt
verify.py

    Do not copy .git, teacher answers or the private course checkout. Keep the same clean input snapshot for A and B. The launcher copies it into a temporary workspace; it does not mount your host workspace and does not preserve in-sandbox edits. All steps can be completed with a keyboard and plain-text editor.

    1. Predict, then check the course replay

    Read question.txt, packet-a.txt and packet-b.txt as text. Write what each packet's answer will say for the four fields. Then run the checker over the course-written pair:

    sh scripts/course-sandbox --profile offline --version VERSION --digest DIGEST --workspace week3-work -- python verify.py --replay ab-replay.json

    Expect exit_code: 0 and three lines: the record's kind: course-synthesised, its configuration and reproduction command, then a with 0 of 4 correct and b with 3 of 4. No model was called for this record; the course team wrote both answers by hand. If any input file differs from the one the record pins, the checker prints input_changed and exits 2 instead of scoring.

    2. Build and check a packet of your own

    Read question-2.txt. It has no course packet. From your own ci-dashboard source, create packet-own.txt in week3-work, at most 400 bytes. Copy whole lines, and start each excerpt with a header line that names its file, as packet B does:

    legacy_app/views.py (require_user):
def require_user() -> int:

    Write your prediction for status and limit, then run:

    sh scripts/course-sandbox --profile offline --version VERSION --digest DIGEST --workspace week3-work -- python packet_check.py packet-own.txt

    Expect one line with feedback_only: true, packet_bytes, budget: 400 and a label per part: covered, no_file, browser_only or missing; the notes explain each. The launcher's exit_code is 0 when both parts are covered and 1 otherwise. A packet over 400 bytes is reported as over_budget with no labels, and a file that is not UTF-8 text as unreadable; both exit 2. No model is called. Revise the packet once, run the same command again and keep both outputs.

    3. Generate and check your own pair

    This step is optional. Each command reads its packet, appends the identical question and makes one call through the launcher's prompt-only broker. It exports the raw answer.txt and input-record.json with the packet, question and prompt digests and sizes. It repairs nothing. Use fresh output directories and trace filenames for each packet. Do not reuse an existing trace or output location, since that would obscure the number of calls or overwrite work.

    With your key, from the Week 0 setup values:

    sh scripts/course-sandbox --profile approved-hosted --version HOSTED_VERSION --digest HOSTED_DIGEST --workspace week3-work --model api --hosted-config HOSTED_CONFIG --key-file ~/.config/course/hosted-key --trace week3-a.jsonl --output week3-a-result -- python generate.py a
sh scripts/course-sandbox --profile approved-hosted --version HOSTED_VERSION --digest HOSTED_DIGEST --workspace week3-work --model api --hosted-config HOSTED_CONFIG --key-file ~/.config/course/hosted-key --trace week3-b.jsonl --output week3-b-result -- python generate.py b

    Without a key, the replay route needs no hosted configuration or key file. Replace REPLAY_FILE and REPLAY_DIGEST with the Week 3 record your instructor names:

    sh scripts/course-sandbox --profile approved-hosted --version HOSTED_VERSION --digest HOSTED_DIGEST --workspace week3-work --model replay --replay-file REPLAY_FILE --replay-digest REPLAY_DIGEST --trace week3-a.jsonl --output week3-a-result -- python generate.py a
sh scripts/course-sandbox --profile approved-hosted --version HOSTED_VERSION --digest HOSTED_DIGEST --workspace week3-work --model replay --replay-file REPLAY_FILE --replay-digest REPLAY_DIGEST --trace week3-b.jsonl --output week3-b-result -- python generate.py b

    Until a Week 3 record exists, the launcher refuses the replay command; use the course replay in step 1 as your comparison. To practise the call itself with no key and no record, use the fake model on the offline profile:

    sh scripts/course-sandbox --profile offline --version VERSION --digest DIGEST --workspace week3-work --model fake --trace week3-a-fake.jsonl --output week3-a-fake -- python generate.py a
sh scripts/course-sandbox --profile offline --version VERSION --digest DIGEST --workspace week3-work --model fake --trace week3-b-fake.jsonl --output week3-b-fake -- python generate.py b

    The fake model returns a fixed practice string. The checker reports it as unreadable; it is not a measured answer.

    Check each answer in a fresh launcher invocation. With your editor or file manager, copy the unchanged verify.py into each result directory. Read answer.txt as text first, then:

    sh scripts/course-sandbox --profile offline --version VERSION --digest DIGEST --workspace week3-a-result -- python verify.py answer.txt
sh scripts/course-sandbox --profile offline --version VERSION --digest DIGEST --workspace week3-b-result -- python verify.py answer.txt

    Expect one line with feedback_only: true, a label per field and the number correct. All four correct exits 0; otherwise 1. An answer that is not one JSON object is reported as unreadable. Record each packet's four labels, tokens and latency from the minimal trace; null usage is missing, not zero, and run.cost_status: unknown stays unknown. Never submit environment dumps or unrelated conversation history.

    4. Check a tool definition by calling it

    Read the DRAFT definitions in label_tools.py and write down what you expect each of its four calls to do, then run:

    sh scripts/course-sandbox --profile offline --version VERSION --digest DIGEST --workspace week3-work -- python label_tools.py

    Expect exit_code: 0 and eight JSON lines, four for draft and four for revised. For the draft: search returns names without IDs, a bare delete_label call deletes (label_still_present: false), the unknown ID returns a traceback, and limit: 50 is accepted. For the revision: IDs with total and truncated, a preview that leaves the label present, a not_found error with retryable: false, and an invalid_argument refusal. The example is in memory with synthetic labels; no server, file or network is involved. Explain which of the five rules each row checks.

    The example checks each argument's type before its range, as the workshop's server scaffold would, so a wrong type such as {"query": 5} or "limit": true returns invalid_argument with retryable: false from either version; it never reaches a handler. Only an exception inside a draft handler, such as the unknown ID above, is shown as a traceback entry.

    To make a call of your own, add one row to the tuple in verify() in your week3-work copy, after the four rows already there, and run the same command again:

            ("My call", "search_labels", {"query": 5}, None),

    A row holds a question, the tool's name, the arguments, and the ID of a label to look for after the call (or None). Each row starts from fresh records, and each version prints one more line per row. Keep the four published rows unchanged, so their output still matches the table in the notes.

    5. Watch an agent use both servers

    First predict, for each server, whether the agent carries an ID from a result into its next call, recovers after the ID is not found, and previews before it deletes. Then:

    sh scripts/course-sandbox --profile offline --version VERSION --digest DIGEST --workspace week3-work -- python agent_replay.py
sh scripts/course-sandbox --profile offline --version VERSION --digest DIGEST --workspace week3-work -- python agent_replay.py --ticket-id 9 --summary

    The first line reads agent: course-written policy, not a model. Each server prints the request, every call, every result, the final message and the labels left. With the default ticket ID 21 the draft run ends without deleting anything and the revised run deletes red-team after a preview. --summary adds the three observations as one JSON line per server, computed from the transcript. The tool results are the real outputs of label_tools.py; the agent's choices follow the five rules in policy, which the script steps through one call at a time. It makes no model request. --ticket-id takes any other ID; the activities use 12 and 7.

    When available, a run of the same request with the course's hosted model, recorded by the teaching team one server at a time with at most four model requests each (the launcher's per-run cap), is the comparison. It uses the same transcript format, starts agent: approved model (hosted) and is labelled with its configuration. Read it with the same three questions, including any guessed ID, unusable reply, step_limit stop or deleted wrong label. Until then, the course replay and its tables are the comparison.

    6. Compact a long session, then check

    long-session.json is a 19-message session the course team wrote by hand in the Week 2 message format; no model or agent produced it. compaction.py builds the context the next request would carry in one of four ways, lets a course-written policy pick the next edit from that context alone, and runs the same six-case acceptance check on the result. The notes explain the four modes and the policy's two rules. First read the whole session, with each message's index, role and size:

    sh scripts/course-sandbox --profile offline --version VERSION --digest DIGEST --workspace week3-work -- python compaction.py full --show

    Expect the first line agent: course-written policy, not a model, the 19 messages, then one JSON line with feedback_only: true, mode: full, context_bytes: 5283, budget: 5500, next_edit in status.py with status-strip-lower, and check: passed. Fill the checklist in the activity from this output. Then predict and run the supplied compaction:

    sh scripts/course-sandbox --profile offline --version VERSION --digest DIGEST --workspace week3-work -- python compaction.py auto --show

    The printed context shows which messages became [cleared: ...] stubs. The JSON line lists kept and cleared message indices, policy_found (the first line the policy found for each rule, or null), next_edit, check and each FAIL line. Then write summary.txt in week3-work, at most 600 bytes, and run it both as a compaction and as a restart:

    sh scripts/course-sandbox --profile offline --version VERSION --digest DIGEST --workspace week3-work -- python compaction.py summary summary.txt
sh scripts/course-sandbox --profile offline --version VERSION --digest DIGEST --workspace week3-work -- python compaction.py fresh summary.txt

    summary replaces messages 1-16 with your file and keeps the newest group; fresh keeps only the task and your file. The launcher's exit_code is 0 when the check passes and 1 when it fails. A file over 600 bytes is reported with file_bytes and limit and is not run; a file that is not UTF-8 text is reported as unreadable; both exit 2. No model is called and nothing is written. Revise the summary once if you like, and keep each output.

    Optional: a permission refusal in memory

    This belongs to the optional reading.

    sh scripts/course-sandbox --profile offline --version VERSION --digest DIGEST --workspace week3-work -- python boundary.py

    Expect exit_code: 0 and allowed_read, denied_export, budget_enforced all true. The returned note is inert text. The example uses an in-memory dictionary, no sockets, real files, secrets or external services. Explain why the export request leaves the effect list unchanged, and why editing this Python hook cannot disable the launcher.
