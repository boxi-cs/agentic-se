    Week 3: Context engineering and agent workflows

    Learning objectives

    One idea runs through this week: an agent acts only on what reaches it. You choose the context it reads, the skill descriptions it chooses by, and the tool names, schemas, errors and results it acts on. Each of those choices is something you can test.

    By the end of this lesson you can:

    • LO4: trace one real ci-dashboard request across files and mark each step of a map confirmed, refuted or cannot tell against the source at your revision.
    • LO2: choose the context a bounded question needs: compare two context packets of the same size by what each answer got right, got wrong or left open, then build a packet of your own under a byte budget and check it.
    • LO2 (optional practice): practise compacting a long agent session into a summary under a byte budget, checking that it kept each fact the next step needs, and saying when you would restart from a written handoff instead.
    • LO2: package the tracing method as one SKILL.md whose description you have tested: it fires on the requests it should and not on a near miss.
    • LO2: design tools for an agent that sees only their names, schemas and descriptions, using five rules; verify each rule with calls rather than by reading the definition; and watch how a tool's design changes what an agent does on one request.
    • LO7: keep a destructive tool behind a brake, check a permission before its effect, and say which layer contains a process that ignores both.

    Each activity names the LO it practises; the repository-context workshop's page lists its required parts. Protocol details, a second tool shape (search, then execute), an in-memory permission example, a published MCP incident, and plans, worktrees and subagents are in the optional reading; they carry no marks.

    Run every command through the route in Week 0 setup.

    All examples on this page are course-authored and synthetic; actual execution evidence comes from your own checks.

    Minimal example

    The continuing dashboard case

    Recall the case from Week 1. The dashboard shows a build with raw status " OK " as unknown. The agreed rule ignores surrounding whitespace and case: this input should display passed, while an unfamiliar status should remain unknown. A reviewer suggests editing the template. First inspect this schematic request path:

    # loader.py
raw = record["status"]
# status.py
label = {"ok": "passed"}.get(raw.lower(), "unknown")
# view.py
render(label)

    Decision: Where does the value first disagree with the rule, and which file should the agent inspect before changing the template?

    The loader preserves " OK ". The mapper lowercases it to " ok ", which is not the key "ok", and supplies unknown to the view. Inspect normalization in status.py: removing surrounding whitespace before lookup repairs this case. Changing every unknown display to passed would also mislabel an unfamiliar status. Check both inputs. The path above is a schematic; the next one is real.

    Acceptance decision: Choose a bounded edit only when the path explains the symptom. A single paired run motivates a next experiment; it does not establish that a context style is generally superior.

    A real path: the project list in ci-dashboard

    In ci-dashboard, GET /domains/ci_dashboard/ lists the signed-in user's projects. Trace it across three files:

    1. domains/ci_dashboard.py, function overview: calls require_user(), selects the caller's projects with WHERE owner_id=? ORDER BY id, and renders ci/overview.html.
    2. legacy_app/views.py, function require_user: aborts with 401 when there is no signed-in user, otherwise returns the user's ID.
    3. legacy_app/templates/ci/overview.html: a {% for %} over the projects whose {% else %} branch prints No projects yet.

    The route function names what happens; the other two files decide what a visitor actually sees. A map of this path is a set of claims: each arrow needs a file and line at your checkout revision. The activity's repository map asks you to mark each arrow confirmed, refuted or cannot tell.

    Context is an intervention we can test

    Now ask a model one bounded question about that path, the shared question: what does a visitor without a session receive, what does a signed-in user with no projects see, and which file decides each. It asks for one JSON object and allows null for anything the context does not show.

    Two packets carry the same number of bytes, 639 each; only their content differs:

    Packet What it holds How it was chosen
    A domains/ci_dashboard.py read on from the route, cut at the budget: overview, then the start of new_project Read more of the file you started in
    B The API's 401 line, the overview excerpt, require_user and the template's empty-table branch Follow the call across files

    Predict, generate, then check. Before any run, write what each packet's answer will say for each of the four fields. Keep the model and profile, the question, a fresh call, one call per packet and the checker fixed. Change the packet only. Do not repair a wrong answer or rerun until it passes.

    The checker labels each field correct, wrong, abstained (an explicit null) or missing. Its answers come from the dashboard itself: run with a signed-out client, the route returns 401, and a freshly registered user sees No projects yet.; the course's tests repeat that check against the running app. An abstention is not a correct answer, but it is honest; a confident wrong file is worse.

    A course-written replay, not a model run. To show how the checker reads two answers, the course team wrote one plausible answer per packet by hand. No model was called.

    Packet Status Deciding file Empty-list text Deciding file Correct
    A 302: wrong domains/ci_dashboard.py: wrong null: abstained null: abstained 0 of 4
    B 401: correct legacy_app/views.py: correct No projects yet.: correct domains/ci_dashboard.py: wrong 3 of 4

    Configuration: no model and zero calls per packet; packets of 639 bytes; the question and packet digests are pinned in ab-replay.json, which the checker refuses if any input has changed. Reproduce it with the offline profile:

    sh scripts/course-sandbox --profile offline --version VERSION --digest DIGEST --workspace week3-work -- python verify.py --replay ab-replay.json

    The replay says nothing about how often any model answers either way. Its B answer still gets one field wrong: the route passes the list on, but the template decides the text. Your own pair, made with the commands in the fixture guide, is the measurement; your instructor may also show a pair recorded with the course's hosted model, labelled with its profile, version and digest. A tie, or A beating B, is a legitimate observation.

    AGENTS.md and CLAUDE.md are context-file names discussed in this course. In this exercise we deliberately load the selected packet into the prompt ourselves: no filename has automatic behavior. When adopting a particular tool, verify its actual discovery, scope and precedence rules. A file that exists but was never loaded cannot explain a result. Do not infer that either filename reliably improves performance.

    Build a packet of your own

    Packets A and B were chosen for you. The second question has no course packet. A signed-in user posts a 121-character project title straight to POST /domains/ci_dashboard/projects/new, not through the browser form: what status comes back, what is the longest title the server accepts, and which file decides each?

    Build the packet yourself from your ci-dashboard source, in at most 400 bytes. Quote whole lines, and start each excerpt with a header line that names its file, as packet B does. Before checking, predict for each part, status and limit, whether your packet holds the lines that decide it. The packet check then labels each part without a model:

    Label Meaning
    covered The deciding lines are there, whole and in order, under a header naming their file
    no_file The lines are there, but the header above them does not name their file
    browser_only Limit only: the packet shows the form's limit, which a direct request never meets
    missing A line the answer depends on is not in the packet

    Revise the packet once, within the same budget, and check it again. Keep both results. The check says whether the evidence is in the packet; it cannot say what a model would answer from it.

    Compaction: what survives a shorter history

    A packet is context you choose before the first request. A summary is context you choose in the middle of a session, when the history no longer fits. The Week 2 notes explain what accumulates and what a summary should keep; here you run one before/after comparison and check the summary twice: against the transcript, and by whether the next step still passes the same check.

    long-session.json is a session the course team wrote by hand in the Week 2 message format; no model or agent produced it. The agent is repairing the continuing " OK " case. It reads NOTES.md, view.py, loader.py and status.py, runs the acceptance check, replaces the lookup with raw.strip(), sees the check fail on " OK " and "OK", rereads status.py and reads the check's source. The history is 19 messages and 5,283 bytes against a 5,500-byte budget: this request fits, and the next check result would not.

    compaction.py builds the next request's context in one of four ways:

    Mode The next request carries
    full Every message
    auto The task, every assistant message and the newest call/result group; each older tool result longer than 80 bytes becomes a one-line stub
    summary FILE The task, your summary in place of messages 1-16, and the newest group
    fresh FILE The task and your file only: a restart from a written handoff

    A short course-written policy then picks the next edit from that context alone, and the same six-case check runs on the result. The policy is not a model. It reads every line it is given with the same care, which nothing guarantees of a model, and follows two rules written in the script: it keeps out of view.py only when a line names view.py and says not to change it, and it adds lower() only when a line says the strip-only fix failed. Without the first fact it changes view.py so that unknown displays as passed, which is the template patch the dashboard case warned against.

    Predict, generate, then verify. Fill the checklist from the transcript first: for each fact, the message that holds it. Predict which facts auto keeps and which file the next edit touches, then run it. Write your own summary of at most 600 bytes, predict again, run it as summary and as fresh, and fill the last two columns.

    Fact the next step needs Message in the session Kept by auto Kept by your summary
    The goal and the acceptance check
    The constraint on which file may change, and its source
    The attempt that failed, and how
    The current state of each file touched (which read is stale)
    The paths the next edit needs

    The supplied compaction, run by the course. These are the script's own outputs, with no model involved; run them yourself with the commands in the fixture guide.

    Mode Context bytes Next edit Check
    full 5,283 status.py: raw.strip().lower() passed, 6 of 6
    auto 3,523 view.py: show unknown as passed failed: "queued" shows passed, and view.py changed

    The constraint arrived once, in the middle of a tool result: the NOTES.md read in message 2. Clearing old tool output removed it. The agent's own sentence about the failed strip-only fix survived because assistant messages were kept, so the policy did not repeat that attempt; it made a different mistake instead. Nothing in the compacted context contradicts the view.py edit, which is why this kind of loss is hard to see from the context alone. Your summary's run is your own measurement.

    The check is not the whole verification. Every mode keeps the task message, so the goal and the acceptance check always survive. Of the other facts the policy reads only two, so a summary can pass the check and still leave out which read of status.py is stale, which a later edit would need. The checklist covers what the check cannot. With a model, the same two steps apply, and one run of each version is one observation.

    Compact or restart? Run the same file as fresh: the context drops to the task and your handoff, under 1,000 bytes for a 400-byte file, and the newest raw group goes too. Restart when most of the history is stale or contradicts itself, or a phase has ended; compact when the newest results still matter. Either way the next session's first step is to reread the files its edit touches.

    A skill packages a repeatable procedure

    A skill is a directory with a SKILL.md file: YAML front matter with a name (the directory's name) and a description, then a Markdown body. An agent that supports skills keeps only the names and descriptions in view and loads a body when a request seems to need it, so the description decides whether the skill is ever used. The body then enters the context and costs space for the rest of the session, so hold the procedure there and leave longer background in a separate file in the same directory. The workshop uses exactly this format and asks for three body sections: the steps, the judgement a step list hides, and the check. Hosts differ in optional fields and in where they look for skills; verify that for the agent you use rather than assuming it.

    ---
name: check-label-tools
description: Checks an edited label tool by calling it through the host before the
  change is reported. Use when search_labels or delete_label changed or a call fails.
---
## Steps
1. Read the changed tool definition and predict one call it could break.
2. Run `python label_tools.py` through the course launcher.
3. Make one call of your own with a wrong type, such as `{"query": 5}`.

## Judgement
- If a call you predicted would fail passes, explain why before going on.
- A definition that only mentions `dry_run` is a claim; call the tool to see it.
- If the launcher refuses execution, stop. Do not install dependencies or retry.

## Verification
The `label_tools.py` output matches the table in the notes, and your own call returns
`invalid_argument`.

    Write judgement from your own corrections. A step list hides the moments when someone had to step in. Reread one of your own agent sessions, or your P1 trace, and list each place where you corrected or stopped the agent. Each correction is a candidate line for ## Judgement, because the next run will need it too.

    Generate, then verify the trigger. A description that says only when ("Use when changing the label tools") can miss "why does search give me no IDs?". One that says only what can fire on every label question. So test it like any other prediction: write three requests in the words people use that should load the skill, and one near miss that sounds similar but needs something else ("rename the label column"). Record your prediction for each before you observe, then observe with an agent session or a classmate who sees only the names and descriptions of the available skills. A near miss that fires means the description is too broad; a missed request usually shares no words with it. Change the description once and recheck only the mismatches.

    A context file states project-wide constraints. A skill describes a reusable procedure and its trigger. Neither grants permissions, and any script a skill refers to is code that needs review and launcher execution. In the workshop you write one skill for the tracing method you practiced by hand, trigger-test it, use it once on ci-dashboard and once, read-only, on your candidate contribution project (or a listed repository if you have no candidate yet), and record what changed. A skill nobody has run is a draft.

    A tool is an interface for a reader that guesses

    MCP (Model Context Protocol) connects an agent's host to servers that expose tools. The agent sees each tool's name, description and input schema, calls it with arguments, and reads the result as data, even when the result asks for something. Whether a tool is reached through MCP or a plain function call, the agent chooses it from that text alone. Design it for a reader that will guess when the text is unclear. Name the effect, not the implementation: search_labels, not handler2. Give the tool no authority beyond its stated purpose. Five rules turn that into checks:

    1. Put every limit in the schema. "enum", "minimum", "maximum", "required" and "additionalProperties": false tell the agent every valid value, and they are checked before your code runs when the server validates each call against the schema, as the workshop's server scaffold does. A limit stated only in a sentence of the description is neither visible as a value list nor checked. When the two disagree, the agent meets rejections that nothing it read accounts for. The MCP specification puts input validation on the server: servers must validate all tool inputs. (tools/model-context-protocol; as_of: 2026-10-09; Source 1; Source 2) It is a requirement on the server, not a guarantee that a given server meets it, so check with a call.
    2. Return only what the next step needs. Hand back the fields the next call will use, including the IDs other tools accept, not the stored record. Every extra field is paid for again at each later step, and mirroring the storage layout breaks the tool when that layout changes. If you cut a list short, say so. Anthropic's tool-writing guide gives the same advice: return high-signal fields, and bound large responses with pagination, filtering or truncation and sensible defaults. (tools/anthropic-effective-tools; as_of: 2026-10-09; Source 1)
    3. Report a failure as a result the agent can read. Return a structured error naming what failed and whether trying again could succeed: an unknown ID fails every time, a rate limit clears. A raw exception gives the agent nothing to act on; {"code": "not_found", "retryable": false, ...} tells it whether a retry is worth making. MCP draws this line too: an unknown tool or a malformed request is a protocol error, but a failed input check, such as a value out of range, is a tool execution error, returned in the result with isError: true so the client can hand it to the model to correct. (tools/model-context-protocol; as_of: 2026-10-09; Source 1; Source 2)
    4. Say what comes back and where each input comes from. State what the tool returns and which tool produces each ID argument ("a label_id from search_labels"), so the agent can call them in sequence. Name arguments so they cannot be misread: label_id, not label. (tools/anthropic-effective-tools; as_of: 2026-10-09; Source 1)
    5. Guard every irreversible action. Mark the read-only tools as read-only. Give an irreversible tool a dry_run that defaults to true, or split it into preview and commit, so a call that leaves the argument out cannot change anything.

    Generate. Below is a course-authored first draft for the request "a search tool and a delete tool for labels", written the way a quick generated answer can look. It looks finished, and it works when the caller already knows the answers.

    [{"name": "search_labels", "description": "Search labels. limit can be up to 50.",
  "inputSchema": {"type": "object",
                  "properties": {"query": {"type": "string"}, "limit": {"type": "integer"}}}},
 {"name": "delete_label", "description": "Deletes a label.",
  "inputSchema": {"type": "object", "properties": {"label_id": {"type": "integer"}}}}]

    Before reading on, predict what each call in the table does to the draft.

    Verify. Reading the definition is not verification; calls are. The worked example applies the published schema as the workshop's server scaffold would: it refuses an unknown or missing argument and checks each argument's type, then its range (true is not an integer), all before the handler runs. It then makes the same four calls against the draft and a revision, each from fresh records. These are its actual outputs, shortened:

    Question Call Draft Revision
    Can the agent chain? search_labels {"query": "red"} ["red-blue", "red-team"]: names, no IDs to pass on label_id and name per label, total, truncated
    Does a bare delete only preview? delete_label {"label_id": 7} Deleted; label gone dry_run: true, would_delete; label still there
    Is a bad ID recoverable? delete_label {"label_id": 99} KeyError: 99 traceback not_found, retryable: false, "use search_labels"
    Does the schema hold? search_labels {"query": "r", "limit": 50} Accepted: the "up to 50" lives only in prose invalid_argument from "maximum": 10

    The revision bounds limit (minimum 1, maximum 10, default 5), adds "required" and "additionalProperties": false to both tools, and gives descriptions that name search_labels as the source of label_id, readOnlyHint: true on the reader and destructiveHint: true with a dry_run defaulting to true on the delete. Each row is a check you can rerun; a new rule needs a new call, not a longer description. The workshop applies the same five rules to a different, four-tool ci-dashboard server, and there your own test must make its calls through the protocol, not by importing the handlers.

    Watch an agent use both servers

    The table checks one call at a time. An agent chains calls, so give one request to an agent twice, once with each server:

    Delete the label red-team. An old ticket gives its label_id as 21.

    There is no label 21; red-team is label 12. Before you look, predict three things for each server: does the agent carry an ID from one result into its next call, does it recover after the ID is not found, and does it preview before it deletes?

    The replay steps a fixed policy through each server: the policy picks a call, the tool returns its result, and the policy picks again. The agent is course-written, not a model: five rules, the same for both servers, that never guess an ID. First use the ID the request gives. After a preview of the requested label, commit it. After a delete that deleted something, report it. After any other delete result, look the label up by name once. After a search, delete the ID found for that name, or stop if there is none. Every tool result in the transcript is the real output of label_tools.py.

    Draft server Revised server
    Call 1: delete_label {"label_id": 21} {"traceback": "KeyError: 21"} not_found, retryable: false, "use search_labels"
    Call 2: search_labels {"query": "red-team"} ["red-team"]: a name, no ID {"label_id": 12, "name": "red-team"}
    Call 3 None: the agent stops, "no label_id ... I will not guess one" delete_label {"label_id": 12} returns a preview, would_delete
    Call 4 delete_label {"label_id": 12, "dry_run": false} deletes red-team
    Carried an ID from a result No: the search returned none Yes: 12, from the search into the delete
    Recovered after not found No: nothing was deleted Yes
    Previewed before deleting No: call 1 would have deleted label 21 at once Yes: the bare call only previewed

    Now change the ticket's ID to 9 (--ticket-id 9), which is the label release-2. On the draft, the first call deletes release-2 immediately and the agent can only report it. On the revision the same call returns a preview of release-2; the agent sees the name does not match, searches, and deletes red-team after its own preview. The brake did not make the agent smarter. It turned a wrong call into a result the agent could read. --summary prints the three observations; it names the second recovered_from_the_wrong_id, which is true when the first delete hit a missing label or a different one and the run still deleted exactly red-team, so it covers both ticket IDs.

    The rules are ours, so the replay shows what the tool design allows, not what a model will do. A model may guess an ID, retry a traceback or ignore an error's message. When available, your instructor shows a run of the same request recorded with the course's hosted model, labelled with its configuration, in the same transcript format; until then, the course replay and its tables are the comparison. A recorded run makes at most four model requests per server, the launcher's per-run cap, so a model that needs a fifth reply stops with step_limit after its fourth reply's calls have run. Compare its transcript with your three predictions, call by call.

    Brakes, hooks and the sandbox

    Three layers keep a wrong call from doing harm, and each covers something different. A tool's brake, such as dry_run defaulting to true, makes a call that omits the argument harmless. A pre-call hook checks an event, such as a write path, before the effect happens; the workshop's hook step allows an ordinary edit and rejects an escape. Neither can contain a process that edits or ignores them. The course launcher does that, with copied inputs, no external network and fixed resources. A hook that logs a bad action after it happened has prevented nothing. The optional reading has an in-memory example of a returned note asking for export.

    For each row, ask the same question of the recording: where does this show up, and what does the record leave out? A context file that exists in the repository but that the record does not show being loaded cannot explain what the agent did.

    Label the final summary. The agent's closing message is a list of claims, just like the arrows of your repository map. Split it into single claims, then label each one against the record:

    • confirmed: an event in the record shows it; cite the event;
    • refuted: an event in the record shows something else; cite it;
    • cannot tell: no event decides it; say what you would read or run.

    Then check every claim again, separately, against the source at your revision, through the launcher where a check needs running. Keep the two labels apart. "Cannot tell" from the record is not "false": the code may well agree. A claim confirmed by the record can still be wrong about the code if the agent read a different revision. For example, take a summary that says "I fixed the bug and all tests pass". If the last test command in the record fails, "all tests pass" is refuted. If the record holds no test command at all, it is cannot tell: name the command you would run, then run it.

    Generate, then verify. The agent generated the run and its summary. Before you read the record, predict which claims it will support. Afterwards, label every claim and rerun one check yourself. The point is the same as in the replay: a mature agent's run is evidence, and its summary is a claim about that evidence.

    Verification

    The fixture guide gives the supported launcher commands.

    For the context comparison, check that both packets are 639 bytes and that the replay command reports kind: course-synthesised, then a with 0 of 4 and b with 3 of 4. For your own pair, compare the two input-record.json files: same question digest, different packet digests, equal packet_bytes, one call and no repair each. Then check each answer.txt with verify.py in a fresh launcher invocation and report the four field labels, input/output tokens and latency from the minimal trace, keeping missing usage or unknown cost unknown. An unreadable answer, a timeout or a missing report is a failed or unfinished attempt. Preserve order and configuration so that a follow-up can repeat or reverse the pair.

    For your own packet, keep the prediction, the packet and the check's output from before and after the one revision. Each run reports packet_bytes within the 400-byte budget and a label per part; a packet over the budget is reported as over_budget and not labelled. Explain any part whose label differs from your prediction from the lines in the packet.

    For the compaction comparison, the first line must read agent: course-written policy, not a model. full reports context_bytes: 5283 of budget: 5500 and passes; auto lists message 2 under cleared, edits view.py and fails with two FAIL lines.     For the skill, check the structure, then the trigger record: three should-trigger prompts that do not name the skill, at least one near miss, a prediction written before each observation, and a recheck of every mismatch after one description change. A trigger test records what an observer did; it cannot prove the skill fires for every phrasing, and an empty mismatch list is not a better grade than an honest one.

    For the tools, run the worked example and confirm each of the four rows for both versions. A rule counts as verified only when a call shows it: the preview leaves the label in place, the bad ID returns retryable: false, the out-of-range limit is refused before the handler runs. Add a call of your own with a wrong type, such as {"query": 5}, as a row in verify() (fixture guide, step 4): both versions should refuse it with invalid_argument, not a traceback. A definition that merely contains dry_run or readOnlyHint is a claim, not evidence.

    For the agent replay, the first line must read agent: course-written policy, not a model. Check your three predictions against the transcript, then against --summary, which prints the same three observations computed from the calls and the labels left. When available, the teaching team's recorded model run starts agent: approved model (hosted); read it with the same three questions. Until then, the replay and its tables are the comparison. For LO7, confirm from the transcript that the revised server's bare delete left red-team in place until the explicit dry_run: false, and explain which layer would contain a process that ignored both the brake and the hook.

    For a mature agent's run, each claim of the final summary carries two labels, one from the record and one from the source at your revision, and every confirmed or refuted label cites the event or line that decides it.     Common mistakes

    Mistake How to detect it Correction
    Calling B "better" before running Prediction appears as a measured conclusion Keep prediction and observed results in separate columns
    Changing more than the packet packet_bytes, model or profile differ between the two records Hold everything but the packet's content fixed, then rerun both
    Judging an answer against the other packet's answer "B said 401, so A is wrong" Check each answer against the code with the checker
    Quoting the right lines without their file packet_check.py reports no_file Start each excerpt with a header line that names its file
    Counting a null as correct, or a confident guess as better than a null Abstained and wrong fields are merged Keep the four labels separate
    Retrying until the answer passes More than one call or an unlabelled repair Record failure; label any later run separately
    Reading the replay agent as a model "The agent learned to search" Its rules are course-written; only a recorded model run, when available, shows a model
    Trusting a summary because the next check passed The checklist has an empty cell in the summary column Check each fact against the transcript as well as rerunning the check
    Naming a file loosely in a summary "Do not edit the template" without view.py; the next edit lands in view.py Write the path the next edit would use
    A description that says only when, or only what Requests in users' words never load it, or a near miss does Say what it does and when; rerun the trigger prompts
    A limit or allowed value stated only in prose An out-of-range call is accepted Move it into the schema; call with the bad value again
    Returning the stored record Large responses, fields no step uses, no IDs to chain Return the documented fields and the IDs other tools accept
    A traceback or bare string as the error The agent cannot tell retry from stop Return code, retryable and an actionable message
    A destructive tool that acts on a bare call Omitting dry_run changes state Default dry_run to true; check the state after the call
    Testing tools by importing the handlers The test still passes when the protocol layer breaks Call through the protocol, as the agent will
    Treating a mature agent's summary as its own evidence A claim is labelled confirmed with no event cited Cite the event that shows it, or label it cannot tell
    Counting a context file in the repository as context the run used AGENTS.md or a steering file is cited, but the record never shows it loaded Name the event that loads it, or say the record leaves it out
    Reading "no file-change event" as "no file changed" The summary says nothing changed, but the record ran a shell command Check what each command writes, in the source or by running it in the launcher
