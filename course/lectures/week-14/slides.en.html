    Demonstrate and defend the result

    This page describes the earlier fourteen-week layout and is being rewritten; where it differs, the syllabus applies.

    Week 14 · CI dashboard

    Can you explain why this feature deserves confidence?

    The final conversation follows the work

    Your feature began with a user need, then acquired code, tests, an evaluator, recovery evidence and review.

    The demonstration connects those decisions. The individual defense asks you to reason without outsourcing the answer.

    One claim small enough to defend

    For the tested role/archive combinations, archived builds remain unchanged when an edit is requested.

    This names a behavior and a checked scope. "The application is secure" would need far more evidence.

    Four evidence locations in your existing work

    Discussion area Work to locate
    Requirement and user need M0 criterion and authorized discovery
    Evaluation M2 contract, scorer and result scope
    Security M1 regressions and M3/M4 audit response
    Deployment and recovery M2 event chain, rollback and recovery checks

    Use references to the same artifacts. Do not create a new evidence portfolio.

    A complete public practice packet

    Policy: edit only if owner or staff, and not archived. Week 6's earlier guard, is_owner or is_staff and not archived, let an archived owner edit. The repaired guard groups the roles:

    allowed = (is_owner or is_staff) and not archived
if allowed:
    title = requested_title

    Inputs are booleans. Guest means neither owner nor staff.

    The supplied evidence matrix

    Case on the repaired guard Decision Title after request
    Active owner Allow New
    Active staff Allow New
    Archived owner Deny Old
    Archived staff Deny Old

    Synthetic practice evidence. Guest cases are absent from this matrix.

    A new role in the question

    A guest requests the same edit on an active build.

    Predict the guard's value and required title. Which part is code reasoning, and which part needs an observed check?

    Explanation can be precise about a gap

    For a guest, both role booleans are false: predict denial and unchanged title.

    The given matrix has not observed that case. Add an active-guest request and assert both response and unchanged state.

    This supports a next check without pretending it already ran.

    Mechanism: A claim that can survive a question

    Each link points to work you already have. A changed input either reuses an observation or names the next check.

    A causal explanation of one change

    Need: protect archived records
Cause: old expression let owner bypass archive condition
Change: apply archive condition to both role paths
Check: archived owner is denied and title remains Old
Limit: name the checked revision and routes

    Point to your own source and actual evidence for the real defense.

    Requirement variation

    A new request lets staff edit archived builds; owners who are not staff still may not.

    Which policy clause and cases change? Which old evidence is still relevant? Answer from the new requirement before proposing code.

    Evaluation variation

    The question changes from "is the status exactly failed?" to "did the build finish without passing?", and canceled builds now appear. The gate still reports its earlier passing cases.

    Which expected answers, cases and earlier results change?

    Recovery variation

    A rollback command reports success. No request has reached the service since.

    Name two possible states of the running service and the observation that separates them. Do not infer "recovered" from the command's message alone.

    A demonstration the audience can follow

    Show the user task, one visible behavior and the verification that supports it. Then explain one decision and a remaining limitation.

    Identify the running revision. Label a recording or fallback by its actual source. The scheduled demo format and defense remain in the course instructions.

    When a demonstration fails

    Preserve the actual failure and identify the next observation. Use a labelled recording if the announced format permits it.

    A prepared screenshot cannot establish that the current candidate works. A missing observation can be explained clearly without inventing a pass.

    Calibration without invented causality

    Reopen your Week 1 calibration report beside the times you recorded in the project workshops. Do you still underestimate, relative to each prediction? Explain one concrete mismatch.

    A later task done faster may also differ in difficulty, familiarity and prior practice. The difference alone does not isolate an agent's productivity effect.

    The software factory is a claim to test

    Definition: a repeatable process that organizes requirements, generation, verification and delivery.

    Claim to test: its stages could run with little human input.

    Test it on the pipeline you know: specify, change, test, evaluate, protect, deploy and recover, audit. For each stage: could it run unattended, and what evidence comes first?

    An agent's change: merge it unattended?

    The agent rewrites evaluator.py and replies:

    Made scoring robust to formatting. Answers are trimmed and lower-cased, and an answer that starts with the expected word now counts.

    Predict the regression gate's exit code before the run.

    Course-authored replay in fixture/proposed_evaluator.py. No model wrote it.

    Run the gate on the change

    cp lectures/week-14/fixture/proposed_evaluator.py week14-gate/evaluator.py
sh evals/evaluator-kit/run-regression.sh --profile offline \
  --version "$week14_version" --digest "$week14_digest" \
  --workspace week14-gate

    Then copy back evaluator.py from the fixture and run the identical command.

    Setup first (workspace, verify.py, profile variables): fixture README.

    A gate that has been seen to fail

    {"cases": 9, "failed": [
  {"case": "extra_text", "observed": "pass", "required": "fail"},
  {"case": "case_changed", "observed": "pass", "required": "fail"}]}

    Proposal: gate exit 1. Current evaluator: gate exit 0, nothing failed. "Robust" meant accepting yes; mark this as passed.

    Evaluate: a candidate, not yet unattended

    Seen to fail on a bad change and pass on a good one. Still missing, at least:

    Each scoring escape becomes a new case; an escape from the checker needs the separate process.

    Could the model audit run unattended?

    Course-synthesised M3 record Count
    Findings 9
    Confirmed 4
    Refuted 3
    Cannot tell 2
    Missed, found by the student's own check 1

    In class, replace these counts with your own M3 record.

    Claims are not checks

    Acting on every finding unattended: 3 changes with no defect, 2 actions on cannot-tell findings, 1 defect still shipped.

    The audit can run unattended as a source of hypotheses. Its confirmed findings become tests, and those tests can join the gate.

    A check never seen to fail is not yet evidence that it would stop a bad change.

    Judge three stages of your own pipeline

    For each stage: unattended now, or not yet? Cite the evidence by its existing reference. Name the check or stop rule that would change your answer.

    Use your own M3 counts for the Audit stage. A partner challenges one stage you marked unattended.

    Before an agent runs after deployment

    Who can stop it? A named person; a stop that needs no deploy and no cooperation. What may it change? Permitted actions granted in one place, per-run caps, approval for irreversible steps. How is it observed? A minimal record, alerts on refusals, frozen evaluator cases rerun.

    Test each answer. One you cannot answer means that stage needs a person.

    Rehearsal with a partner

    Locate one evidence reference in each discussion area. Rehearse one concise claim, then let a peer change an input or condition.

    Answer the variation independently and revise an unsupported claim. These are public practice prompts, not the private defense bank.

    Exit: what you can now explain

    Choose one changed decision from your own project.

    What did you first expect? Which observation changed your mind? What would make you revisit the decision again?

    The expo and your defense

    At the expo, demonstrate the final product and its evidence from your submitted M4 revision: M4 in the project guide.

    Attend your individually scheduled defense; the expo does not replace it.

    The final calibration is feedback. It adds no separate reflection report.
