    Week 14: Demonstrate and defend the result

    Learning objectives

    Rehearse one engineering claim with visible verification, then explain a new input or failure independently. Explain the reasoning independently (LO1, LO2, LO3, LO4, LO5, LO6, LO7, LO8, LO9).

    All examples, counts and files on this page are course-authored synthetic practice.

    Minimal example

    A public defense practice packet

    The agreed policy permits an edit exactly when owner or staff is true and archived is false. Guest means both role booleans are false. The packet continues the Week 6 dashboard case, whose earlier guard, is_owner or is_staff and not archived, let an archived owner edit. The repaired guard groups the two roles:

    allowed = (is_owner or is_staff) and not archived
if allowed:
    title = requested_title

    The supplied synthetic evidence matrix contains active owner/allow/New, active staff/allow/New, archived owner/deny/Old and archived staff/deny/Old. Guest cases are absent. Predict an active guest's decision and final title before reading on.

    The code predicts denial and unchanged title for a guest, but the provided matrix has not observed it. State that distinction and propose the guest request with both response and state assertions. If those checks then complete on the repaired guard, acceptance can extend to those checked cases. A phrase such as "all permission boundaries are safe" would exceed this packet. These are public formative prompts, not the defense bank.

    Explain the cause, not only the result

    A concise account links a user need to a source change, discriminating check and revision: archived content needs protection; the old owner term bypassed archive; the new grouping applies archive to both roles; the archived-owner regression checks denial and unchanged state. Use actual references to your own work in the defense. A complete spoken explanation does not create missing evidence.

    Locate the existing work across the required areas

    Discussion area Existing work to locate Public practice variation
    Requirements/acceptance M0 need, consented discovery and criterion Staff may now edit archived builds; owners who are not staff still may not. Which cases change?
    Evaluation M2 task/environment/agent/scorer and declared outcomes The question changes from "is the status exactly failed?" to "did the build finish without passing?", and the environment now includes canceled builds. Which oracle, cases and earlier results change?
    Security M1 regressions and M3/M4 audit response Add a guest input and check both response and state.
    Deployment/recovery M2 event chain, rollback and recovery assertions A rollback command reports success, and no request has reached the service since. Which states of the running service remain possible?

    A changed question needs a new accepted contract and corresponding scorer cases: canceled now requires yes, running still requires no, and an earlier pass remains evidence for the old question only. A rollback's success message describes the command, not the running service: the previous revision may be serving, or the faulty revision may still be serving. Observe the running service itself, then one user request, before declaring recovery. A changed role policy requires its own authorization and cases rather than silently rewriting the previous expectations. The student answers new variations independently.

    A demonstration with an honest fallback

    Your M4 demonstration takes place at the expo in the Week 14 workshop. Everyone demonstrates at the same time while staff and classmates move between stations and ask questions, and each student answers at least one staff question. The M4 section of the project guide says what to demonstrate. The expo does not replace your individually scheduled defense.

    Show one user task, its visible behavior and the check that supports it. Identify the actual revision and explain a decision and remaining limit. If the live path fails, retain that result and state the next observation; use a labelled recording only if the announced format permits it. Do not relabel an older result as current.

    A later task taking less time than an earlier one does not isolate an agent's productivity effect: difficulty, familiarity and prior practice may differ. Explain a prediction mismatch from your actual work without inventing causal measurement.

    The software factory is a claim to test

    A software factory is an engineering concept that organizes requirements, generation, verification and delivery into a repeatable production process. This lecture tests the stronger claim that its stages could run with little human input. Treat that as a claim, not a conclusion. You can test it on the one pipeline you know in detail: your own ci-dashboard work. Split the pipeline into stages. For each stage, ask whether it could run unattended and what evidence would be needed first.

    Stage Course evidence you already hold What must be shown before the stage runs unattended
    Specify M0 acceptance criteria; the user tests begun in Week 11 The criteria were executable, and the user tests found no need they missed
    Change M1 reviewed change; P2 review Review checks find the faults a person found, on changes that the reviewer did not author
    Test Week 7 surviving mutant, property and fuzz input The tests fail on meaningful faults, not only on the cases they were written for
    Evaluate M2 evaluator challenged in Week 10 The scorer has been challenged and still holds; Unknown is never counted as a pass
    Protect M1 security regressions from Week 8 The inert attack stays blocked and permitted work still succeeds
    Deploy and recover M2 incident drill from Week 11 Rollback and the recovery check, including the user's view, run without a person
    Audit Your verification of the teaching team's model audit on your frozen snapshot, M4 responses Each finding is marked confirmed, refuted or cannot tell with evidence, and no confirmed finding is one your own checks should have caught

    A gate that has been seen to fail

    The Evaluate stage already has an executable gate: run-regression.sh from the evaluator kit, the local gate from the M2 evaluator workshop. It copies only evaluator.py and verify.py into a fresh workspace, runs verify.py through the launcher and exits with the candidate's status. The lecture runs it on the Week 14 fixture: an evaluator for the Week 10 contract, "is a supplied status exactly failed?", and nine frozen cases.

    Generation: an agent proposes a change to the evaluator. The proposal, proposed_evaluator.py, is a course-authored replay; no model wrote it. Its reply says: "Made scoring robust to formatting. Answers are trimmed and lower-cased, and an answer that starts with the expected word now counts." Would an unattended pipeline merge it? Predict the gate's exit code before the run.

    Verification: the instructor runs the gate on the proposal and then on the current evaluator, with the commands in the fixture README. With the proposal, the launcher record shows "exit_code": 1, the gate exits 1, and the record's stdout names the cases that failed:

    {"cases": 9, "failed": [{"case": "extra_text", "observed": "pass", "required": "fail"}, {"case": "case_changed", "observed": "pass", "required": "fail"}]}

    With the current evaluator the gate exits 0 and the failed list is empty. The proposal made formatting "robust" by accepting yes; mark this as passed, the Week 10 answer that tried to talk the scorer into a pass. The gate stopped it because a frozen case had been written for exactly that answer. If the record shows the launcher's generic "status": "failed" instead, the launcher refused the run: keep that result, and do not count it as the gate catching anything.

    A stage runs unattended only with two kinds of evidence: a check seen to fail on a bad change and pass on a good one, run from cases the changing agent cannot edit, with the candidate scored in a separate process, and a stop path that someone has exercised. The demonstration shows the check failing and passing, but in a pipeline the cases would sit where the agent could edit them, the candidate runs inside the checker, and the stop path is untried. So the Evaluate stage is a candidate for merging evaluator changes unattended, not yet unattended. At least three things are still missing:

    • Cases the changing agent cannot edit. The gate copies verify.py from the same workspace as the candidate. In the demonstration it came from the fixture, which the replayed change did not touch. An agent that can rewrite the cases can make any change pass, so the gate must read verify.py from a location the agent cannot write, not from the candidate's workspace.
    • A candidate scored in its own process. verify.py imports the candidate and calls it in the same process. The candidate runs inside the process that checks it, so it can end the run or print its own report. An unattended gate must score the candidate in a separate process and treat that process's output only as data.
    • The stop rule exercised once. The stop rules say that any failed case, any refused cap or any rollback stops the agent and pages its owner. Someone has to see a failed gate run actually halt the merge and reach the owner; naming the rule is not exercising it.

    The nine cases also have a limit. A change that only trims spaces (output.strip() == expected) passes all nine, although the contract makes " yes" a fail. If that matters, " yes" becomes the tenth frozen case. Each new scoring escape becomes a new case. An escape from the checker itself, such as ending the run early, needs the separate process above, not another case. The optional step in the fixture README lets you see this: write the trim-only change, watch the nine cases pass it, add " yes" as a tenth case and watch the gate stop it while the current evaluator still passes.

    Could the model audit run unattended?

    Ask the same question of the Audit stage. This course-synthesised record stands in for one student's M3 verification of a model audit on one frozen snapshot:

    Course-synthesised M3 record Count
    Findings in the model audit 9
    Confirmed with a failing test or a repeatable reproduction 4
    Refuted with runnable evidence 3
    Cannot tell (undetermined): a named input is missing 2
    Defects the student's own check found and the audit missed 1

    By Week 14 you hold your own M3 record. In class, replace these counts with yours: how many findings you confirmed, refuted or marked cannot tell, and whether your own check found something the audit missed.

    The software-factory claim is that stages could run with little human input. Suppose an agent had acted on every audit finding unattended. It would have changed code for 3 findings with no defect behind them, acted on 2 cannot-tell findings that nothing observed, and still shipped the 1 defect the audit missed. Unlike the gate, the audit has not been seen to fail and pass on known inputs; its output is a set of claims that become evidence only when someone runs a check. So the audit can run unattended as a source of hypotheses on every snapshot, but not yet as a stage that changes code or blocks a merge on its own word. The two stages connect: each confirmed finding becomes a test that fails before its repair, and that test can join the gate.

    The useful outcome is a bounded claim, such as "evaluator changes: a candidate for unattended merging behind this gate once its cases sit where the agent cannot write, the candidate is scored in a separate process and the stop rule has been exercised; audit findings verified before anything changes". It is not a yes or no about factories in general. A check that has never been seen to fail is not yet evidence that it would stop a bad change, and a stop rule that nobody has exercised is not yet a stop.

    Operating an agent after deployment

    Week 11 introduced agents that keep running after deployment. Before such an agent runs unattended, answer three questions with something you can test.

    • Who can stop it? A named person, and a stop that works without a deploy and without the agent's cooperation. The launcher does this when it destroys a container at a cap or deadline. Test it: stop the agent midway and check that no partial effect remains. That is the same idempotency question as a retried request.
    • What may it change? A list of permitted actions and paths, granted in one place, with per-run caps. Irreversible operations wait for a person's approval.
    • How is it observed? A minimal record of what it read, proposed and changed, and an alert when a cap refuses it. Rerun the frozen evaluator cases on a schedule: a hosted model's name does not guarantee unchanged behavior over time.

    If you cannot answer one of these for a stage of your pipeline, that stage needs a person.

    Hands-on exercise

    Locate one existing evidence reference in each required discussion area. Rehearse a concise causal claim and answer a partner's changed condition independently.

    Use the activity for feedback and revision; no additional report.

    Final calibration

    Your calibration notes are one short "Final calibration" entry in your existing work record, beside your M4 delivery record. They are not a new file or report, and they carry no mark. The entry has three parts.

    1. Week 1 against now. Reopen the report you produced in Week 1, week01-calibration-report.json, and the explanation you kept with it. From its overall block, copy count, mean_actual_minus_predicted_minutes and pass_prediction_error_rate. Then collect the predicted and actual times you recorded in the project workshops and compute the same signed error, actual minus predicted, for each. Workshop tasks are far longer than the Week 1 tasks, so compare each error with its own prediction: an error of 10 minutes on a 5-minute prediction is larger than one on a 3-hour prediction. Do you still underestimate, and has the error shrunk relative to the prediction? Explain one mismatch from your own records, such as a requirement you missed, setup or waiting, without attributing it to an agent. A time you never recorded stays missing; do not estimate it now. If no Week 1 attempt completed, say so and compare the workshop times alone.
    2. The software-factory judgment. Pick three stages from the table. For each, write whether it could run unattended now, cite the evidence by its existing reference, and name the check or stop rule that would change your answer. If you pick the Audit stage, use your own M3 counts in place of the synthetic record. Let a partner challenge one stage you marked unattended.
    3. One revised claim. The unsupported claim you revised in the workshop, with the observation that changed it.

    Leave week01-calibration/calibration.csv as it is. It holds only the calibration controller's Week 1 attempts, and its validator rejects any other row, so the workshop times belong in this entry, not in the CSV.

    Verification

    Distinguish a hand prediction from an actual completed check. Present only the verified scope and explain the next observation needed for a new input.

    All execution follows Week 0 setup. The classroom packet is authored practice; actual runs and participants need their own evidence.

    For the Week 1 comparison, check that the numbers you copied still follow from the unchanged record. From the course root or unpacked student ZIP, with your Week 1 session directory:

    uv run --locked python tools/validate_calibration_log.py \
  week01-calibration/calibration.csv
uv run --locked python tools/calibration_report.py \
  week01-calibration/calibration.csv --out week14-calibration-recheck.json

    Expected evidence: the validator reports a valid log with the same row count as in Week 1, and the overall block of the new report matches the one you copied. The report destination must be a new file. If the blocks differ, the record changed after Week 1: keep both reports and note the difference rather than choosing the better one. If the validator refuses the record, keep its message, which names what no longer matches, and compare with the Week 1 report you already hold.

    For the software-factory judgment, check each stage you marked unattended. Its evidence must include a check you have seen fail on a bad input and pass on a good one, run from cases the changing agent cannot edit, with the candidate scored in a separate process, and a stop path that someone has exercised. A stage supported only by passing runs is "not yet", however many passes there are.

    The gate demonstration is the worked case for the failing and passing check. Command: run-regression.sh on the workspace that holds the proposal, as in the fixture README. Expected evidence: gate exit 1, with extra_text and case_changed in the record's stdout, then gate exit 0 on the current evaluator. Failure case: a record that shows the launcher's generic "status": "failed" is a refused launcher run; it neither passes the change nor shows that the gate caught it. Even with both real runs, the Evaluate stage stays "candidate, not yet unattended" until the gate reads verify.py from a location the agent cannot write, scores the candidate in a separate process, and the stop rule has been exercised once.

    Common mistakes

    A good prepared demo does not establish every path. A failed live attempt does not disappear when an older recording is shown. Work with others does not replace individual explanation.

    Mistake Better next action
    Answering "can agents run software unattended?" in general Judge one stage of your own pipeline against its evidence
    Citing green runs as proof that a check would stop a bad change Show the check failing on a deliberately bad input first
    Treating an audit finding as a one-off fix Ask which unattended stage would have let it through
    Judging the Audit stage by how many findings the model produced Count confirmed, refuted and cannot-tell findings, plus what your own check found that the audit missed
    Counting a refused launcher run as a caught change Keep it labelled as a refused run and rerun until the record has an exit_code
    Calling a stage unattended because its check failed once on a bad change Run the check from cases the changing agent cannot edit, score the candidate in a separate process, and exercise the stop rule once
    Naming an off switch nobody has tried Stop the agent midway once and check that no partial effect remains
    Filling in a workshop time you never recorded, or adding it to the Week 1 CSV Mark the time missing and compare only the times you recorded, in the final calibration entry
