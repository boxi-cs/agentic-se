    Week 8: Security: refuse before effects

    Learning objectives

    This week has one main line: text an agent reads is data, not authority, so permission is decided before any effect and verified in both directions. By the end of the lesson, you can:

    LO Observable action Practice and self-check
    LO7 Trace an inert request through the boundary, keep refused and unlisted calls effect-free, harden an agent policy, and separate approval from launcher containment Workshop route and replay; questions 1 to 11
    LO5 Verify a repair in both directions, triage scanner findings as claims with observations, and record one agent claim that was wrong Triage drill; questions 2, 8, 10, 12 and 13

    Use the slides, workshop and self-check together. Foundation refreshers remain optional; they do not create an extra assignment or require prior specialist coursework.

    Minimal example

    The continuing dashboard case

    A log asks an agent to enable export, although only a label read is authorized. The public in-memory boundary below records a synthetic effect and returns a response. Use its exact contract and candidate to decide whether permission is checked early enough. The same text can arrive through each supplied surface; no actual export is implemented. Predict response and effects before opening the worked result.

    Fix the contract before inspecting the proposal

    A request has exactly two string fields, tool and record. The record names one of three supplied synthetic surfaces. Only read_label is permitted. Malformed requests return invalid_arguments; other tool names return tool_denied. Refused calls must not append an effect. Every attempted call consumes one of two attempts, including invalid and denied requests. A third call returns budget_exhausted without any new effect.

    Predict before running

    Read candidate.py as text. Before execution, record one input, its required result and what the starter is likely to do. Inspect exercise.py to identify how the public checks distinguish the two.

    Worked result. The same passive note arrives as repository text, a tool response or a copied log. Its request to enable export is data, not authority. The starter returns the right denial message but appends export to a synthetic list before checking permission. No export handler, file access, subprocess or socket exists in this exercise.

    The three denied-surface cases are predicted to fail: they report tool_denied but leave export in effects. The denied_unlisted case, which asks for a delete_label tool that the contract never names, fails the same way. Allowed reads and malformed-input checks should still work. These are expected results derived from the source, not a run transcript.

    The small demo.py generation packet in the fixture makes the proposal step reproducible. It emits four synthetic requests and contract expectations; verify_demo.py executes those requests against the candidate and compares both response and effects. This is course-authored material, not a model transcript or an attack against a real service. The packet is optional practice; if you run it, keep the packet, verifier output and the candidate revision together when you explain a decision.

    Generate a repair, then keep verification independent

    Move the authority decision before the effect append, preserving argument validation, the permitted read and attempt accounting. Do not fix the negative cases by denying every request or by clearing evidence after an effect has already occurred.

    A person or an allowed assistant can propose the change; either way it remains a candidate until checked through the workshop execution route. Use only the public contract and fixture when requesting assistance. Do not change the expected results to accommodate the proposal, and keep your own explanation attributable.

    Three surfaces, one authority boundary

    Repository content, tool output and copied logs can all contain requests outside the authorized task. The fixture uses the same passive synthetic sentence in each surface so that permission cannot depend on trusting a label such as "tool response." Request parsing establishes shape, not authority. Denial must occur before the handler records an effect.

    A package-name suggestion raises a different question: identify the intended source, version and transitive/install-script effects before trusted preparation. This exercise installs no package. A scanner result supplies another bounded claim; investigate actual findings and add security regressions, without treating a clean scan as universal safety.

    Where the boundary runs

    Permission is enforced at more than one layer, and each layer has a different observable claim:

    Layer Concrete question in this lesson Evidence that can answer it
    Data and prompt Is this sentence an input or an authority grant? The fixed contract and the input trace
    Controller Did the allowlist run before the effect handler? effects plus the response from Boundary.call
    Launcher and host broker Can a generated command reach an unapproved network, mount or key? The launcher run record and its refusal; the key stays on the host
    Application state Did the permitted label read still return the required text? The positive regression and its returned value

    For example, a copied log may request export. The controller must reject it before appending an effect. If a modified process tries to bypass the controller, the external launcher still needs to deny network and filesystem access. Conversely, a permitted read_label must cross the controller and return the supplied label. A passing in-memory check therefore supports only the dispatcher claim; launcher evidence is still needed to establish containment.

    Supply-chain decisions are authorization decisions

    Suppose a generated patch proposes course-label-fixture==0.0.0 and an install hook that runs a setup command. The fluent name is only data. Before installation, ask for the intended source, exact version and lock digest, transitive dependencies, install-script behavior and the smallest launcher command that can prepare it. If any item is missing, reject the suggestion or keep the work on the supplied standard-library fixture. Do not let a package manager resolve a plausible name as a side effect of exploring the example. This lesson installs no package; the example is synthetic and stops at the authorization decision.

    Why injected text can become an instruction

    A model receives repository notes, tool results and user requests as tokens in one context. The token stream does not carry a trustworthy authority bit. Salient imperative wording can therefore steer the next proposal even when the text is data. The FAKE replay in the security workshop makes that mechanism observable: it reads an injected note and poisoned MCP output, proposes editing its own policy to auto-approve and contacting a mock, then lets a separate policy controller decide which effects can run. No model output is a permission grant.

    Use the registered incident cards to compare boundaries, not to execute a payload: the GitHub MCP research describes untrusted public text crossing into private data and public writes (incidents/github-mcp; as_of: 2026-09-05; Source 1); the Nx S1ngularity postmortem shows how poisoned package content can enter a release path (incidents/nx-s1ngularity; as_of: 2026-09-05; Source 1); and the Amazon Q bulletin illustrates why reported code entry still needs separate execution-boundary analysis (incidents/amazon-q; as_of: 2026-09-05; Source 1). The reviewed Codex documentation distinguishes approval policy from sandbox limits (tools/codex; as_of: 2026-09-05; Source 1): removing a confirmation prompt does not itself remove network or filesystem containment.

    For a settings-escalation comparison, use the reviewed disclosure (incidents/github-copilot-rce; as_of: 2026-10-07; Source 1). In your own words, compare its settings-escalation pattern—an injected instruction changing an agent setting so later actions are auto-approved—with this local replay. In this replay, an explicit confirmation requirement still applies even when auto_approve is true. The course fixture is the only executable example.

    Scanners make bounded claims

    Three kinds of scanner answer three different questions. Static analysis matches patterns in the code you wrote, such as a query built by string concatenation. Dependency analysis compares the versions you installed against published advisories. Secret scanning looks for credential-shaped strings, and it has to look at history as well as the working tree: deleting a file does not delete the secret from earlier commits, and an exception written for a file outlives that file for the same reason.

    An agent is useful for triage when each finding is handled as a claim. Is the flagged code reachable from an input an attacker controls? Can you reproduce the problem with an inert input? Does the repair keep permitted behavior working, and is there a regression test? When a finding is a false positive, record the reason beside a narrow exception instead of disabling the rule. Rerun the scanner after each repair, and keep in mind what a clean result means: no known pattern matched, under this rule set, on this date.

    Use the fixture's scan-report.json as a synthetic disposition exercise. Handle each row rather than copying the overall status:

    1. SYN-001 is reachable and reproducible, so move the authorization check before the effect, retain denied_export as a regression, and rerun the public checks.
    2. SYN-002 describes an uninstalled package suggestion. Reject it until source, pin and install effects are evidenced; there is no dependency change to approve.
    3. SYN-003 is a credential-shaped string in teaching text. Looking like a placeholder does not decide it: a real key can be pasted into an example, and an example value can still be wired into a client. Decide by whether any code path reads the string as a credential, for example by loading it into a client, sending it in a header or comparing it in an authorization check. Here no fixture code does: searching the copied .py files for the string finds nothing. Record that search beside a narrow exception and rerun the secret scan. If a code path did use the string, handle it as a hard-coded credential: move it out of the code and, if the value was ever real, revoke it and check history. A clean rerun does not erase the need to review history or the rule set.

    The report itself is synthetic and deliberately small. A real project record should add the reviewer, date, changed path and command output without turning a scanner summary into a blanket security claim.

    Triage scanner output with an agent

    The security workshop asks you to triage real scanner output with an agent's help. This example rehearses the same steps on a small course-authored module, preferences.py, so that you meet the mistakes here first. It shares no function, input, trajectory or answer label with the project or the security workshop. The files are synthetic course material, not a model transcript.

    1. The scanner reports three findings (triage-scan.json):

    Finding What the rule saw
    static:unsafe-deserialization@preferences.py::parse_config Caller text reaches pickle.loads
    static:html-interpolation@preferences.py::format_status A value is interpolated into a status label
    dependency:COURSE-ADV-017@course-preferences==2.0.0 The locked version is in an advisory's affected range; the advisory applies only when an optional toml-loader extra is installed

    Before reading anything else, write your own prediction for each row.

    2. Generate: an agent drafts a classification (agent-draft.json). The course authored this draft to show typical errors; it is not a model transcript. It calls parse_config a false positive because the input is text, calls format_status a true positive, and calls the dependency a false positive because the optional extra is not visible in the lock file. With a real agent, treat one draft as one sample: the optional Semgrep study in the readings reports that results can be quite noisy and non-deterministic (studies/semgrep-ai-vulnerability-finding; as_of: 2026-10-07; Source 1). Each claim still needs its own observation.

    3. Verify: every claim meets an observation. Each class needs its own evidence:

    • A true positive needs a bounded observation of the risky path. The verifier replaces the loader with an in-memory recorder and passes ordinary JSON text and one line that is not JSON (theme = dark); the starter still calls pickle.loads. No payload is executed. The agent's claim that text cannot carry executable behavior is therefore unsupported by the source path.
    • A false positive needs the condition that stops it, with evidence. format_status first looks up status in the two-value ALLOWED_STATUSES map and rejects unknown values. The interpolated label is thus one of two fixed strings, and the allowed status still formats.
    • Needs more evidence is an answer when you name what is missing. The dependency version is in the affected range, but this fixture does not show whether the optional toml-loader extra is installed at runtime. The honest entry names that missing fact and the environment check that would supply it.

    verify_triage.py prints the agent's class, observed class and raw observations. It exits 1 while the unsafe loader is still called, text that is not JSON is accepted, or the allowed status path is broken.

    4. Fix one true positive and keep the observation as a regression. Parse the documented configuration with the data-only JSON decoder and keep the format_status allowlist unchanged. Rerun the same verifier: JSON text now returns the expected mapping, theme = dark raises an error, the recorder sees no pickle call, and status:Ready still works while an unknown status is rejected. A suppression comment or a rewrite that merely hides the scanner pattern would leave the unsafe path and still fail. So would a parser that tries JSON first and falls back to pickle: the JSON inputs pass, but the line that is not JSON still reaches the loader.

    5. Record the wrong claim. Write down one agent claim that turned out wrong, what was wrong about it, and which check caught it. In this example the parse_config false positive is caught by observing the loader call without executing an attack payload. That record is the evidence that you verified the agent's work rather than copying it.

    Hands-on exercise

    The 120-minute workshop plan includes prediction, bounded execution, policy hardening, scanner triage and individual explanation. It is a proposed allocation within the existing weekly practical work, not an extra assessment or a measured completion time.

    Keep the failing case, response, effect list, change and actual rerun result together. Explain why both a positive case and a denied-effect case are necessary. Reuse the existing work-record/AI-note ID; no separate transcript or new graded submission is required. The handoff below says what carries into M1.

    Verification

    Follow the complete copy and launcher commands. The public checks are intentionally inspectable and editable; they provide learning feedback, not authoritative grades. Their fixed input/output cases expose a known wrong implementation but do not prove all possible behavior.

    For the optional generation-plus-verification path, create a fresh practice directory and run the launcher for demo.py, saving its launcher envelope separately. Extract the envelope's stdout into generated.json on the host, then run the launcher for verify_demo.py generated.json. The unchanged candidate should fail on denied_export and denied_unlisted; after moving the check before effects.append, the same generated packet should pass. Keep the expected packet unchanged. The host-side extract only parses launcher output; it does not execute the fixture outside the launcher. This separates a generated proposal from the verifier and makes the two sides of the claim visible.

    For the triage example, copy the five triage files and run verify_triage.py through the launcher, as the triage drill shows. The starter exits 1 and reports that none of the three agent claims is supported. After you switch parse_config to the data-only JSON decoder, the same command exits 0. Keep both outputs: the first is your reproducer, the second is your regression.

    First preserve the starter's actual failure. Propose a repair in the editor, rerun the unchanged public checks and explain at least one relevant observed difference. Challenge the apparent success with a counterexample derived from the contract. If a peer changes the proposal or a requirement changes, identify the new verification target rather than reusing an old passing label.

    The effect list demonstrates dispatcher ordering, not operating-system containment. A modified process could bypass this toy dispatcher. The external launcher remains responsible for actual isolation. This in-memory exercise is not the security workshop loopback mock, a live attack, a vulnerability scan or M1 security acceptance.

    Two directions of verification

    Security evidence has two independent directions. First, a denied request must leave the protected state unchanged: export returns tool_denied and the effect list stays empty, and so does delete_label, a tool the contract never names. Second, an allowed request must still work: read_label returns the supplied text and records only the permitted effect. Add the budget case as a third check because a refusal still consumes an attempt. A patch that denies every tool can satisfy the first direction while breaking the task; a patch that keeps the read path but appends export fails the boundary condition.

    Common mistakes

    Mistake Better next action
    Trust a refusal message Inspect the effect list as well as the return value.
    Deny all calls Retain a positive read case.
    Block only the tool named in the injected text Allow only read_label, and keep a check for a tool name nobody wrote down, such as delete_label.
    Treat a log hook as prevention Place the check before dispatch/effect, not after.
    Ignore refused calls in the budget Count every attempt; do not grant free retries.
    Call this a sandbox test Separate interface behavior from external isolation.
    Accept an agent's "false positive" without a reproducer Run an inert input against the flagged code, and name the condition that stops it.
    Fix a finding by suppression, deletion or renaming Repair the behavior; keep the reproducer as a test that fails before and passes after.
    Rewrite code only until the pattern stops matching Rerun the reproducer; a quiet scanner is not a repair.
    Clear a secret finding because the value looks like a placeholder Check whether any code path reads, sends or compares the string as a credential; a real key can look like an example.
    Treat a version match as exploitable, or as safe Check each condition the advisory lists; say what evidence is missing.
    Accept the agent's proposed fix as written Check that it is possible and keeps permitted behavior working.

    Transfer to a new situation

    The user now authorizes read_summary as well as read_label; export is still not authorized. Name one new positive check and one retained negative check, and say which policy change must come before the implementation.

    Write the expected behavior and the next check before comparing with a partner.

    Handoff to the security workshop

    Bring the repaired fixture result, the itemized scan dispositions and the positive and negative regressions to the security workshop. The workshop exercises its loopback mock through the approved launcher; this classroom fixture is a separate synthetic dispatcher example and does not reuse a workshop or seed instance, so keep the two evidence sets named separately.

    In your own ci-dashboard, triage every finding from the three workshop scanners and repair each true positive with a regression test. Then rerun scan/check_triage.py on the starting tree and your current tree (workshop step 6), and run python3 -I launch.py smoke on the current revision (project kit step 2). The planted security seeds are not published: at M1 review the teaching team runs its own seed check on your revision. Keep payloads local and inert.
