    Workshop: Security: refuse before effects

    Purpose and materials

    Proposed duration: 120 minutes within existing practical work. Materials: notes, public fixture guide, text editor, terminal and the course-supported execution route. Mode: individual work with an optional written comparison. Output: one existing work record containing the candidate, actual verification and your own short explanation (LO5, LO7).

    Minutes Action Evidence
    0-10 Read the contract and prepare only public files. State the permitted input, output and boundary.
    10-20 Predict from the contract and displayed candidate excerpt before opening full fixture comments or checks. Input, expected result and proposed result.
    20-40 Run the public check, propose one repair and rerun the same check. Preserve the actual original failure, your change and the rerun, including denied_unlisted.
    40-70 Run the FAKE agent replay, harden the policy and inspect every decision. Dangerous effects are absent while health still passes.
    70-110 Complete the 40-minute triage drill. One disposition per finding, the repaired verifier run and one wrong agent claim.
    110-120 Record your evidence and decision, then read the handoff. Regression evidence, remaining limits and your accept/narrow/observe/stop decision.

    The generation packet in the execution route is optional and sits outside these 120 minutes.

    If preparation consumes the first ten minutes, ask for support and start the text trace. Do not spend the whole session repeatedly retrying setup. During the repair block, use the contract hint in the notes if the repair is still unclear; do not replace individual explanation with copying a solution. Timing is a help checkpoint, not a penalty.

    Save your own expected results from the fixed contract before opening the worked explanation or public checks. If you already saw the answer, identify this as informed practice.

    Execution route

    Use Week 0 setup for access and execution requirements. These preparation commands copy only public course files; they do not run the exercise on the host. Start from the reviewed course root. Use a new directory name if this one already exists; do not overwrite another attempt.

    mkdir week08-work
cp lectures/week-08/fixture/candidate.py week08-work/
cp lectures/week-08/fixture/exercise.py week08-work/
cp lectures/week-08/fixture/demo.py week08-work/
cp lectures/week-08/fixture/verify_demo.py week08-work/
week08_profile=$(uv run --project infra/hosted --locked python infra/hosted/resolve_profile.py --profile offline --json)
week08_version=$(printf '%s' "$week08_profile" | python3 -c 'import json,sys; print(json.load(sys.stdin)["version"])')
week08_digest=$(printf '%s' "$week08_profile" | python3 -c 'import json,sys; print(json.load(sys.stdin)["digest"])')

    Run the public check, then use the identical command after editing only candidate.py in your editor:

    sh scripts/course-sandbox --profile offline --version "$week08_version" --digest "$week08_digest" --workspace week08-work -- python exercise.py

    Expected fixture behavior: the unchanged starter's public check exits 1; a contract-correct repair should exit 0 with every named check passing. Compare these predictions with your actual launcher and exercise results. No model is called by these commands.

    Optional, outside the 120-minute plan: the generation-plus-verification route repeats the same contract as a generated packet. It uses the same launcher and a fresh output file. Generate the synthetic packet first, then verify that unchanged packet after editing only candidate.py:

    sh scripts/course-sandbox --profile offline --version "$week08_version" --digest "$week08_digest" --workspace week08-work -- python demo.py > week08-demo-launcher.json
python3 -c 'import json; from pathlib import Path; envelope=json.loads(Path("week08-demo-launcher.json").read_text()); assert envelope["exit_code"] == 0; Path("week08-work/generated.json").write_text(envelope["stdout"])'
sh scripts/course-sandbox --profile offline --version "$week08_version" --digest "$week08_digest" --workspace week08-work -- python verify_demo.py generated.json

    The first command is generation, not a model run. The second is verification. The starter is expected to exit 1 because denied_export and denied_unlisted observe an effect; after a bounded repair it should exit 0.

    An exercise assertion/report mismatch is different from a launcher safety or preparation failure. If the launcher refuses execution or reports a safety failure, stop and use the course support route; do not change the executor, mount private assets, weaken limits or run the proposed code on the host. Missing exercise output is not evidence that the candidate passed.

    Agent-loop injection and hardening

    Estimated time: about 30 minutes inside the 120-minute workshop. Materials: the public capstone/security-workshop/student/ bundle and the Week 0 launcher. Output: a proposal/decision trace and a short explanation in the existing work record.

    The FAKE replay reads two untrusted strings: victim-project/agent-notes.md and the text-only poisoned MCP result. A language model receives both as context tokens; neither source is an authority grant. The replay still proposes write_policy, contact_mock and health because the model follows salient imperative text. This is the mechanism to inspect: token prediction does not carry a trustworthy provenance bit, and the controller must enforce policy after proposal but before effects.

    Run the starter once, save the proposal and effect trace, then edit only the policy controls. The hardened policy removes the policy write path, allowlists health, and requires confirmation for the two dangerous tools. Rerun it and check both directions: the dangerous effects are absent, while health still writes its local result.

    Use the same offline profile values from the execution route; the command runs inside the launcher-mounted copy rather than on a host project:

    mkdir -p week08-security
cp -R capstone/security-workshop/student/. week08-security/
sh scripts/course-sandbox --profile offline --version "$week08_version" --digest "$week08_digest" \
  --workspace week08-security -- python attack/run_all.py --workspace run
sh scripts/course-sandbox --profile offline --version "$week08_version" --digest "$week08_digest" \
  --workspace week08-security -- python attack/run_all.py --workspace run-fixed --policy harden/policy.json

    A successful dispatcher check does not establish OS containment. The launcher must still provide the bounded workspace and network namespace; the mock accepts only the current random loopback capability.

    Triage drill

    Estimated time: about 40 minutes. Materials: the triage example in the notes and five fixture files. Mode: individual work. Output: a short triage record in your work record. This drill uses course-authored code as a rehearsal; it does not reuse a project or security-workshop instance.

    1. Read triage-scan.json and preferences.py. Write your own class for each finding: true positive, false positive or needs more evidence.
    2. Read agent-draft.json. Mark each claim you would accept as written.
    3. Run the verifier from a new directory, using the profile values from the execution route:

    sh mkdir week08-triage cp lectures/week-08/fixture/preferences.py week08-triage/ cp lectures/week-08/fixture/preferences.lock week08-triage/ cp lectures/week-08/fixture/triage-scan.json week08-triage/ cp lectures/week-08/fixture/agent-draft.json week08-triage/ cp lectures/week-08/fixture/verify_triage.py week08-triage/ sh scripts/course-sandbox --profile offline --version "$week08_version" --digest "$week08_digest" --workspace week08-triage -- python verify_triage.py

    The starter exits 1. Compare your prediction, the agent's class and the raw observation for each row. For the deserialization finding, confirm the recorder saw a loader call; no attack payload is executed. For the dependency, write the missing fact and the check that would supply it. 4. Repair parse_config to call the provided data-only JSON decoder and run the same command. It should exit 0. Do not keep pickle.loads as a fallback for text that is not JSON; the verifier sends one such line. Do not change verify_triage.py or the expected classifications. 5. Record one agent claim that was wrong, what was wrong and which check caught it. Compare one alternative disposition: did your first claim survive the verifier?

    If execution is unavailable, trace the parser's loader call and the status allowlist by hand and label this as text analysis. Do not construct or run a payload.

    If execution is unavailable

    Trace the public source and the synthetic case in the notes, write the expected and proposed outcomes, and give a reasoned repair. Label this as text analysis. Keep required execution pending until the course supplies an approved supported route; text work does not stand in for an execution, a passed launcher check or a completed practice unit. Keyboard-only work and typed peer feedback are supported.

    Record and handoff

    Keep the failing case, response, effect list, change and actual rerun result together, for the boundary fixture and for the triage drill. Explain why both a positive case and a denied-effect case are necessary. Reuse the existing work-record/AI-note ID; no separate transcript or new graded submission is required. Reflection and self-check answers remain your own: a shared candidate can support a pair discussion, but another person's output does not establish your understanding.

    Before leaving, decide whether to accept your repair, narrow the task, obtain one missing observation or stop. Explain what evidence could change that decision.

    Into the security workshop and M1. Bring the repaired fixture result, the triage record and its positive and negative regressions to the security workshop. Keep two evidence sets named separately: this fixture's in-memory effect list is a teaching boundary, while the workshop's loopback mock and the launcher are the execution boundary. In your own ci-dashboard, triage every finding from the three workshop scanners and repair each true positive with a regression test. Then rerun scan/check_triage.py on the starting tree and your current tree (workshop step 6), and run python3 -I launch.py smoke on the current revision (project kit step 2). The planted security seeds are not published: at M1 review the teaching team runs its own seed check on your revision. Any inert payload the workshop supplies stays marked INERT PAYLOAD — course material and contacts only its allocated 127.0.0.1 mock.

    After-class extension (outside the 120-minute plan): For the optional scan-report.json exercise in the notes, write one disposition per finding: the reachable claim, a local reproduction or reason it is unreachable, the decision, and the regression or narrow exception that will be rerun. A green summary without these rows is incomplete evidence.

    Practitioner guest (optional)

    This week may also have a practitioner guest on agent and application security. If one is announced, a practitioner from a partner organization joins the first class for up to 45 minutes and the rest of the class runs as usual. Before class, write one question for the guest; after class, write one sentence comparing one claim the guest made with this week's evidence, such as your triage record. The talk is not assessed and adds no time outside class. A guest speaks about their own organization's practice; the course endorses no product. The talk is recorded only with advance notice and the consent of those present. Without a guest, the class runs as usual.
