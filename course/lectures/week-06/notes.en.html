    Week 6: Review and delegate a bounded change

    Learning objectives

    This week has one main line: review a change against what was asked, using roles whose context you control. A model reviews; you verify each point it raises. By the end of the lesson, you can:

    LO Observable action Practice and self-check
    LO2 Assign a bounded task, context, permissions and verification; run a planner, an implementer and a reviewer in separate contexts Activities 1, 2 and 3; M1 delegation run; questions 6 and 12
    LO3 Review a request before the change: find a clause with two readings, give an input that separates them and the question for the request's owner, or show the search behind a no-finding Contract review before Activity 2; question 9
    LO5 Review a short change yourself, reproduce a failure, mark each point of a model review confirmed, refuted or cannot tell with its evidence, and explain a revision Activities 1, 2 and 3; questions 1, 2, 3, 7 and 12
    LO9 Keep minimal source/AI-use evidence, respect another person's access and participation boundaries, calibrate your time prediction and judge what an unattended run costs Activity evidence note; issue-run record; Activity 3 merge decision; questions 4, 5 and 8

    Estimated time this week is about 13 hours. This includes the classes, P2's three hours (workshop, verification and short explanation included), Activity 2's 35 minutes and Activity 3's 25 minutes in class, about two hours 15 minutes of M1 project work (45 minutes to write your review rules and 90 minutes for the delegated change and the verified model review, including waiting and checks), and finishing your C1 contribution and C2 proposal. Activities 2 and 3 are part of the scheduled class time, not additional projects. These are course estimates, not measured completion times. Ask for help at the checkpoint rather than widening the task or buying model access. Workflow types and parallel worktrees are optional reading; optional extensions do not affect the attainable grade.

    Before the first review, use only the permission contract and candidate on the slides. Save your finding before opening the worked explanation here. If already exposed, identify informed practice; P2 uses the first review of your actual new candidate before the assistant comparison.

    Minimal example

    The continuing dashboard case

    The dashboard allows owners or staff to edit active builds. An agent proposes an authorization expression and a reviewer checks only a staff account.

    allowed = is_owner or is_staff and not archived

    Decision: Can an owner edit an archived build under this expression?

    Python's operator precedence puts and before or. An owner can satisfy the first term even when archived. The required policy is (is_owner or is_staff) and not archived; verify the role/archive combinations independently.

    Write your own review before consulting the agent. Ask it for claims tied to inputs and code references, then mark each claim confirmed, refuted or cannot tell with its evidence.

    Acceptance decision: Merge only after the repaired expression passes every role and archive combination on the exact revision you will merge. A model's review or explanation does not establish who may edit.

    The public permission fixture below supplies a compact review target. Relate its parentheses to the dashboard role policy; do not infer permission from a model explanation.

    This is a course-authored, hand-worked example. Actual execution evidence comes from your own checks.

    The synthetic change

    Use the fixture contract. An account can edit a document exactly when active is true and at least one of owner or staff is true. Inputs are booleans. The bundled candidate is course-written, deliberately faulty, and has this body:

    return owner or staff and active

    Predict the result for an inactive owner before testing. The expression allows that owner to edit: owner alone can make the result true. The contract requires the active check on both role paths. A proposed revision is:

    return active and (owner or staff)

    Do not accept the revision just because it looks clearer. Verify inactive accounts, active outsiders, each permitted role and overlapping roles. This is an access decision exercise with synthetic booleans, not a production authentication system.

    Prepare the accepted launcher

    Model access, keys and the launcher check follow Week 0 setup. From the course root, run the trusted configuration query:

    uv run --project infra/hosted --locked python infra/hosted/resolve_profile.py --profile offline --json

    In the commands below replace VERSION with version and DIGEST with digest from that output. The offline profile runs without a key. Do not change profile parameters to make a run pass.

    With your editor/file manager create week6-work inside the course root, as Week 9 does with week09-work. Copy only access.py and check_access.py from lectures/week-06/fixture into it. The commands use week6-work from the course root; the launcher refuses any workspace path that contains ... Exclude .git, teacher material, keys, private code, raw interviews and unrelated personal data. The launcher copies these inputs into its bounded temporary workspace and exports only explicitly emitted files. Host files are not mounted into student execution. Do not run these scripts on the host, in an editor terminal without the launcher, or in the Dev Container directly.

    Launcher limits. This is the one place this week states them. Each launcher run has a 30-second wall-clock limit including model time, at most four model requests, 64 KB of total output (including JSON prompt frames and base64 artifact frames) and 1 MB of aggregate input. The fixture's delegate.py also rejects any single input file over 32 KB. For the two-request issue stage, keep the target file around 12 KB; when plan and implement run separately, a target around 20 KB fits each run. A timeout or limit refusal is a recorded result. Keep its record; do not rerun for a nicer output, raise a limit or move to another tool. If a target is too large, narrow the issue.

    Review, check and revise the bundled candidate

    Every student reviews the same bundled candidate. In the lecture the instructor may also generate one fresh candidate and request one model review of it through the launcher with the fixture's workflow.py; you do not run that script. Keep a live candidate and its results apart from the bundled one.

    Write your own review before reading any AI review. Name a location, a concrete input, expected versus observed behavior and consequence. If no defect appears, explain the cases you checked and the limits of that conclusion. Then execute the public checks:

    sh scripts/course-sandbox --profile offline --version VERSION --digest DIGEST --workspace week6-work --output week6-check-before -- python check_access.py -v

    For the bundled candidate, test_inactive_owner and the inactive case in test_overlapping_roles fail. Record the actual result; do not copy this prediction as your observed output. The launcher JSON includes the container exit_code, combined output in stdout and model request count. Read those fields rather than treating creation of an output directory as success. Each invocation also runs the launcher's actual safety suite, including deliberate limit probes; include this waiting in your time record.

    Save your review in the existing work record, then compare it with the course-written review claims A1 and A2 in Activity 1, or with the instructor's live review if one was shown. Verify each claim against the contract and inputs. An AI review is a hypothesis source: it may identify a useful boundary, miss a defect, or invent a requirement. For example, a demand to accept strings such as "false" is outside this boolean-only contract. A human can also miss an operator-precedence defect, follow the model's suggestion too readily or misunderstand the specification. Your own first review and a reproducer make both more useful; neither is a correctness guarantee.

    Revise only the necessary code in your editor. Rerun the same checks with a fresh output directory, week6-check-after, and compare before/after behavior and the actual diff. For the proposed revision all seven checks should pass, covering the eight boolean combinations. Inspect the copied test source against the course version too: a candidate can alter its own writable sandbox. Public self-check results are practice evidence, not an isolated hidden grader, trusted score or automatic merge authorization.

    Review the request before you delegate it

    Contract review: 10 minutes, AI-off. A review judges a change against what was asked, so check what was asked first. An unattended planner fills a gap in the request with a guess, and a review point that depends on a clause with two readings cannot be confirmed or refuted. Suppose the first draft of this week's issue had this acceptance line:

    Only active owners and staff can edit.

    Before reading on, write four things in your work record: the clause, two readings of it, an input that the two readings treat differently, and the question you would ask the person who owns the request. If you find no clause with two readings, write your search instead: the clause you examined most closely, the two readings you tried, and an input both readings treat alike.

    One answer: "active" can apply to both nouns or only to the first.

    • Reading A: owners and staff must both be active.
    • Reading B: owners must be active; staff can edit whatever their status.
    • Separating input: an inactive staff member, can_edit(active=False, owner=False, staff=True). Reading A denies it; reading B allows it.
    • Question for the person who owns the request: "Must a staff member's account be active to edit, as an owner's must?"

    The words group two ways, just as owner or staff and active does. The answer was reading A. The fixture contract records that answer ("Inactive accounts cannot edit, including inactive owners and staff"), and so does the example issue's first acceptance line. Until such a question is answered, the issue states which reading it implements or the change waits. A review point that depends on the open reading is cannot tell. P2 asks for the same four parts on its own contract.

    Plan, implement and review in separate contexts

    Delegating one change to an agent hides three jobs: deciding what to do, doing it, and checking it. Give each job its own launcher run and its own workspace, so that each role sees only what it needs. The fixture's delegate.py runs one role per invocation. It reads only the files it names and sends them to the model as data. It never executes the model's code or the issue's verification command, and it exports text for you to inspect.

    Role Workspace holds Exports You do next
    Planner delegate.py, issue.md, the target file plan.md Read the plan; strike anything the issue does not ask for
    Implementer delegate.py, issue.md, your edited plan.md, the target file proposed-<file>, change.diff, pr-description.md Apply the file on a branch; run the checks
    Reviewer delegate.py, issue.md, change.diff, evidence.txt, REVIEW.md review.txt Verify each point: confirmed, refuted or cannot tell

    The issue is a short plain-text file. Copy issue-example.txt to issue.md and replace BASE_SHA with the base commit that the practice repository setup prints. It names one target file, the acceptance criteria, the verification command and what is out of scope. Every run also exports run-record.json, which lists each file that went into the prompt with its SHA-256 digest and the number of model requests. Keep these records: they show what each role could see.

    The reviewer's context is the point of the exercise. Its workspace holds the issue (the specification), the diff, your check output and your review rules, and nothing else. It never sees the plan, the implementer's prompt or the drafted description. A reviewer that has read the plan inherits the plan's assumptions; one that sees only what was asked, what changed and what ran has to judge the change against the request. The script refuses to review when the workspace holds any other file, before it reads or sends anything.

    With VERSION and DIGEST resolved as above, create the workspaces with your editor and run each role with a fresh output directory:

    sh scripts/course-sandbox --profile offline --version VERSION --digest DIGEST --workspace w6-plan --output w6-plan-out --model fake -- python delegate.py plan
sh scripts/course-sandbox --profile offline --version VERSION --digest DIGEST --workspace w6-impl --output w6-impl-out --model fake -- python delegate.py implement
sh scripts/course-sandbox --profile offline --version VERSION --digest DIGEST --workspace w6-check --output w6-check-out -- python check_access.py -v
sh scripts/course-sandbox --profile offline --version VERSION --digest DIGEST --workspace w6-review --output w6-review-out --model fake -- python delegate.py review

    Between the second and third commands, make w6-check hold check_access.py and the exported proposed-access.py saved as access.py. Copy the third command's launcher JSON, with its exit_code and stdout, into evidence.txt for the reviewer's workspace. Each model run makes one request. A refusal or an incomplete response is a result to record, not a reason to rerun until something appears.

    As written, with --model fake, these commands check only the launcher connection: every stage refuses the FAKE placeholder and writes no plan, change or review. For a real run, take the API route. Resolve the approved-hosted profile and hosted configuration as Week 0 setup describes, and use its options in place of --profile offline --version VERSION --digest DIGEST --model fake, for example:

    sh scripts/course-sandbox --profile approved-hosted --version HOSTED_VERSION --digest HOSTED_DIGEST --model api --hosted-config HOSTED_CONFIG --key-file ~/.config/course/hosted-key --workspace w6-plan --output w6-plan-out -- python delegate.py plan

    Without a key, take the replay route below.

    The model reviews; you verify each point

    A model, not another student, reviews your change, and you verify what it says. Fresh context is not independence. The same model may share the implementer's blind spots, and a reviewer that sees only a diff cannot notice a change that is missing from it. So call its output a model review, never an independent review, and treat every point as a claim.

    1. Before you read the review, write your own short review against REVIEW.md: one input you expect to fail, or a no-finding with the inputs you checked.
    2. Run the reviewer on your change in a fresh workspace, as above.
    3. Give every point in review.txt exactly one outcome:
    4. Confirmed: a reproducer shows the problem. It is an input with its actual result, a diff line, or a line of the evidence, and someone else can rerun it.
    5. Refuted: runnable evidence shows the point is wrong: the input passes, or the rule it cites is met. Or the contract or issue shows the requirement it asserts does not exist.
    6. Cannot tell: the files you have cannot decide it. Write what is missing and why. Never record it as confirmed or refuted. P2 calls this outcome unverified.
    7. Read the issue again for anything the diff should contain and does not. The reviewer could not see it, so record it as your own finding.

    Cannot tell is the usual outcome for a point about code outside the reviewer's files. Suppose a review says that a caller in another file may rely on the old behavior. The issue, the diff and the evidence do not hold that caller, so the reviewer was guessing, and from those files you cannot decide it either. Mark it cannot tell and name the file and the call that would decide it. In your own repository you can then look: search for the changed function's callers, for example with git grep -n "can_edit(", and read what each one passes and expects. With that evidence the point becomes confirmed or refuted, and the callers you checked go into your review record.

    Record each point, its outcome and its evidence under ## Review evidence in the PR. Fix each confirmed point, or record why it waits for a later change. Keep refuted points with the evidence that refutes them. Whether the reviewer caught something or nothing, write which inputs it considered and whether your own checks already covered them.

    Without a key. You may take the replay route without giving a reason. Replay the model review that the teaching team recorded with the approved configuration on the course sample change, using the replay command in Week 0 setup, and verify each of its points in the same way. Until that record is published, verify the course-written comments in the sample run and label them course-written. For your own M1 change, write your own review against REVIEW.md, note under ## Review evidence that no model review ran, and ask a TA, as the PR template says.

    Review rules you write and check

    An AI reviewer and a human reviewer drift toward different concerns unless you state what matters. Write a short REVIEW.md in your project repository: three to six rules, each with the source that justifies it and a check that a reviewer can apply to a diff or a run. Derive the rules from your M0 specification and from defects you have already met, such as a CP1 repair or an M1 regression. The fixture's review-rules-example.txt shows the shape for the document-edit guard.

    R3  Inputs stay Python booleans; the change adds no parsing and no new input type.
    Source: contract "Inputs are booleans"; issue out of scope "Parsing strings".
    Check: the diff adds no str handling, conversion or default argument.

    "Code should be clean" is not a rule: nobody can show that a diff breaks it. The review role reads REVIEW.md and cites a rule ID for each point; cite the same IDs in your own review. A point that cites a rule is still a claim, and a reproducer decides its outcome, not the rule ID. Change the rules by PR, like code. When a rule keeps producing refuted points, rewrite or remove it and record why. REVIEW.md tells reviewers what to check; it enforces nothing. The launcher and your merge rule enforce.

    From an issue file to a PR description

    The handoff can become a pipeline: an issue describes a bounded task, a trigger starts an agent, and the agent returns a pull request. The issue run does this locally and unattended. One launcher invocation plans and implements with no person between the two steps:

    sh scripts/course-sandbox --profile offline --version VERSION --digest DIGEST --workspace w6-issue --output w6-issue-out --model fake -- python delegate.py issue

    As above, --model fake checks only the launcher connection: the run stops at the planner with the FAKE message. A real issue run uses the API route options. w6-issue holds delegate.py, issue.md and the target file. The run makes two model requests and exports the plan, the proposed file, change.diff, pr-description.md and its run record. The draft names the branch and base and lists the acceptance criteria. It leaves the four explanation questions as the template's prompts, so the explanation check reports them incomplete until you answer them yourself.

    An issue is data from whoever could write it. Its wording cannot widen what the run may do; the script's structure decides that. The script refuses an issue that leaves BASE_SHA unreplaced, names more than one target, names a check or test file as the target, uses a path containing .., or contains a line that is not a known field. It cannot create a branch, push, reach the network or run the verification command. A model can still return a wrong or over-scoped change from a well-formed issue. The course-written sample run shows a plan that added string parsing nobody asked for, and a change that still passed all seven checks.

    The proposal then goes through the same gate as any other change. In the practice repository from the Activity 2 setup, create the branch from the recorded base with trusted commands, save the proposed file over w6-practice/access.py with your editor, and inspect the staged diff:

    git -C w6-practice switch -c issue/inactive-owner BASE_SHA
git -C w6-practice add access.py
git -C w6-practice diff --cached

    Run the checks through the launcher as above, then let the model review the change and verify each point as described. Answer the four explanation questions from your actual result. Only a person merges.

    PR hygiene and the explanation gate

    Before submitting a small PR, inspect git status --short and git diff --cached in the practice repository. Stage explicit files. Keep unrelated formatting, dependency changes, artifacts and private data out. Give the base and candidate revision, scope, observed failure, changed behavior and unresolved limitations. A changed candidate needs fresh verification and a fresh review.

    A context file, such as the Week 5 AGENTS.md, tells each role what to do, and a hook, such as the Week 5 lint hook, checks an event such as a commit. Neither is isolation: the launcher enforces the execution boundary. Treat a suggested change to a rule file or a hook as reviewable code, not as permission for the author to widen their own access.

    The existing explanation guide supplies the four-question PR template:

    1. What changed? Identify the boolean guard and the affected behavior.
    2. Why? Connect the guard to the active-account requirement.
    3. Which inputs are likely to fail? Include inactive owners and overlapping roles.
    4. What did you personally verify? Reference your actual launcher result and version.

    These hints are not completed student answers. Write your own causal account. The explanation check looks only for completeness, so a complete answer can still be false; the guide explains how staff check the answers. Another student's explanation does not prove your understanding, and no one may infer authorship or grades from writing style.

    When unattended runs help

    An unattended run helps when the task is independent and has an exclusive file, its acceptance criteria and verification command are written down, waiting would otherwise dominate, and someone is free to review the result when it returns. It does not help when the task is ambiguous, because an unattended planner fills gaps with guesses, or when review is already the bottleneck.

    Unattended runs have costs that attended work makes visible. Every run uses model requests from the same budget whether you keep its output or not. An over-scoped or failed run costs review time. Rerunning until the checks pass selects an output; it does not verify one. For each run, record the model requests from the launcher result, the time you waited, the minutes spent reviewing, and whether you kept or discarded the output. Compare these with doing the same change attended. This course runs these steps locally inside the launcher. It provides no hosted agent service and no CI trigger that holds credentials; the issue file, run records and review record practice the same decisions.

    A background agent: what its token allows and who merges

    A background agent takes the issue run one step further. A trigger, such as a label on an issue, starts the agent in a workspace of its own, and it hands back a branch, a pull request with a description and a run report. Nobody watches in between. Two questions decide whether such a pipeline is safe to use. First, what can the agent's token do: push which branches, change which files, and can it merge? Second, what decides the merge? If the required check runs a test file that the agent may edit, a green check shows only that the agent's change agrees with the agent's tests. Take the check's test file from the base commit, keep the agent's grants to what the issue needs, and stop the pipeline at a person who reviews the pull request against the issue. The description and the run report are claims, like any model review point: run the checks yourself and read every hunk. The background-agent activity is a replay of one such run on a dashboard issue; it needs no key.

    Hands-on exercise

    Complete the 45-minute review and handoff activity. You will first predict one result and review individually, exchange a reproducible finding, then revise and retest. Use the supplied synthetic candidate for the same comparison so every student has the same input. Keep any real-model candidate and its results clearly separate. The instructor may show one live generation and model review during the lecture; you do not run that demonstration.

    Verification

    Use the exact launcher commands above with resolved identity and fresh output directories. Evidence should let another reviewer answer: which candidate, which inputs, which actual result, what changed after feedback, and what remains uncertain? Inspect the test file, candidate diff and the actual result together. If execution fails, retain the safe failure category and ask for supported help; do not enable network, add a host mount, enlarge a resource limit or move execution to another tool. Reading the fixture as text remains possible but is not an execution pass.

    For the delegated change, check the run records before the outputs. The reviewer's run-record.json should list exactly issue.md, change.diff, evidence.txt and REVIEW.md as its inputs, with digests matching the files actually reviewed. Plan text pasted into evidence.txt, or no review record at all, is evidence that the review was not fresh; stop and record that limitation. Each confirmed or refuted point needs evidence that someone else can rerun, and each cannot-tell point names what is missing. The drafted PR description is not verified until the four answers are yours and the explanation check reports them complete. One failure case to recognize: the issue run exports a change whose checks pass but whose diff adds behavior the issue ruled out of scope.

    Common mistakes

    Mistake How to detect it Small correction
    Reviewing the change before the request A review point depends on a clause with two readings Write both readings and a separating input, ask the request's owner, and mark the point cannot tell until it is answered
    Trusting a green public test run Test source changed or edge cases absent Compare the test snapshot and reproduce the boundary input
    Calling AI findings your own review Your first review appears only after the AI response Keep stages separate; acknowledge actual assistance and seek required remediation
    Letting the reviewer read the plan Plan text appears in evidence.txt, or the review record is missing Stop and record the non-fresh or incomplete review; use a new workspace with only the issue, diff, evidence and rules
    Calling a model review independent review The record says "independent", or a point is accepted without your evidence Label it a model review and mark each point confirmed, refuted or cannot tell with evidence
    Forcing every point to confirmed or refuted A point is decided without the input or file that could decide it Mark it cannot tell and name what is missing
    Trusting a reviewer's "no finding" The issue asks for a change the diff does not contain Read the issue against the diff yourself and record the missing change
    Rerunning an unattended pipeline until the checks pass Several run records, one kept and unexplained Report every run; fix the issue or the plan instead of resampling
    Letting a background agent's green check merge The required check runs a test file the agent could edit Run the base commit's checks against the agent's code, and leave the merge to a person
