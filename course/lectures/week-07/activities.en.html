    Make a weak test fail

    Purpose

    Duration: 55 minutes, including verification, feedback and revision, within the budget for the Week 7 workshop and the testing workshop. Materials: notes, the public fixture, a keyboard-accessible text editor and terminal, and, for actual execution, a device that passed the Week 0 setup check. Grouping: pairs rotating driver/observer roles, or individual work with the same feedback checkpoint. Output: your changed assertions, actual failure/pass evidence and a short explanation of their relation to the contract. This is formative practice.

    Each launcher command first repeats the launcher's safety checks, including a 30-second time-limit probe, so expect about 40 seconds per command. The table needs about twelve of your own runs, roughly eight minutes of waiting in total. Start a run, then read or write while it finishes. The instructor shows the pristine mutation, fuzz and replay runs on screen in class, so you do not rerun them here.

    Minutes Action Evidence and LO
    0-7 Read the contract and weak assertions in notes. Individually explain why each of the three assertions cannot distinguish an incorrect integer result. Three blind spots and proposed replacements (LO5)
    7-15 Run weak, unit and property checks on the supplied candidate (three runs). Explain why a passing property does not settle rejection behavior. Actual outcomes, expected versus unexpected exception (LO5)
    15-25 Write three meaningful replacements in weak_checks: an expected value, a boundary case and an invalid-input check. Keep the contract fixed. Rerun on the broken candidate before proposing a repair (one run). A demonstrated red test, then a length/ASCII repair proposal (LO4/LO5)
    25-31 Switch roles. Run the mutation command on your revised checks (one run) and compare with the instructor's pristine result of weak 0/3, strong 3/3. Named survivor, or all three killed, and the distinguishing input (LO5)
    31-39 Apply the repair to candidate.py. Rerun your changed checks, then unit, property, seeded fuzz and both replays on the repaired workspace (six runs). Repaired results; the "" and "12" replays now pass (LO5)
    39-48 A peer points out one oracle blind spot or unsupported success claim. Revise a test or explanation and rerun the relevant case. Before/after evidence and visible revision (LO5)
    48-55 Individually write what belongs in the M1 baseline and which security items remain open. Answer self-check Q4. Functional snapshot and individual attribution; Week 8 closure boundary (LO4/LO5)

    At minute 15, offer help: (1) compare the asserted value with the contract; (2) try "9" and "12"; (3) use unit_checks and property_checks as public worked support. Keep the original public files separately so the published 0/3-versus-3/3 comparison can be reproduced. Your revised weak suite may produce different counts; report its actual revision and counts. verify_demo.py describes the original fixture, so run it on that original copy. It intentionally detects changed expected fixture behavior.

    If time is consumed by setup, arrange supported continuation or the text exercise. Do not increase limits or use host execution. The testing workshop's four-hour and Week 7's 12-hour budgets are design/help checkpoints, not grading penalties. Extending the fuzz harness is optional and does not lower attainable marks when omitted.

    Execution route

    Complete Week 0 setup before using the following execution route.

    Run these trusted preparation commands from the reviewed course root. They copy only public synthetic files and resolve public configuration; they execute no exercise code on the host. The two workspaces are intentionally separate:

    • week07_pristine_work: keep an unmodified original copy for the demonstration
    • week07_repaired_work: use this one for student edits and repaired validation

    Use distinct names and keep these variables for the subsequent commands.

    week07_pristine_work=$(mktemp -d ./week07-pristine.XXXXXX)
week07_repaired_work=$(mktemp -d ./week07-repaired.XXXXXX)

cp lectures/week-07/fixture/candidate.py lectures/week-07/fixture/demo.py lectures/week-07/fixture/verify_demo.py "$week07_pristine_work/"
cp lectures/week-07/fixture/candidate.py lectures/week-07/fixture/demo.py "$week07_repaired_work/"
week07_profile=$(uv run --project infra/hosted --locked python infra/hosted/resolve_profile.py --profile offline --json)
week07_version=$(printf '%s' "$week07_profile" | python3 -c 'import json,sys; print(json.load(sys.stdin)["version"])')
week07_digest=$(printf '%s' "$week07_profile" | python3 -c 'import json,sys; print(json.load(sys.stdin)["digest"])')

    The workspace contains only these files and your exercise edits. Never copy the whole private course checkout, teacher answers/tests, .git, credentials or user data. Use your editor for modifications. The launcher copies input into a bounded temporary workspace; no host workspace is mounted, no package installation is needed, and each invocation reruns the actual safety checks, about 40 seconds per command.

    Run each command separately so an expected nonzero result does not hide the next case. Keep all baseline commands on the pristine workspace. Run these three yourself:

    sh scripts/course-sandbox --profile offline --version "$week07_version" --digest "$week07_digest" --workspace "$week07_pristine_work" -- python demo.py weak
sh scripts/course-sandbox --profile offline --version "$week07_version" --digest "$week07_digest" --workspace "$week07_pristine_work" -- python demo.py unit
sh scripts/course-sandbox --profile offline --version "$week07_version" --digest "$week07_digest" --workspace "$week07_pristine_work" -- python demo.py property

    Expected: weak and property exit 0; unit exits 1 with IndexError.

    The instructor runs the remaining pristine commands on screen in class. You do not need to rerun them during the activity; run them afterwards on your own pristine copy if you want your own record:

    sh scripts/course-sandbox --profile offline --version "$week07_version" --digest "$week07_digest" --workspace "$week07_pristine_work" -- python demo.py mutation
sh scripts/course-sandbox --profile offline --version "$week07_version" --digest "$week07_digest" --workspace "$week07_pristine_work" -- python demo.py fuzz --seed 7
sh scripts/course-sandbox --profile offline --version "$week07_version" --digest "$week07_digest" --workspace "$week07_pristine_work" -- python demo.py replay --text ''
sh scripts/course-sandbox --profile offline --version "$week07_version" --digest "$week07_digest" --workspace "$week07_pristine_work" -- python demo.py replay --text '12'
sh scripts/course-sandbox --profile offline --version "$week07_version" --digest "$week07_digest" --workspace "$week07_pristine_work" -- python verify_demo.py

    Expected on the unmodified fixture workspace: mutation exits 0 and reports weak 0/3, strong 3/3; fuzz exits 1 with 109 cases and findings; the two replays exit 1 with unexpected_IndexError and accepted_invalid_input; verify_demo.py exits 0 with six checks. These are predicted synthetic fixture outputs, not a transcript of a model run. Inspect actual launcher results when executing.

    First edit demo.py's weak_checks in $week07_repaired_work and use the changed-test commands before repairing the parser. Then edit candidate.py in that same mutable workspace and rerun regression checks in that repaired workspace. Keep public test expectations unchanged and do not move verify_demo.py to this workspace. Select --implementation candidate to exercise your edited candidate.parse_level; the name identifies the module, even after you repair it.

    sh scripts/course-sandbox --profile offline --version "$week07_version" --digest "$week07_digest" --workspace "$week07_repaired_work" -- python demo.py unit --implementation candidate
sh scripts/course-sandbox --profile offline --version "$week07_version" --digest "$week07_digest" --workspace "$week07_repaired_work" -- python demo.py property --implementation candidate
sh scripts/course-sandbox --profile offline --version "$week07_version" --digest "$week07_digest" --workspace "$week07_repaired_work" -- python demo.py fuzz --implementation candidate --seed 7
sh scripts/course-sandbox --profile offline --version "$week07_version" --digest "$week07_digest" --workspace "$week07_repaired_work" -- python demo.py replay --implementation candidate --text ''
sh scripts/course-sandbox --profile offline --version "$week07_version" --digest "$week07_digest" --workspace "$week07_repaired_work" -- python demo.py replay --implementation candidate --text '12'

    All repaired regression commands should exit 0 on that revised workspace. fuzz with seed 7 should report no findings in the given corpus, which is not a proof. Replay successes show your revised invalid-input regression behavior is enforced. Leaving candidate.py unchanged still fails unit, fuzz and both replay checks. For an optional worked comparison, select the supplied demo.repaired function on the pristine workspace:

    sh scripts/course-sandbox --profile offline --version "$week07_version" --digest "$week07_digest" --workspace "$week07_pristine_work" -- python demo.py unit --implementation repaired

    That comparison does not test your edits. Keep each run's output with its workspace, command and candidate revision; these commands do not export or overwrite files. No invocation calls a model: these supplied proposals are course-authored practice. For optional actual agent generation, use only the Week 0 model/broker route, give the contract and public fixture, and inspect its response as text before editing. All proposed tests, repairs, dependencies and harnesses still require launcher execution. Do not label a scripted proposal or FAKE response as an actual model experiment.

    Checking the tests you changed

    After replacing the assertions in weak_checks, run this on the mutable workspace before repairing its parser. It executes your new checks, not the original unit suite:

    sh scripts/course-sandbox --profile offline --version "$week07_version" --digest "$week07_digest" --workspace "$week07_repaired_work" -- python demo.py weak --implementation candidate

    Keep that actual failure. After repairing candidate.py, rerun the same command. Then compare what your revised checks detect in the supplied mutant set:

    sh scripts/course-sandbox --profile offline --version "$week07_version" --digest "$week07_digest" --workspace "$week07_repaired_work" -- python demo.py mutation

    The report's weak field now refers to your revised weak_checks; identify that revision. Its count can differ from the pristine fixture's published result. Mutation mode runs these checks against the supplied correct original and its three fixed mutants, not against your edited candidate.py. verify_demo.py belongs only on the pristine copy. If an unexpected exception interrupts a mutant run, diagnose it; do not count every process failure as a kill.

    Records

    Keep the parser/test diff, snapshot revision, command, seed, relevant actual exit/output, counterexample and a brief explanation together. Note AI use once and reuse the same ID in the testing workshop and M1; no separate disclosure file or full conversation is required. Keep your tests and explanation attributable to you.

    For M1, name the Week 7 snapshot functional baseline and identify characterization tests, repairs, locked upgrade state, CI result and unresolved security items. The CI result is the exit status and summary output of your own offline gate command, as defined in the notes. It is not final M1 acceptance. After the Week 8 security teaching and the security workshop, close every known planted vulnerability and scanner item, then seek M1 final acceptance. A green gate run does not replace your explanation in the testing workshop or a checkpoint.

    Review

    The peer reviews correctness of the oracle, reproducibility and the baseline claim; the author makes one visible revision. These public tools do not issue formal grades.

    Keyboard, text and equivalent participation

    All materials, code, inputs, outputs and slide content have plain-text paths. Use a keyboard-only editor and terminal; no dragging, color distinction or timed pointing is required. The instructor reads inputs and failure categories aloud. Pair roles can rotate through typed observations rather than spoken performance.

    If you cannot run the practices yet, annotate this synthetic text walkthrough: input "3" returns 3; input "12" returns 1 in the faulty parser despite the contract; input "" attempts indexing and raises IndexError. Predict which assertion or property distinguishes each case, then explain the proposed repair and M1 boundary. This text exercise provides learning support, not actual execution evidence.

    Your instructor can approve typed or asynchronous explanation, additional time or an equivalent supported device or interaction with the same LO, verification and individual evidence. Such a path keeps the same attainable marks; ask through the course support route. Required execution still needs the Week 0 launcher. See current fallbacks.

    Your C2 contribution

    C2 starts this week on the project, issue and scope approved before Week 7, and continues through Week 13; it is due in Week 13, before your individual defense. Plan it alongside the project work each week. The test habits from this page carry over: before you change upstream behavior, add a test that fails without your change. See the syllabus.
