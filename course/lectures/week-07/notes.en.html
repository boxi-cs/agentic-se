    Week 7: Testing and verification with agents

    Learning objectives

    • LO4: preserve a legacy module's intended behavior during a repair, connect its regression evidence to your offline gate command, and explain what an M1 functional baseline establishes.
    • LO5: challenge generated tests with an independent oracle, a property, a mutation and a reproducible fuzz input; explain the limits of each result.

    The activity and self-check map to both outcomes. LO4 is assessed individually in CP1 and the individual defense. LO5 is assessed individually in P2 and through CP1/CP2. The testing workshop feeds M1. A green run does not replace your own explanation of each failure and pass, and project work does not replace checkpoint work.

    M1 timing: Week 7 produces a reproducible functional baseline snapshot showing the state of characterization tests, defect repairs, dependency upgrades and your CI result. This is not final M1 acceptance and does not establish that security work is complete. After the Week 8 security teaching and the security workshop, close all known planted vulnerabilities and scanner items, then undergo M1 security closure and final acceptance.

    CI result in this course means the exit status and summary output of your own offline gate command: the one command your agent-readiness Checks row names, run on the baseline revision. If you do not have a gate command yet, record the test command you ran and say that no gate command exists yet. If a command could not run, record "not executed" and the reason instead of a result.

    Minimal example

    The continuing dashboard case

    The dashboard level field accepts exactly one ASCII digit and rejects every other string with ValueError. The supplied candidate passes the ordinary input "3" and the current happy-path test:

    def parse_level(text: str) -> int:
    if text[0] in "0123456789":
        return int(text[0])
    raise ValueError("Invalid level")

    Decision: What rejected input can distinguish the candidate from the product contract?

    For "12", the candidate reads only the first character and returns 1. For "", indexing crashes with IndexError instead of the required ValueError. These are two different defects. Derive rejection cases from the single-ASCII-digit contract; valid-input properties alone miss this boundary. The exit variation later considers a different candidate, int(text), under this same contract.

    Generate a test for an independently stated invariant. Mutate a correct candidate, inspect surviving mutants and choose an input that can distinguish the changed behavior.

    Acceptance decision: Accept a test improvement when it detects a meaningful fault while preserving valid behavior. Explain the mutant denominator; a score by itself does not identify the remaining risk.

    The integer-parsing fixture represents the level field in the continuing case. Keep its deliberately narrow input contract fixed when judging candidate tests.

    This is a course-authored, hand-worked example. Actual execution evidence comes from your own checks.

    Specify the oracle before asking for code

    This is a course-authored synthetic slice of the dashboard level field. A legacy configuration field represents a level. Its input domain is Python strings; callers are responsible for supplying a string. Its contract is:

    requires: text is a string
accepts:  exactly one of "0", "1", ..., "9"
ensures:  an integer with the corresponding value, with no state changes
rejects:  every other string by raising ValueError

    Thus "3" maps to 3; "12", "", whitespace and a non-ASCII digit are rejected. Exception message wording is deliberately unspecified. This lightweight specification is precise enough to make examples and properties executable. It is not a formal proof. A test explores selected executions; even complete enumeration of the ten accepted strings does not cover the infinite rejected-string domain.

    Before generating a repair, write assertions for "3", "" and "12". Inspect the supplied candidate as text:

    def parse_level(text: str) -> int:
    if text[0] in "0123456789":
        return int(text[0])
    raise ValueError("Invalid level")

    Characterize the intended "3" behavior, but do not preserve acceptance of "12" merely because the old implementation does it. Record that disagreement as a defect against the explicit contract. For a real legacy ambiguity, seek a requirement decision before changing the oracle. An agent cannot settle the requirement by copying the code.

    Red, generate, green, then challenge green

    Run all commands through the activity's launcher route. First run demo.py unit against the supplied candidate: it fails on the empty string with IndexError, where the test expects ValueError. In class the instructor replays "12" separately to show silent acceptance rather than a crash. A failed test due to an import or missing dependency is a setup problem, not a demonstrated behavioral defect.

    Now propose a repair in your editor: check the length before indexing, and require one ASCII digit. Test the proposal through the same launcher. The public repaired function in demo.py supplies a worked comparison when you need help. It is teaching support, not a hidden testing workshop solution. Rerun the original tests unchanged. Then ask which defect could still pass them and add a distinguishing test. Only after this evidence should a refactor be considered; rerun again on the refactored revision.

    This is agent TDD: the person fixes the intended behavior and reviews the tests before generation; the agent may propose tests or an implementation; actual execution judges the proposal. These supplied proposals are synthetic AI-style examples, not recorded model outputs. If you use an agent through the Week 0 route, give it only this public contract and fixture, and execute its test, harness and repair proposals through the course launcher. Do not give it private teacher tests, credentials, real user data or unrestricted shell/network access.

    Three assertions that cannot distinguish a wrong result

    The following course-written sample represents an AI-style weak test. For the supplied integer-returning candidates, all three assertions pass even when the result is wrong:

    result = parser("3")
assert result == result
assert parser
assert result or True

    Explain each assertion's blind spot before replacing it. The call can still crash; these assertions do not make a program immune to exceptions. The activity asks for three meaningful replacements and evidence that each checks the contract rather than echoing the implementation. An agent's confident explanation is not that evidence.

    A property describes a family of inputs

    For every integer n from 0 through 9, parsing str(n) must return an actual integer in range and round-trip to str(n). The public property_checks enumerates this whole small valid domain. It detects a constant-return parser that one happy-path example misses. It still passes the faulty candidate: rejection behavior needs its own checks.

    In a larger property test, choose generators from the input domain, define invariants or relations independently of the implementation, and retain counterexamples. A round-trip between two equally faulty functions can agree for the wrong reason; here the independent numeric enumeration supplies the expected values. The classroom uses standard-library enumeration to expose the principle. It does not replace the course's selected property-testing tooling or the testing workshop's required explained property.

    Mutation tests ask whether a defect would be noticed

    Our bounded mutation demo changes a correct original in three ways: return zero for all accepted strings, return zero only for "9", and accept trailing characters. First require the original to pass. Then run the same suite separately against each mutant. A mutant is killed when an assertion detects its changed behavior. A survivor shows a change the suite cannot see. It stays a survivor until a test kills it or a written contract reason shows that it is equivalent.

    For this fixed classroom set, the weak suite kills 0 of 3, and the unit-plus-property suite kills 3 of 3. These are reproducible course fixture counts, using Python 3.12 and demo.py mutation through the launcher. They are not industry statistics, a testing workshop feedback goal or a course grade. The report names every mutant and its outcome.

    In a real report, state the tool/configuration, original revision, tests, selected mutants and denominator. Investigate timeouts, invalid mutants and infrastructure failures separately; do not relabel them as behavioral kills. For this contract, a mutation changing only a ValueError message is equivalent and is excluded with that reason. The testing workshop's project fixes its denominator the same way: its public mutant_manifest.json, beside the mutants.json configuration, gives each equivalent or control entry a kind and a reason. Its scorer also reports a feedback_score, which is formative feedback only and never enters the course mark. Do not remove a surviving non-equivalent mutant just to improve that number. Line coverage records execution; mutation evidence asks whether a particular change was detected. Neither proves general correctness or security closure.

    Fuzz the boundary, then replay the input

    The supplied fuzz function generates nine explicit boundary inputs plus 100 strings from a fixed alphabet with maximum length four, using a caller-specified seed. It compares observations with a separate mapping of accepted strings to values. Expected ValueError on an invalid string is normal; unexpected exceptions, accepted invalid strings and wrong results are findings. Catching every exception and returning success would hide the defect this harness is meant to discover.

    In class the instructor runs demo.py fuzz --seed 7 on the unmodified fixture. The first finding is the boundary seed "" causing unexpected_IndexError. This is seeded discovery, not a claim that random search discovered it. It is already minimal by string length. The instructor replays it with demo.py replay --text ''; keep the exact input and add it as a regression before repair. "12" is replayed too: fuzzing must detect an incorrect result as well as crashes. You rerun both replays on your repaired workspace. For a longer finding, delete characters while preserving the same failure category; save the reduced input even when you also retain the seed. A seed alone may not reproduce a changed generator or runtime version.

    An agent can propose an additional harness input or oracle, but independently check both and verify the harness on a known-bad and a repaired target. Extending this supplied harness is optional. The bounded random run is not exhaustive, coverage-guided fuzzing or a proof that no other defect exists. It uses only synthetic strings.

    Let the agent propose the harness, then verify it dynamically

    An approved model can propose a property strategy, a mutation command or a small fuzz harness for the ci-dashboard validation boundary. Treat that response as a list of claims and candidate code. Inspect the oracle and run the proposal through the launcher; never let the proposal choose its own score or mutate the scoring tool. The locked course mutator changes the validation implementation from a fixed seeded configuration and reruns the submitted tests, while the course's standard-library property helper supplies bounded, reproducible examples. Dynamic results decide whether a claim survives. Week 3's mature-agent dissection applied the same rule to an agent's final summary: "all tests pass" stays a claim until a test result in the record, or your own launcher run, shows it.

    For each surviving non-equivalent mutant, record the mutant, the missing observation and the model claim it challenges. Keep equivalent changes (such as an unspecified error-message wording change) outside the denominator with a written reason. A timeout, missing dependency or launcher failure is infrastructure evidence and is not a kill. Add one property with an independent expectation, then replay the same seeded fuzz input against the repaired revision. This is the verification loop of the testing workshop's agent-generated tests step. Without a key, start from its frozen replay response, a fixed proposal that you inspect and score the same way.

    The workflow reflects the role of generated harnesses in current fuzzing practice; see the registered tool cards (tools/oss-fuzz-gen; as_of: 2026-09-05; Source 1; Source 2; Source 3) and (tools/fuzzingbrain; as_of: 2026-09-05; Source 1). Those cards are context for the method, not performance claims about this course fixture.

    Hands-on exercise

    Use the 55-minute activity, including peer feedback and visible revision. Keep one work product with its verification and short explanation, and add AI use once (or state no AI use). Reuse that evidence in the testing workshop and M1 where relevant; no second report or full conversation export is required. Personal reflection stays AI-off. Optional harness extensions do not change the full-mark requirements.

    Week 7's published estimate is 12 total hours, including about two hours on your C2 contribution; the testing workshop's four-hour time box includes its workshop, verification and explanation. The activity fits within that work rather than adding another assignment. These are help and design checkpoints, not measured durations, penalties or automatic stopping rules. Ask for support if setup consumes the time box; do not move execution onto the host to catch up.

    The main line of the testing workshop is mutation testing against its published feedback goal, one explained property and running the supplied fuzz example to explain a planted defect. Its own assignment supplies its feedback tool and feedback goal; this lecture invents neither. Reuse your test changes and failure/pass evidence in your M1 repository. The Week 7 baseline records commit, locked environment, commands, CI result (your offline gate command's result, defined above) and open security items. Week 8 teaching and the security workshop precede closure of all known planted vulnerabilities and scanner items and M1 final acceptance.

    Verification

    The execution route contains complete copyable commands, resolves the offline profile and copies only public fixture files. Every test, mutation and fuzz invocation stays inside scripts/course-sandbox, with no external network, host credentials or teacher assets. Complete the Week 0 launcher check first.

    Read the launcher's actual exit code and bounded output, not just a printed success label. Expected candidate results: weak passes, valid-domain property passes, unit fails, fuzz fails, empty-input replay fails. Expected repaired results: unit/property pass, fuzz has no findings in its stated corpus, and both replays pass. Mutation counts are 0/3 weak versus 3/3 strong. verify_demo.py checks these expectations, seed reproducibility, invalid strings and oracle failures inside the launcher.

    If a student changes the public checks to print success, that proves nothing about the parser. These are editable formative tools, not an authoritative scorer. Keep the contract and expected outputs fixed during repair, inspect the diff, and rerun the tests on the exact candidate used for the baseline. Preserve an unexplained failure as unresolved. Failures of launcher safety checks stop execution entirely.

    Common mistakes

    Mistake How to notice it Corrective action
    Generate implementation and derive all expected values from it Wrong result equals the same wrong result Write the contract oracle first; use explicit counterexamples
    Preserve a planted defect as characterization "12" is accepted despite the requirement Separate observed behavior from approved behavior
    Claim properties prove correctness Valid digits pass but empty input crashes Include invalid-input obligations and report tested domains
    Count any failed mutation run as a kill Missing dependency or timeout replaces an assertion Diagnose infrastructure separately and report every disposition
    Swallow fuzz exceptions Known-bad target reports no findings Check the harness against known-bad and repaired targets
    Treat a green gate run as security evidence or as your explanation Security items remain open, and the run does not say which behavior each test checks Record what the gate runs, explain your test changes, label the Week 7 functional baseline and finish security closure in Week 8

    Transfer to a new situation

    A property checks that parsed values are non-negative for generated digit strings. Does it cover negative or decorated inputs?

    Write the expected behavior and the next check before comparing with a partner.

    Testing workshop evidence goes directly into the M1 functional baseline.
