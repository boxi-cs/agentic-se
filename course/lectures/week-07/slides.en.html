    Challenge the tests

    Week 7 · CI dashboard

    Would our tests notice a meaningful fault?

    A passing check still has a boundary

    Week 6 required evidence for a review claim. This week we inspect the checks themselves.

    The dashboard's level field accepts exactly one ASCII digit.

    The parser contract

    Input: a Python string.

    Exactly "0" through "9" return the corresponding integer. Every other string raises ValueError.

    Exception-message wording is unspecified. There are no state changes.

    The actual public candidate

    def parse_level(text):
    if text[0] in "0123456789":
        return int(text[0])
    raise ValueError("Invalid level")

    parse_level("3") == 3 passes.

    Two invalid strings, two different failures

    Trace "12" and "" through the candidate.

    For each, state the required behavior and the predicted behavior. Keep the exception type precise.

    Acceptance and rejection are both behavior

    Input Contract Candidate hand trace
    "12" ValueError Returns 1
    "" ValueError Raises IndexError

    The first silently accepts invalid input. The second fails through an unintended exception.

    Mechanism: Red, generate, green, then challenge green

    You fix the contract and tests first. The agent only proposes; a launcher run on the unchanged tests decides.

    A length check before indexing

    if len(text) == 1 and text in "0123456789":
    return int(text)
raise ValueError("Invalid level")

    Keep the rejection tests and valid cases unchanged during repair. Then challenge what the green suite might still miss.

    Which assertion compares with the requirement?

    result = parser("3")
assert result == result
assert parser
assert result or True

    Could all three pass if the result were 0? What could still make the function call fail?

    An oracle supplies an independent expectation

    assert parser("3") == 3

    The contract supplies 3; the candidate does not. The weak assertions can accept a wrong integer, though the call can still crash.

    Replace them with a value check, a boundary case and a rejection check.

    A property covers a family of inputs

    For each integer n from 0 through 9:

    result = parser(str(n))
assert type(result) is int
assert result == n

    Here the valid domain is small enough to enumerate completely. The rejected-string domain is still untested by this property.

    Deliberate faults test the tests

    A mutant is an intentionally changed implementation. A behavioral assertion failure kills it.

    Which faults survive one happy-path test?

    The only assertion is parser("3") == 3.

    Mutant Deliberate change
    all_zero Every valid input returns 0
    nine_to_zero Only "9" returns 0
    accept_trailing Accept a digit followed by extra text

    Predict killed or survived for each.

    Survivors point to missing cases

    all_zero is killed by "3". nine_to_zero survives; "9" -> 9 distinguishes it. accept_trailing survives; "12" -> ValueError distinguishes it.

    A survivor shows a change the suite cannot see. It stays a survivor until a test kills it or a contract reason shows it is equivalent.

    The denominator has a meaning

    Report which mutations were selected and each outcome.

    An error-message-only change is equivalent under this contract. A missing dependency or timeout is infrastructure evidence, not a behavioral kill. The testing workshop's scorer reports a feedback_score: formative feedback only, never a course mark.

    Do not discard an unexplained survivor to improve the score.

    Fuzzing searches beyond the chosen examples

    A harness generates inputs and compares each observation with the independent contract.

    The supplied harness combines explicit boundary seeds with bounded random strings. It accepts a reproducible seed.

    Expected ValueError is normal; unexpected acceptance is a finding too.

    A finding must survive replay

    input: ""
reason: unexpected_IndexError

    Why is this a defect? What is the regression expectation? Does a saved random seed alone identify this exact input forever?

    The input and failure category make replay useful

    Retain the exact string and expect ValueError after repair. The empty string is already minimal by length.

    For a longer input, remove characters while retaining the same failure. Keep the generator/runtime version as well as its seed.

    An agent proposes a harness; execution verifies it

    Give the approved model one M1 contract and ask for tests, a property and a bounded fuzz input.

    Run the proposal through the launcher, then let the locked, seeded course mutator change domains/validation.py and rerun the tests. The course mutator is a local, standard-library tool; (tools/oss-fuzz-gen; as_of: 2026-09-05; Source 1; Source 2; Source 3) and (tools/fuzzingbrain; as_of: 2026-09-05; Source 1) are context for the model-proposed harness pattern, not tools used by this run.

    Record each surviving mutant, the claim it challenges and the independent property you added.

    Steps and a no-key frozen replay: agent-generated tests.

    Workshop: improve your own checks

    Replace the weak assertions, run your changed suite on the faulty candidate, and retain the failed result before repair.

    Then compare the repaired behavior and the supplied mutation/fuzz runs. Keep the pristine fixture separately for its published comparison.

    Feedback on an untested domain

    A peer observes that your property generates only valid digits.

    Add an invalid-input obligation and explain why it reaches behavior that the original generator never visited.

    Exit: conversion is not this contract

    A fresh proposal simply returns int(text).

    Give an input it accepts that this contract rejects. Would checking only that the returned value is non-negative expose it?
