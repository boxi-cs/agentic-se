    Week 4: Requirements, user discovery and specification-driven development

    Learning objectives

    By the end of this lesson, you can:

    • LO3: replace a leading question with a question about a concrete event; distinguish an observation, an inference and an unanswered question.
    • LO3: connect discovery evidence to a problem statement, a small product requirements document (PRD), an acceptance criterion and an executable test.
    • LO9: explain when evidence may be used, what must be removed, and why a synthetic exercise cannot prove real participation or approved equivalence.
    • LO3, LO9: diagnose a generated implementation against the agreed criterion, revise it after feedback, and explain both the verification and its limits.
    • LO3: carry agreed acceptance criteria into a staged delegation (research, propose, plan, implement, test), decide at a checkpoint after each stage, tie every plan step to a check derived from a criterion, and record where you stopped or narrowed the task.

    The activity and self-check map each output to these outcomes. Every scenario and data value in this lesson is invented for teaching; none of it is discovery evidence for M0.

    Minimal example

    The continuing dashboard case

    A fictional maintainer wants to isolate failed runs. Scenario S4-A below supplies the event, input and workaround. The classroom implementation returns unique failed IDs in ascending order; this ordering is an explicit exercise decision, not a participant preference. Use the same contract through the worked example, tests and first repair. The slide's later first-occurrence ordering question is a new agreed requirement, not the original oracle. "Latest per pipeline" would require additional fields and a separate product decision.

    Discovery before a feature request

    Fitzpatrick's Mom Test teaching guidance emphasizes improving questions and recognizing biased data. Jobs-to-be-Done (JTBD), as described by Ulwick, focuses on the underlying job a customer wants to accomplish rather than the product. (studies/user-discovery; as_of: 2026-09-08; Source 1; Source 2)

    Use these course interview practices to apply that focus:

    1. Ask about a specific past event: "Walk me through the last time you checked a run."
    2. Ask what happened, what the person tried and what remained difficult. Avoid pitching a solution or asking for predictions such as "Would you use our smart dashboard?"
    3. Listen and follow up without supplying the answer. A compliment does not establish a requirement. Keep contradictions and uncertainty in your own notes.

    Scenario S4-A: A fictional project maintainer checks run results before deciding which failed job to investigate. The supplied run list is [(12, "passed"), (9, "failed"), (11, "running")]. In the fictional event, a "not passed" filter displayed runs 9 and 11. The maintainer opened run 11, found it still running and returned to the list. A handwritten list of failed run IDs was the workaround. The maintainer wants to inspect failures; there is no evidence of a need for notifications, user tracking or automatic retries.

    Do not add personal experiences, real repositories, screenshots, recordings or participant details to this practice.

    Evidence step Our worked example What we still cannot conclude
    Observation S4-A The fictional filter included a running job How common this is in real work
    Inference Mixing running and failed jobs may distract from investigating failures Whether a separate filter is the preferred interface
    Follow-up question "What did you do after opening the running job?" Whether alerts would help
    JTBD frame (course wording) When checking run outcomes, I want to identify failures so I can choose a job to investigate That every maintainer has the same job
    Problem statement P1 The fictional maintainer cannot isolate failed runs because the current filter also includes running runs That a particular technology is needed

    Generate the statement by hand, then verify each clause against S4-A. Remove "everyone needs instant alerts": neither "everyone" nor alerts has supporting evidence. This is also the boundary for M0's yellow AI rule: the student owns the problem statement and its reasoning; use AI only within the actual assignment's specified assistance scope. Discovery notes and reflection remain AI-off throughout.

    A small PRD and one criterion

    A PRD records the problem, intended user, desired result, scope and unresolved choices. It is a decision document, not a list of tools. This course example needs only:

    • P1 / evidence: S4-A, explicitly synthetic; one fictional maintainer's task.
    • Outcome: obtain the IDs of failed runs to support manual investigation.
    • In scope: a pure function failed_ids(runs) over a list of (id, status) pairs.
    • Agreed assumptions: IDs are integers; status is passed, failed or running. Each pair describes an input observation. Repeated failed IDs appear once in output.
    • Non-goals: a web UI, login, notifications, network access, retries, persistence and validation of malformed input. These need separate requirements if adopted.
    • Open question: what order best supports the user's next decision? For this example we choose ascending ID order as a deterministic design decision, not an interview finding. Record that distinction and revisit it with appropriate evidence.

    AC1: Given any list satisfying those input assumptions, when failed_ids is called, then it returns the ascending, duplicate-free list of IDs whose status is exactly failed. It returns [] if there are no failures and leaves the input unchanged.

    AC1 replaces the ambiguous "show jobs needing attention." It specifies observable behavior; it does not prescribe an algorithm. Acceptance tests can check this function contract but cannot establish that the product is useful or that consent exists.

    Generation, failure, diagnosis and repair

    First predict the result for S4-A without executing anything. A plausible generated candidate uses the wrong predicate:

    return sorted({run_id for run_id, status in runs if status != "passed"})

    It returns [9, 11]; AC1 requires [9]. The problem is the interpretation of "needs attention," not Python syntax. Repair the predicate to status == "failed" and run the same test again. Also test empty input, no failures, ordering, repeated IDs, a different ID and input preservation. The public example contains the complete failing and repaired implementations and executable checks. Use only the launcher commands in Verification to execute them.

    Trace the decision: S4-A -> P1 -> AC1 -> AC1-mixed -> predicate repair. The sorting/duplicate rules are explicit design choices. A passing test of those choices does not retrospectively turn them into interview evidence.

    Spec Kit and specifications as source

    Spec Kit documents a workflow of principles, specification, plan, tasks, implementation and convergence against the artifacts. Its optional analysis reads the specification, plan and tasks and reports conflicts, gaps and ambiguities without editing them. (tools/spec-kit; as_of: 2026-10-09; Source 1; Source 2; Source 3; Source 4)

    Use the constitution -> spec -> plan -> tasks sequence to organize this example:

    Artifact Course example Verification before moving on
    Constitution No personal data; no network; changes need behavior checks Confirm input provenance and launcher boundary
    Spec P1, input assumptions, AC1 and non-goals Trace the problem to S4-A; label design choices
    Plan Pure function plus public checks; no service or database Check that the plan can implement every AC1 clause
    Tasks Write counterexample; implement filter; verify; explain limits Every task names an artifact and its check

    Then generate the small implementation and compare code, tests and spec. We practice the artifacts here without installing a Spec Kit integration or adding an unapproved model. Tool-specific setup belongs to the approved environment for the actual practice unit.

    "Specifications as source" means versioning intent and reviewing its changes alongside tests and code. A requirement change should identify affected tests and implementation; a code change should still satisfy the current requirement. Record each agreed change under the Change log heading of the feature specification template: the changed clause, the acceptance cases and tests it affects, the reason and who agreed. Prose is not automatically executable, complete or true. A mistaken spec can produce consistent but unwanted code. An AI consistency report is a review input, not a proof of correctness or authorization.

    Delegating against the specification in stages

    AC1 says what must be true. It does not say how to hand the work to an agent. One request such as "implement AC1" asks the agent to research, choose, plan, write and judge in a single step, and you only see the end. Split the delegation into five stages instead: research, propose, plan, implement, test. Different workflows name these stages differently; the names matter less than the stop after each one. At every stop a person reads what the stage produced and decides: continue, narrow the task, return to an earlier stage, or stop. An agent can draft the output of every stage. It cannot make those decisions for you, and it cannot be the one who checks its own result.

    Use the course-written research-codebase skill for Research and plan-change for Plan, here and in your M0 round. They return the located claims and the plan tables this lesson checks; the stops stay yours.

    Each stage hands the next one a file. End every stage with a short written artifact: research.md holds the located claims you kept, plan.md the step-to-check table. Start the next stage in a fresh session that reads only that file and the paths it names, not the conversation that produced it. The next session then starts from what you checked rather than from every guess and dead end along the way, and the file is something a partner can review. The order matters too. A wrong research claim becomes a wrong option, then a wrong plan step and wrong code, so striking it at the first stop is the cheapest repair in the round.

    Choose the least elaborate delegation that still leaves you an independent check. A direct prompt fits a small change in code you already know when one acceptance case can check the result. Start with a plan when the change is bounded but you need to agree the files and checks first. Research before planning when the repository or call path is unfamiliar and the acceptance case can be made concrete after the map. Use repeated research-to-plan rounds when the scope or boundary is still uncertain and several acceptance cases must be negotiated. The last two levels use research-codebase followed by plan-change; stop and narrow whenever the next check is not yet observable.

    Delegation level Use it when ci-dashboard example Handoff
    Direct prompt The edit is small, the code is familiar, and one acceptance case can check it Rename the label in a known status component and run its existing rendering check One bounded request and its result
    Plan first The edit is bounded, you know the area, and one acceptance case can check the planned files Add the empty-state branch to a familiar builds view and map each step to its check plan-change output before implementation
    Research then plan The path crosses unfamiliar files, and one acceptance case can be made checkable after tracing Trace the /projects/<id>/builds status filter, then plan a change to its handler and template research-codebase record, then plan-change
    Multiple research → plan rounds The boundary is uncertain, you know little of the path, or several cases must be agreed Trace status filtering and the permission boundary, revise the scope, then plan each bounded slice A checked research record and a revised plan at each stop

    Here is one round for the failure filter. The agent, whether a model or you playing its part, reads only the public example directory, and generated code runs only through the launcher.

    Stage What you ask for What must come back Your checkpoint
    Research "Read README.en.md, acceptance.py and run_example.py. Change nothing. Report what already exists for AC1, citing file and function." Claims with locations, such as "acceptance.py CASES has six cases; verify also fails if the input changes" Open each cited location. A claim without one is a question, not a finding
    Propose "Give two or three ways to meet AC1 within the non-goals; for each, what changes and what could break." Options with trade-offs You choose and write down why
    Plan "List the steps for the chosen option. Name the AC1 check that shows each step is done." Steps, each with an observable check Every AC1 clause has a step; every check existed before the code
    Implement "Write only failed_ids in one new file. No imports. Do not edit acceptance.py." One bounded change Read the diff as text; reject anything outside the bound, even if it passes
    Test Run the existing checks in the launcher Launcher JSON exit_code plus the first failing case/output, or the one summary line after all cases pass Record the failure and the stage to revisit; checks after a failure are not run, not passed

    repaired already implements AC1 and remains the worked reference; the delegation round must preserve that oracle while it evaluates a new candidate.

    At Propose, suppose the agent offers three options. (A) Change the predicate inside broken: smallest diff, but it removes the counterexample the class relies on. (B) Add a separate failed_ids checked by the same verify: one new function, and the counterexample stays. (C) Add a status option to the run list screen: a web UI is a non-goal. You choose B. Rejecting C is a scope decision from the PRD, not a technical judgment, so write it down as one.

    At Plan, each step points to a check written from AC1 before any code existed:

    Step AC1 clause Check
    Keep only status exactly failed "whose status is exactly failed" AC1-mixed, AC1-no-failures
    Return each ID once "duplicate-free" AC1-duplicate
    Sort ascending "ascending" AC1-sort
    Handle no runs "returns []" AC1-empty
    Use the input, not fixed values the whole criterion AC1-other-id
    Do not change the input "leaves the input unchanged" the input was modified assertion

    Use the feature specification template for this plan: list each permitted changed file with its relevant line number (or new), and list each test separately against its acceptance case. Implementation may change only those files; revise and check the plan before adding another file.

    If a step has no check, you either write the check first or drop the step. The plan is where you narrow: if ordering were still disputed, you could take only the first two rows now and record the ordering question as open.

    At Implement, the bound is part of the request. The model mode of run_example.py sends exactly such a bounded request; read its prompt and check that it names every clause in your plan. It exports candidate.py and stops. Without a model, the three course candidates are what you read at this stop. Read the candidate as text before starting Test with the separate launcher command below. A failure tells you where to go back. A wrong predicate returns you to Implement. A clause the plan never covered returns you to Plan. A misread requirement returns you to Propose or Research. Do not repair a failure by editing the check.

    Record the round in a few lines: the brief for each stage, what came back, your decision at each stop, and where you stopped or narrowed the task. Stopping after Plan because the first step is not yet small enough is a legitimate result.

    A worked round on ci-dashboard

    The failure filter fits on one screen. Here is the same round on the project repository, ending in a stop after Plan. The course wrote this record; no model was called. Line numbers refer to the course's starting capstone/legacy/ci-dashboard, so open each one before you accept a claim. This slice is the worked example; choose a different one for your own M0 round.

    AC-W (written for this example): given a signed-in owner with one active and one archived project, when the owner opens the overview, then the active project is listed and the archived one is not. The archived project's own page still opens.

    Research with research-codebase returns four claims:

    Claim Location After opening it
    R1. overview selects the caller's projects WHERE owner_id=? ORDER BY id and renders ci/overview.html domains/ci_dashboard.py:28-38 Keep
    R2. The template prints one row per project with an Archived or Active label; its {% else %} branch prints No projects yet. only when the list is empty legacy_app/templates/ci/overview.html:17-24 Keep
    R3. archive_project flips archived and redirects to the overview; it deletes nothing. The Unarchive button is on the project page domains/ci_dashboard.py:96-106; legacy_app/templates/ci/project.html:6-8 Keep
    R4. "The overview query already skips archived projects, so only the label needs to change." domains/ci_dashboard.py:34 Strike: the query has no archived condition

    If R4 had survived, the plan would have changed only the label, and the archived project would still be listed.

    Propose. (A) Add AND archived=0 to the overview query at domains/ci_dashboard.py:34. (B) Keep the query and wrap each row of the template loop at overview.html:17-23 in {% if not project.archived %}. B touches only the template, but for an owner whose projects are all archived the loop still receives rows, so the {% else %} branch never runs and the table is blank. Choose A, and record that B was rejected for a case you could name before any code existed.

    Plan. Changed files: only domains/ci_dashboard.py:34. Tests to write, one per clause:

    Test AC-W clause Expected result
    test_overview_hides_archived the active project is listed and the archived one is not the active title appears; the archived title does not
    test_archived_project_page_opens the archived project's page still opens status 200 for that project's page

    Stop. Writing the tests exposes a case AC-W never names: an owner whose projects are all archived. With A, that owner reads No projects yet. (overview.html:24), which is untrue, and the only way back to the Unarchive button is to type the project's URL. Neither is a code question. The round stops after Plan: record both questions against AC-W and take them back to the specification before anyone edits code.

    Hands-on exercise

    Complete the 10-minute, AI-off discovery activity in activities.en.md. It uses a fresh case, S4-B, so you practise these moves on input you have not seen worked. Work from the provided text, individually or in pairs. Produce a question revision, your own short observation/inference record, a problem statement and one acceptance criterion. A silent keyboard-only path uses exactly the same input and outputs. No personal disclosure or real participant recruitment is required.

    Use another 25 minutes within class for the staged delegation round: take AC1 through research, propose, plan, implement and test, stop at each checkpoint, and run the launcher checks. Get peer feedback on one plan step whose check is weak and revise it. At Implement you read the three course candidates as text, or generate one through the optional hosted route; Test then runs them in the launcher. Ask for help after five minutes without an explainable failure. If setup is unavailable, trace the cases on paper or in text and label them not executed.

    Then carry one round into your personal M0 project outside class (about 45 minutes). Pick one acceptance criterion, by its AC-n ID, from your personal M0 feature specification and the smallest slice of the ci-dashboard feature that it constrains, other than the worked overview slice above. Research uses research-codebase, as in class. Implement only if the first planned step is small and bounded; otherwise stop after Plan and say so, because the reviewed change itself belongs to M1. Write the round into your personal M0 work record, citing the criterion by its ID. The specification itself stays as it is, and the round is not a separate submission.

    The M0 feature specification holds AC-1 through AC-3 as Given/When/Then criteria, each traced to exactly one [interview:ID]. The workshop's remaining(capacity, requested) function is an optional warm-up, not the M0 task. Reuse discovery IDs where the actual topic is relevant and consent covers both uses.

    Before actual discovery or reuse

    Before any activity with a real participant, follow the course participation rules and the discovery workshop's input and privacy rules. Obtain active consent first, collect only what the task needs, and write and de-identify your notes yourself, without AI. Participant material, de-identified or not, never goes into a model prompt. If someone withdraws, stop using their material and remove it with your teacher. An approved alternative keeps the same learning outcomes, analysis steps and maximum score.

    Verification

    Run the public example inside the launcher

    Use the approved hosted or replay route in Week 0 setup. Run code only after that page's check shows you can run the practices. Independent assessments remain AI-off.

    From the trusted course root, resolve the course profile:

    uv run --locked python scripts/hosted_profile.py --profile approved-hosted --json

    Replace VERSION and DIGEST below with the returned version and digest. They are explicit placeholders, not additional model settings. Use the public example directory alone; never mount the private course checkout, teacher answers or credentials. These commands preserve the launcher's network, filesystem, CPU, memory, process and timeout limits.

    sh scripts/course-sandbox --profile approved-hosted --version VERSION --digest DIGEST --workspace lectures/week-04/example -- python run_example.py broken
sh scripts/course-sandbox --profile approved-hosted --version VERSION --digest DIGEST --workspace lectures/week-04/example -- python run_example.py repaired

    The first invocation is expected to fail: AC1-mixed: expected [9], got [9, 11]. The repaired invocation must have container exit_code: 0 and AC1: all public checks passed; this is practice feedback, not a grade. Read the launcher's actual JSON result; a printed success line alone is insufficient. Safety probes take time on every invocation. A safety failure stops execution; do not change the limits or switch to host execution to finish the exercise.

    Implement and Test without a model

    The three course candidates are versions of failed_ids that the course wrote; no model was involved. At the Implement stop, read each one as text and decide whether it stays inside the bound before you test it. Then run Test on each:

    sh scripts/course-sandbox --profile approved-hosted --version VERSION --digest DIGEST --workspace lectures/week-04/example -- python -c 'from candidates.candidate_a import failed_ids; from acceptance import verify; verify(failed_ids)'

    Replace candidate_a with candidate_b or candidate_c for the other two. Record each JSON exit_code and the first failing check or the all-pass line next to the decision you wrote before running it.

    Optional live generation

    With your own key on the hosted route, generate one more candidate. Choose a new output directory for each attempt:

    sh scripts/course-sandbox --profile approved-hosted --version VERSION --digest DIGEST --model api --hosted-config HOSTED_CONFIG --key-file ~/.config/course/hosted-key --workspace lectures/week-04/example --output week4-candidate-01 -- python run_example.py model

    Without a key, the course candidates above are your Implement and Test material. If your instructor names a Week 4 replay record, replay it by replacing --model api --hosted-config HOSTED_CONFIG --key-file ~/.config/course/hosted-key with --model replay --replay-file REPLAY_FILE --replay-digest REPLAY_DIGEST.

    Generation sends only the supplied synthetic specification through the broker's course_llm call and saves a candidate. It does not ask AI to write discovery notes. The separate Test invocation reports syntax errors, truncated responses, incorrect behavior or timeouts as failed attempts. Inspect the emitted candidate as text before starting Test; never execute exported code on the host. The launcher writes the output directory only on success; a failed attempt keeps the emitted artifact in its bounded JSON result.     Common mistakes

    Mistake How to notice it Correction
    Asking "Would you like our feature?" The answer supplies approval but no concrete event Ask about the last occurrence and workaround
    Treating a design choice as a user finding No observation supports sorting or duplicates Label the decision and state how to revisit it
    Equating not-passed with failed A running item appears in AC1 output Use the exact agreed status predicate
    Writing tests from the implementation only Both repeat the same wrong interpretation Derive expected results from AC1 and critique a fresh case
    Delegating all five stages in one request You first see the agent's work when the tests run Stop after each stage and record a decision before the next
    Accepting research without locations A finding names no file or function you can open Treat it as a question and ask for, or find, the location
    A plan step with no check You cannot say what would show the step is done Derive a check from a criterion clause, or drop the step
    Letting the implementation widen The diff touches checks, other files or non-goals Reject the change, restate the bound and narrow the plan
    Fixing a failed check by editing it The check changes in the same diff as the code Go back to the stage the failure points to; change the requirement only by agreement
    Treating tests as complete validation Nothing checks consent or whether P1 matters Review provenance and usefulness separately
    Letting AI write or polish discovery notes The submitted account is no longer your own record Write and de-identify notes yourself; keep AI in permitted work
    Counting S4-A as a real or approved equivalent activity There is no actual participation/approval record Label it practice and obtain the required arrangements
    Keeping withdrawn notes or lowering an alternative's ceiling Old confirmation is reused or fewer marks are available Stop use, follow removal, and preserve equal assessment limits
