    Turn a user need into an executable specification

    Week 4 · CI dashboard

    What should the program do, and why?

    Code cannot settle an unclear requirement

    Last week we located a behavior in source. This week the request is: "Show jobs needing attention."

    Does that mean failed, running, or something else?

    A fictional maintainer's recent task

    Run 12: passed
Run  9: failed
Run 11: running

    A "not passed" filter displayed 9 and 11. The maintainer opened 11, saw it was running and returned. A handwritten list of failures was the workaround.

    Course-authored scenario S4-A, not a participant observation.

    What did we observe?

    Classify each sentence:

    • The maintainer opened run 11 and returned.
    • Including running jobs may distract from finding failures.
    • All maintainers need notifications.

    Which statement can S4-A directly support?

    Observation, inference and unsupported claim

    Sentence Status
    Opened 11 and returned Supplied event
    Running jobs may distract Interpretation to investigate
    Everyone needs notifications Unsupported generalization

    A useful problem statement stays close to the user's task.

    Mechanism: From observation to a check

    An observed event becomes a bounded criterion, then an independent check decides what the evidence supports.

    A question that does not supply its answer

    Would our smart alerts save you time?

    Rewrite this to ask about a concrete recent event. What could the response help you learn?

    An event-based follow-up

    What did you do after opening the running job?

    This can reveal a workaround or another obstacle. It does not ask the participant to endorse our proposed interface.

    Your own discovery notes and problem reasoning remain AI-off.

    A bounded product decision

    For the classroom exercise, return IDs of runs whose status is exactly failed.

    Inputs are (integer ID, status) pairs, with statuses passed, failed or running.

    A UI, notifications and automatic retries are outside this small task.

    Ordering is an explicit design choice

    For this exercise, output IDs are ascending and duplicate-free.

    That convention makes the result precise. S4-A did not establish it as the fictional maintainer's preference.

    Selection, duplication and order each need an agreed rule.

    An acceptance example before implementation

    [(7, "failed"), (2, "running"),
 (7, "failed"), (3, "failed")]

    Write the exact output using the agreed rules. Which input checks more than simple filtering?

    Deriving the output

    Select failed:  7, 7, 3
Remove repeats: 7, 3
Ascending:     [3, 7]

    Each step follows a specification clause. The candidate implementation does not supply the expected answer.

    The proposed predicate

    ids = {run_id for run_id, status in runs if status != "passed"}
return sorted(ids)

    A generated implementation might look reasonable and still interpret "failed" incorrectly.

    One case that exposes the disagreement

    Which input makes status != "passed" disagree with status == "failed"?

    Give the input and expected output before reading the repair.

    Running does not mean failed

    Input:    [(2, "running")]
Required: []
Proposal: [2]

    The repair changes the predicate to status == "failed". Keep the duplicate/order case and an empty-list check as regressions.

    A testable criterion

    Given valid run pairs, calling failed_ids returns the ascending, duplicate-free IDs whose status is exactly failed.

    assert failed_ids([(2, "running")]) == []
assert failed_ids([]) == []

    Finite checks support these cases. They do not establish that users prefer the feature.

    A small specification connects the decisions

    S4-A: difficulty isolating failures
  -> problem statement
  -> failed-only selection, explicit order/non-goals
  -> input/output examples
  -> implementation and unchanged verification

    An assistant may propose implementation within the assignment's rules. The student owns discovery and the expected behavior.

    One request hides five decisions

    "Implement AC1" asks an agent to research, choose, plan, write and judge in a single step.

    You see its work only when the tests run.

    Five stages, a stop after each

    Research -> stop -> Propose -> stop -> Plan
         -> stop -> Implement -> stop -> Test -> stop

    At every stop a person decides: continue, narrow, go back or stop. The agent cannot check its own result.

    Each stage hands the next one a file

    research.md -> fresh session -> plan.md -> fresh session -> candidate

    The next session reads only the checked file and the paths it names. A wrong research claim becomes a wrong plan and wrong code: strike it at the first stop.

    Choose the delegation level

    Level Use it when
    Direct prompt Small edit, familiar code, one case checks it
    Plan first Bounded edit in an area you know
    Research, then plan The path crosses files you have not read
    Repeated research and plan The boundary is still uncertain

    Pick the least elaborate level that still leaves you an independent check.

    Research returns locations

    acceptance.py, CASES: six cases. verify also fails if the input changes.

    Open each cited location before moving on. A claim without a file and function is a question, not a finding.

    Three options come back

    • A: change the predicate inside broken
    • B: add failed_ids, checked by the same verify
    • C: add a status option to the run list screen

    Which option does the specification rule out, before any code?

    Ruling out C is a scope decision

    A web UI is a non-goal in our small PRD. A removes the counterexample the class relies on.

    Choose B and write down why. The choice is yours, not the agent's.

    Which clauses have no step?

    Plan step Check
    Keep status exactly failed AC1-mixed
    Return each ID once AC1-duplicate
    Sort ascending AC1-sort

    Compare with AC1 before reading on.

    Every clause gets a step and a check

    Missing step Check
    Return [] when nothing failed AC1-empty
    Use the input, not fixed values AC1-other-id
    Leave the input unchanged input-modified assertion

    Each check was written from AC1 before the code existed.

    Implement inside a bound

    Only failed_ids, in one new file, with no imports. acceptance.py stays unchanged.

    Read the candidate as text: the model's, or one of the three course candidates. A change outside the bound is rejected even when every check passes.

    A failed check points to a stage

    Failure Go back to
    Wrong predicate Implement
    A clause the plan never covered Plan
    A misread requirement Propose or Research

    Do not repair a failure by editing the check.

    Record where you stopped

    One line per stage, a decision at each stop, and where you narrowed or stopped the task.

    Stopping after Plan because the first step is still too large is a legitimate result.

    ci-dashboard: which claim do you strike?

    AC-W: the overview lists active projects, not archived ones.

    Claim Location
    R1 overview selects projects by owner_id domains/ci_dashboard.py:28-38
    R2 {% else %} prints No projects yet. for an empty list ci/overview.html:17-24
    R3 archive_project flips archived, deletes nothing domains/ci_dashboard.py:96-106
    R4 The overview query already skips archived projects domains/ci_dashboard.py:34

    Open each line before you answer.

    Option A, planned line by line

    • A: add AND archived=0 at domains/ci_dashboard.py:34
    • B: wrap each template row in {% if not project.archived %}; an owner with only archived projects gets a blank table

    Plan for A: change only line 34, and write test_overview_hides_archived and test_archived_project_page_opens.

    Stop after Plan

    The tests expose a case AC-W never names: every project archived.

    No projects yet. would be untrue, and Unarchive is reachable only by URL. Take both questions back to the specification before anyone edits code.

    Class practice and actual discovery

    The activity gives you a fresh case, S4-B, to practise on.

    Actual discovery for the discovery/specification workshop and M0 needs the established consent or an approved equivalent route. Do not relabel a fictional case as participation.

    Transfer: the ordering decision changes

    A new agreed requirement says "retain first occurrence order." The same failed IDs arrive as 7, 7, 3.

    What output now follows? Which specification, check and code need review before accepting the change?

    A change of requirement needs a new oracle

    The new expected output is [7, 3]. The previous [3, 7] expectation belongs to the old rule.

    Record the change in the specification's change log: the clause, the superseded check and why. A consistent specification and test can still need validation with users.

    Exit: "latest failure" is a new question

    A user asks for the latest failed run per pipeline. Our inputs contain only ID and status.

    Name one missing piece of information and a question that would let another person derive the expected output.

    M0 supplies the next change's contract

    Keep the problem, agreed criterion, evidence and open questions together. Record one staged round for your personal ci-dashboard slice in the M0 work record.
