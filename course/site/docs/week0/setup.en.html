    Set up, generate, then verify

    Week 0 prepares you to explain a model response, test a small program and keep an agent inside its workspace (LO1, LO2 and LO7). Budget three hours for setup, the primer, the diagnostic and safety checks together. If access or waiting consumes that time, use the fallback checklist.

    This page is the single student entry point for the sandbox checks, the approved hosted API route, key handling, per-run request and token limits and the replay alternative. Other student pages link here instead of repeating those rules.

    Prepare trusted course tools

    Use a reviewed checkout or audited student ZIP. Install Python 3.12, uv, Git and a local Docker engine that runs Linux containers, through your institution's supported path. The course runs these checks on a Linux x86-64 computer with a local Docker engine. On any other computer, run the same checks; if one fails, keep what it reports and use the fallback checklist.

    All generated code, shell commands and dependency scripts run through the course launcher; do not run an unknown repository command on the host. Run these course tools from the course root, in this order:

    python3 --version
uv --version
git --version
docker info --format '{{.OSType}}/{{.Architecture}}'
uv sync --locked
uv run --locked python scripts/doctor.py
uv run --locked python scripts/prepare_sandbox.py
uv run --locked python scripts/doctor.py --runtime

    docker info prints linux/ and your computer's architecture, for example linux/x86_64. If it prints an error instead, start the Docker engine before you go on.

    prepare_sandbox.py is the one step that needs network access. It downloads only the pinned sandbox image for your engine's platform and runs no student code; a first download can take several minutes. On success it prints one line, here for a Linux x86-64 engine:

    Pinned sandbox image for linux/amd64 is available; run the runtime checks next.

    If it prints Sandbox preparation failed: instead, the rest of that line names the cause. Fix that cause and run it again. Sandbox runs afterwards use that image with no network and never download anything.

    Check that you can run the practices

    doctor.py on its own checks your tools and the course configuration; it starts no container. doctor.py --runtime also runs the launcher's safety checks: workspace boundaries, blocked network access, resource limits, log redaction and prompt-only IPC.

    You can run the practices when doctor.py --runtime prints "status": "passed" and "can_run_practices": true. That covers every launcher exercise: the smoke test and diagnostic below, the primer with its supplied candidate, and lecture fixtures that use FAKE, the course's scripted model replies. It does not depend on a key. A step that asks a model for a new candidate also needs an open model route: the API route with your own key, or a published replay record. The hosted and replay fields of the same output say which route is open; "status": "disabled" under hosted means the API route is closed.

    Every launcher run repeats these safety checks before your command starts. One check waits out the 30-second run limit, so each launcher run takes at least half a minute.

    If a check fails

    If doctor.py reports false for a tool under checks, install that tool and run it again. doctor.py --runtime reports a launcher failure as failed_probe, failed_invariant and failed_exception; it never prints raw Docker or workload output. A launcher run whose safety checks fail shows the same value as invariant= inside its details field. Look up failed_invariant:

    failed_invariant Cause What to do
    boundary_probe_completion with failed_exception FileNotFoundError The docker command is not installed or not on your PATH. Install a local Docker engine, check that docker info works in the same terminal, then rerun.
    docker_context The docker command could not read its current context. Run docker context ls, select a local context with docker context use NAME, then rerun.
    local_docker_engine Docker points at a remote engine; the sandbox accepts only a local one. Select a context whose endpoint starts with unix://, then rerun.
    pinned_image_available The pinned sandbox image is missing, or the engine is not running. Start the engine, run prepare_sandbox.py again, then rerun.
    docker_engine_available The engine stopped answering. Restart the engine, wait until docker info works, then rerun.
    native_engine_platform The engine does not run Linux containers, or its architecture is not one the sandbox accepts. Use a local engine that runs Linux containers natively; the sandbox never uses emulation. Without one, use the fallback checklist.
    pinned_image_platform The prepared image is for another platform, for example after you switched engines. Run prepare_sandbox.py again, then rerun.
    container_start Docker refused to start the sandbox container. Restart the engine and check its disk space and memory, then rerun.
    any other value A safety boundary did not hold. Stop. Bring failed_probe, failed_invariant and failed_exception to course support.

    Never enable network access, add privileges, mount the Docker socket or enlarge limits to make a check pass.

    Select the approved configuration

    The course resolver is the sole source of profile identity, endpoint, model, sampling, and request/token limits. Save its output once and print the two values that launcher commands need:

    uv run --locked python scripts/hosted_profile.py --profile approved-hosted --json > week0-profile.json
uv run --locked python -c 'import json; p = json.load(open("week0-profile.json")); print("VERSION", p["contract"]["version"]); print("DIGEST", p["models_sha256"])'

    In every launcher command, replace VERSION and DIGEST with the two printed values. Never override an endpoint, model, header, sampling parameter or limit. Until the hosted payload is enabled, the resolver output is marked enabled: false; keep the public version/digest and follow the fallback checklist. When the hosted payload is enabled, the reviewed setup flow supplies HOSTED_CONFIG from that resolver output. Do not create, edit or substitute this file; a student-controlled configuration is rejected by the launcher.

    API route and key handling

    If you choose the API route, register with one approved configuration listed by the resolver and create a key in your own provider account. Store it on your own device in a file outside Git and outside every course workspace. Create an empty private file first:

    mkdir -p -m 700 ~/.config/course
install -m 600 /dev/null ~/.config/course/hosted-key

    Open ~/.config/course/hosted-key in your editor, paste the key as the only line, and save. Then check the file without printing the key:

    uv run --locked python scripts/doctor.py --key-file ~/.config/course/hosted-key

    Under hosted, "key": "available" means the file is usable. invalid means the file is empty, holds anything besides the key on one line, sits inside the course folder, or other users can read it or its folder. If your editor changed its permissions, run chmod 600 ~/.config/course/hosted-key.

    The launcher host-side broker reads that file. The key never enters the sandbox environment, filesystem, prompt, trajectory, screenshot, output or log. Do not put it in an argument or ordinary environment variable. A shared Docker host is replay-only; do not store a personal key there. If a key is ever committed or pasted into a prompt, screenshot or log, revoke it with the provider immediately and notify the teaching team.

    Each real run uses the resolver's published request and token limits; the launcher enforces those per-run limits. Ask your provider about its own spending limit or prepaid credit before using a personal key. The broker records provider usage for the run and never prints the key. A missing, invalid or unreachable key route has a fixed failure category; then use the replay route or the fallback checklist.

    Replay route

    You may choose replay without giving a reason. When a reviewed teaching record is available, the student launcher replays the same task through course_llm. Write predictions first, inspect the replay, recompute the checks and explain the result in your own work. Mark replay evidence in P1. Its score ceiling is identical to the API route and it is not a real API call.

    sh scripts/course-sandbox --profile approved-hosted --version VERSION --digest DIGEST --model replay --replay-file REPLAY_FILE --replay-digest REPLAY_DIGEST --workspace week0-work -- python generate.py

    This is a template. After the teaching team publishes a frozen record, replace REPLAY_FILE and REPLAY_DIGEST with the supplied path and digest. Until then, do not run it: the public file is a synthetic placeholder, and the launcher refuses it before starting a container. Keep the JSON result and verification together; inspect any model suggestion and run proposed code through the launcher again.

    Run a small isolated exercise

    Create a separate week0-work directory containing only public exercise files. Symlinks, special files, host paths, credentials and teacher assets are refused. Dependencies cannot be downloaded inside the sandbox. Save this smoke test as verify.py:

    from pathlib import Path
from sandbox_model import emit_artifact

Path("result.txt").write_text("verified\n")
assert Path("result.txt").read_text() == "verified\n"
emit_artifact("result.txt")

    Run the verification through the launcher:

    sh scripts/course-sandbox --profile approved-hosted --version VERSION --digest DIGEST --workspace week0-work --output week0-smoke -- python verify.py

    Expected result: the launcher prints JSON with "exit_code": 0, and week0-smoke/result.txt contains verified. The launcher saves files only from a run that exits with 0, and only into a new --output directory.

    Diagnostic and primer

    Copy the public diagnostic files into a new workspace and run them through the same launcher:

    mkdir week0-diagnostic
cp assessment/diagnostic/run.py assessment/diagnostic/questions.json week0-diagnostic/
sh scripts/course-sandbox --profile approved-hosted --version VERSION --digest DIGEST --workspace week0-diagnostic -- python run.py
sh scripts/course-sandbox --profile approved-hosted --version VERSION --digest DIGEST --workspace week0-diagnostic -- python run.py --answers answers.json

    The first command prints the questions. Before the second, create answers.json in week0-diagnostic with your editor. This is public formative feedback, not a threshold or an official grade. Follow the primer before asking for model output.

    Troubleshoot and submit

    If the resolver or a launcher run fails, keep the fixed category and use If a check fails. If the API route is unavailable, use replay or the fallback checklist. Keep the work product, verification and a brief explanation together with one AI-use note; do not submit keys, full conversations or environment dumps.
